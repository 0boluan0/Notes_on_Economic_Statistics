# AutoResearch Clearly Explained (and how to use it)

## 一句话总结
这支视频把 Andrej Karpathy 提出的 AutoResearch 讲成了一个非常清晰的模式：固定评测、只开放一个可修改对象、给定时间预算，让 agent 持续提出假设、运行实验、保留有效改动，从而把“优化”变成一个自动循环；它真正稀缺的不是执行，而是指标设计与约束设计。

- AutoResearch 到底是什么，它和普通“让 AI 帮我做事”有什么本质区别？

## 详细梳理
### 1. 视频给出的核心定义：不是聊天，而是闭环优化
视频一开始就把 AutoResearch 定义为一种“让 AI 自主改进”的循环，而不是一次性的回答器。它的基本动作是：
- agent 先提出一个假设，猜测某个改动可能让结果更好
- 然后修改目标对象并跑一次实验
- 再用固定评测去判断这次改动是不是更优
- 如果更优，就保留并提交；如果更差，就回滚并继续下一轮

这里最重要的不是“AI 会不会写代码”，而是整个系统是否形成了一个可重复、可比较、可自动淘汰失败方案的 loop。视频把这个点讲得很直白：真正的价值在于让 agent 在你睡觉时也能持续做实验，而不是停留在“你问一句，它答一句”的水平。

### 2. `prepare.py` 的意义：把“什么算更好”锁死
视频最早进入技术细节的地方，是解释为什么 `prepare.py` 不能被 agent 修改。它的作用不是普通脚本，而是“定义更好”的那一层评测标准。
- 如果 agent 能改评测脚本，它就可以通过篡改评分逻辑来伪造进步
- 因此，必须有一部分内容是只读的、稳定的、不可被优化器本身碰到的
- 这使得系统优化的是目标，而不是“测量目标的方式”

这个设计其实非常关键，因为它揭示了 AutoResearch 的第一原则：你不是把自由度全部交给 agent，而是非常严格地把自由度限制在一个小范围内。视频后面反复强调，指标一旦设错，系统只会非常高效地把错误目标优化到极致。

### 3. 为什么要固定时间预算：保证实验可比
视频里有一个很好的类比：如果两个求职者，一个给 7 天，一个给 7 分钟，他们的结果根本不能直接比较。AutoResearch 也是一样。
- 每次实验必须在相同时间预算内完成
- 这样你比较的是“想法本身有没有更好”，而不是“某次训练得更久、算力花得更多”
- 固定时间预算后，每一次 commit / revert 才有可比性

这一点把 AutoResearch 和随意调参、无约束试错区分开了。它不是“跑得越久越好”，而是“在同样预算下，谁更有效”。

### 4. 视频真正想强调的，不是 ML，而是“任何可测量任务”
虽然 Karpathy 的原始例子来自 GPT-2 训练脚本优化，但视频花了很大篇幅在扩展这个模式：
- 只要目标可以压缩成清晰指标
- 只要实验可以自动跑完
- 只要能把修改范围约束在一个对象上

那么这个模式就不只适用于模型训练，还可以迁移到营销、交易策略、网页性能、prompt engineering，甚至部分个人流程优化上。

视频在这里有一个明显的观点升级：未来真正稀缺的不是“谁会做执行”，因为执行会越来越便宜；真正稀缺的是谁能定义正确的 metric、约束和搜索空间。也就是说，瓶颈从“手工做实验”转向“设计实验制度”。

### 5. 三文件架构：`program.md`、`train.py`、`prepare.py`
视频把 AutoResearch 的最小架构压缩成三个文件：
- `program.md`：人类写给 agent 的总说明书，规定目标、约束、原则、允许动作
- `train.py`：agent 唯一允许修改的对象。它可以是代码、配置、prompt、数学表达式，只要是你想优化的那一个对象
- `prepare.py`：不可触碰的评测逻辑，负责输出那个标量分数

这个拆法的价值在于，它把系统中的三种角色拆开了：
- 决策边界由人定义
- 搜索动作由 agent 执行
- 成败判断由固定 evaluator 输出

这其实是一种很值得借鉴的 agent 工程模式。很多所谓“agent 会乱跑”的问题，本质上不是模型不够强，而是这三件事没有分开。

### 6. 适用场景：交易、营销、代码性能、prompt
视频给了几个具体用例，核心都不是行业，而是是否满足“可自动评测”的条件。
- 交易：agent 改交易规则，用历史数据回测，以 Sharpe ratio 之类的指标评分
- 营销：agent 改邮件文案、广告素材、落地页、标题或缩略图，通过转化率判断优劣
- 开发：让 agent 直接面向代码库做“让它更快”的优化，以性能 benchmark 为指标
- Prompt engineering：把 system prompt 当成可变对象，自动寻找更好的表达、上下文结构和措辞

这几个例子共同说明，AutoResearch 不是某个特定产品，而是一种搜索框架。只要你能把“更好”客观化，它就能工作。

### 7. 成功条件：三个条件缺一不可
视频后半段把成功条件总结得非常明确：
- 一个清晰、单调方向明确的标量指标
- 一个无需人工介入的自动评测流程
- 一个且仅一个允许 agent 修改的文件或对象

这三个条件其实分别对应三件事：
- 指标清楚，系统才知道往哪走
- 评测自动，系统才能真的在你不在场时跑起来
- 修改面收窄，系统才不会因为搜索空间过大而失控

如果这三点不满足，就算也在“研究”，也不算视频意义上的 AutoResearch。

### 8. 失败条件：主观目标、慢反馈、坏指标
视频明确指出，一旦“更好”是主观判断，AutoResearch 就容易失效，比如：
- 品牌设计
- UX 审美
- 大多数定价问题

原因不是这些领域不重要，而是它们通常缺少快速、稳定、低成本的客观反馈。即便某些场景能通过大流量 AB test 把主观问题转成客观指标，门槛也依然高。视频还反复提醒：坏指标会把系统推向错误方向，而且会推得非常坚定。这是所有自动优化系统最值得警惕的风险。

### 9. Karpathy 的远景：分布式 AutoResearch 网络
视频引用了 Karpathy 的一个更大愿景：像当年的 SETI@home 一样，把分散算力组织起来，给大规模 AI 研究循环供能。

这个愿景的重点不在于单个 demo，而在于把“实验搜索”做成可扩展网络：
- 多台机器
- 大量 agent
- 不断并行探索不同假设
- 统一通过 evaluator 保留有效进展

这已经接近“递归式自我改进”的直觉图景了。视频也用较强的修辞把它描述成前沿 AI 实验室最终会走向的方向。

### 10. 最实用的部分：作者现场演示如何搭最小 loop
视频最后一段其实最有操作价值。作者没有继续停留在概念层，而是现场搭了一个网页性能优化 loop。

他的流程大致是：
- 先把 Karpathy 的原始仓库克隆到 `original/`，作为参考
- 再新建一个 `website/` 项目，生成一个很普通的 portfolio 网站
- 用 benchmark 脚本测本地加载速度，得到 baseline
- 参考原仓库的 `program.md`，为这个具体网站场景重写一份新的 `program.md`
- 把 baseline 提交进版本历史
- 然后要求 agent 按 `program.md` 约束，持续跑实验、记录结果、自动 commit / revert

视频里展示的 benchmark 用的是 Puppeteer，本质上是在本地自动测页面速度。这就是一个很好的例子：
- 可变对象：网站代码
- 固定评测：benchmark.mjs / evaluator
- 指标：页面加载时间
- 时间预算：每轮实验都在受控预算里完成

### 11. 演示真正说明了什么
视频给出的最直观证据，不是“它很先进”，而是 agent 在几分钟内完成了多轮“失败即回滚、成功即保留”的闭环。
- 第一次尝试变差，于是 agent 自己确认并回退
- 后面找到改进，从约 50ms 降到 33ms
- 再降到 28ms，最后提到大约 25ms 左右

这一段说明了两个关键事实：
- AutoResearch 的价值来自快速、连续、无人值守的试验密度
- 它不要求每次都成功；恰恰相反，允许大量失败并快速丢弃，才是它的正常工作方式

### 12. 我对这支视频的整体判断
这支视频的优点是结构非常清楚，把 AutoResearch 解释成了一个可迁移的工程模式，而不是一个神秘名词。缺点是修辞上明显偏“创业叙事”和“未来机会”包装，比如“这会制造百万富翁”“奇点早期阶段”等表述，更多是动员式说法，不应直接当成技术结论。

如果把营销包装剥掉，剩下的硬核内容其实非常值得保留：
- 把评测锁死
- 把修改面缩小
- 把结果压成标量
- 把试验预算标准化
- 允许 agent 在可控边界内高速试错

这五点，才是这支视频真正可复用的部分。

## 关键论点与依据
- AutoResearch 的本质是“自动实验闭环”，不是更会聊天的 agent。依据：开场定义与假设-改动-评测-提交/回滚循环说明（00:05-00:18，01:53-02:24）。
- `prepare.py` 之所以不能被修改，是为了防止 agent 通过篡改评测标准来“作弊式成功”。依据：对 `prepare.py` 的解释（01:32-01:49，04:35-04:43）。
- 固定时间预算是实验可比较性的前提。依据：求职者 7 天 vs 7 分钟的类比（02:32-02:56）。
- 这个模式的适用边界，不取决于行业，而取决于任务能否被自动评测为单一指标。依据：从模型训练推广到营销、交易、开发、prompt 的讨论（04:55-05:23，07:02-09:45）。
- AutoResearch 最容易在“主观目标”上失效，因为目标函数不稳定。依据：对品牌设计、UX、定价的反例讨论（10:17-10:55）。
- 视频中的网页性能 demo 证明了该模式的工程可行性：即使早期实验失败，系统也能自动回退并继续搜索。依据：benchmark + commit/revert + 速度从约 50ms 降到 33ms / 28ms / 25ms（15:51-19:46）。

## 可复用框架
### 一个通用的 AutoResearch 设计框架
1. 先定义唯一目标。
   - 把“更好”压成一个清晰标量，例如延迟、转化率、Sharpe ratio、正确率。
2. 再定义唯一可变对象。
   - 只允许 agent 改一个文件、一个 prompt、一个策略模块，避免搜索空间失控。
3. 把 evaluator 锁死。
   - 评测脚本必须只读，不能被优化器本身碰到。
4. 固定实验预算。
   - 每轮用相同时间、相同资源、相同环境跑，保证可比。
5. 用版本控制记录结果。
   - 成功就提交，失败就回滚，让历史成为搜索轨迹。
6. 监控指标异化。
   - 持续检查 metric 是否仍代表你真正想要的目标，防止“优化得很对，但方向本身错了”。

### 一个判断“适不适合上 AutoResearch”的快速清单
- 我能不能把目标压成单一分数？
- 这个分数能不能自动计算，不需要人看？
- 每轮实验能不能在足够短时间内完成？
- 我能不能明确限制 agent 只改一块东西？
- 即使连跑几十轮，我还能解释这个指标为什么值得优化吗？

只要这几条里有两三条答不上来，就不该急着上 AutoResearch，而应该先修目标函数和评测制度。

## 对我的启发
- 这支视频最有价值的地方，不是“AI 会自动优化一切”，而是提醒我：很多工作真正难的不是执行，而是把目标定义成可以被机器反复试验的形式。
- 如果把这个思路迁移到个人工作流，值得尝试的不是“让 agent 替我做所有事”，而是先找那些有硬反馈的局部任务，例如网页性能、prompt 表现、抓取成功率、脚本运行时间、笔记抽取准确率。
- 对知识管理来说，这也提醒我区分两件事：一类任务适合开放式思考，一类任务适合封闭式优化；把两者混在一起，往往既得不到创造性，也得不到稳定改进。
