# FlashAttention：为什么关注显存往返？

← [[dao2022FlashAttentionFastMemoryEfficient|返回论文脉络]] · [[FlashAttention 原文.pdf#page=4|本段原文：§2.2–3.1，p.4]]

论文先重新描述了一个熟悉的问题：长序列注意力的实际瓶颈，除了要做多少运算，还取决于中间结果在哪里存、来回搬多少次。读懂这一点，后面的分块算法才有明确目的。

## 从熟悉的公式走到执行过程

已有原子 [[缩放点积注意力]] 给出了计算目标：对每个 query 算出各个 key 的权重，再加权汇总 value。论文 §2.2 为简化表达写成 $S=QK^\top$、$P=\operatorname{softmax}(S)$、$O=PV$；实际使用的缩放和掩码可以纳入相同计算过程。

现在把关注点从公式转到它的中间结果。论文的标准实现（Algorithm 0）依次：

1. 算出完整分数矩阵 $S$，写入显存。
2. 从显存读出 $S$，计算 Softmax，再把完整权重矩阵 $P$ 写回。
3. 读出 $P$ 和 $V$，计算最终输出 $O$。

对于长度为 $N$ 的自注意力，$S$ 和 $P$ 都有 $N^2$ 个位置。它们在这个实现中既占空间，又产生大量读写。[[FlashAttention 原文.pdf#page=4|对照 Algorithm 0]]

## 为什么这会拖慢 GPU？

论文区分两层存储：**HBM** 是容量较大的 GPU 显存；**SRAM** 是更小、更快的片上存储。计算时需要在这些层级之间搬运数据，论文称之为 IO。这里讨论的 IO 是 GPU 内部的数据读写。

如果计算单元在等待数据，减少几次算术运算未必能明显缩短总时间。作者因此追问：**能否在片上算完一个小块就把它用掉，只把后续需要的结果写回？** [[FlashAttention 原文.pdf#page=3|§2.1 的硬件背景]] · [[FlashAttention 原文.pdf#page=2|Figure 1 的执行示意]]

这一步要接到 [[注意力计算与显存]]：计算涉及 $N^2$ 个位置，并不意味着必须同时保存 $N^2$ 个中间值。原子说明这个通用区分；论文把区分变成了具体的执行算法。

## 问题因此变成了什么？

可以保留 [[稠密注意力二次成本]] 中“所有位置对仍需参与计算”的判断，同时重新设计中间结果的存储与使用。FlashAttention 的 dense 版本就沿着这个方向展开。

但一个障碍马上出现：[[Softmax]] 的一整行共用分母，不能把每个块各自归一化后简单平均。要边读边算，就必须在看见新块后正确修正旧结果。
