## 1. 没有预期行为，就没有真正的测试

<!-- bilingual-en:start -->
*1. Testing needs an expected behavior*
<!-- bilingual-en:end -->

写一个用于课堂小数值例子的 `mean(values)` 前，先给出[[函数契约]]：正常输入是非空数值列表，计算其浮点平均值；这个接口另行规定空列表抛出 `ValueError`。这里不承诺任意量级下的精确算术，浮点误差与溢出仍需另行处理。这些约定分别决定正常结果与失败行为。若接口没有规定空输入，你发现除零只能说明需要澄清接口，不能凭个人偏好把“返回零”当成正确答案。

<!-- bilingual-en:start -->
Give the classroom function `mean(values)` a [[函数契约|contract]] for small numerical examples: compute a floating-point mean for a nonempty numerical list, and raise `ValueError` for an empty list. This is not a promise of exact arithmetic at arbitrary magnitudes; rounding and overflow require separate treatment. Without an empty-input policy, division by zero raises an interface question, not an automatic right to substitute zero.
<!-- bilingual-en:end -->

[[测试用例]]安排一次实验，[[测试判据]]决定它是否通过。例如 `[2, 4]` 是输入，预期结果 `3.0` 是判据；空列表是另一次输入，预期 `ValueError` 才是它的判据。只调用函数并确认“没崩溃”，会放过返回 `99` 的程序。[[软件测试]]必须把实际行为与预期比较，包括契约关心的返回值、异常和状态变化。

<!-- bilingual-en:start -->
A [[测试用例|test case]] arranges an experiment; a [[测试判据|test oracle]] decides whether it passes. Input `[2, 4]` has expected result `3.0`; input `[]` has an expected `ValueError`. Merely observing no crash would accept a result of `99`. [[软件测试|Software testing]] compares all contract-relevant behavior with expectations.
<!-- bilingual-en:end -->

```python
def mean(values):
    if not values:
        raise ValueError("mean requires at least one value")
    return sum(values) / len(values)


def check_mean():
    if mean([2, 4]) != 3.0:
        raise AssertionError("wrong mean")
    try:
        mean([])
    except ValueError:
        pass
    else:
        raise AssertionError("empty input must raise ValueError")
```

这是手写的最小检查，不是完整测试框架。它故意用 `if` 与显式 `raise`，让检查在 `python -O` 下仍执行；后面会解释它与 `assert` 语句的差别。对于一般浮点结果，还要按误差要求选择判据，不能照搬这里可精确表示的 `3.0`。

<!-- bilingual-en:start -->
This is a minimal handwritten check, not a testing framework. Explicit `if` and `raise` remain active under `python -O`; later we distinguish them from the `assert` statement. General floating-point results need an appropriate error criterion rather than copying this exact comparison to representable `3.0`.
<!-- bilingual-en:end -->

## 2. 从规格找边界，再用代码寻找遗漏

<!-- bilingual-en:start -->
*2. Derive boundaries from the specification, then inspect code for omissions*
<!-- bilingual-en:end -->

[[黑盒测试]]先不看实现，按规格做[[分区与边界选例]]：平均数可以检查单元素、多个相同元素、正负抵消、空输入。分区只是选例的理由，不是“每组挑一个就保证其余都正确”。[[白盒测试]]再看分支和循环，补上尚未执行的路径。两者提供不同证据，应当互补。

<!-- bilingual-en:start -->
[[黑盒测试|Black-box testing]] derives [[分区与边界选例|partitions and boundaries]] from the specification: singleton, repeated values, cancellation and empty input. A partition motivates cases; one representative does not certify every member. [[白盒测试|White-box testing]] then examines branches and loops for unexecuted paths. The two approaches complement each other.
<!-- bilingual-en:end -->

Lecture 12 的绝对值反例说明了为什么[[代码覆盖率]]不能代替判据与边界：

<!-- bilingual-en:start -->
Lecture 12's absolute-value counterexample shows why [[代码覆盖率|coverage]] cannot replace an oracle and boundary cases:
<!-- bilingual-en:end -->

```python
def bad_abs(x):
    if x < -1:
        return -x
    else:
        return x
```

测试 `2` 和 `-2`，两条分支都经过，结果也都正确；但 `-1` 仍返回 `-1`。这里既没有漏走分支，也不是忘了比较结果，而是遗漏了错误阈值附近的输入。[[覆盖率不能证明正确]]因此是独立边界，不是覆盖率定义的附带口号。

<!-- bilingual-en:start -->
Tests on `2` and `-2` execute both branches and return correct answers, yet `-1` returns `-1`. The missing evidence concerns an input near the wrong threshold, not an unvisited branch or an absent comparison. [[覆盖率不能证明正确|Coverage does not prove correctness]] is a separate boundary.
<!-- bilingual-en:end -->

[[单元测试]]先检查 `mean` 这样的组件；[[集成测试]]再检查它与成绩统计函数配合后，结果形状与异常传播是否符合接口。[[回归测试]]不是第三个同类“层级”，而是改动后检查已有行为是否退化，可以出现在任一层级。用户完整流程也值得检查，但不能用它替代组件层的定位证据；把外部依赖换成替身时，也只能证明相对于那个替身的行为。

<!-- bilingual-en:start -->
[[单元测试|Unit tests]] examine a component such as `mean`; [[集成测试|integration tests]] examine its interaction with the grade-statistics function. [[回归测试|Regression testing]] describes checking for deterioration after changes, not a third testing level. Whole-user-flow checks and dependency substitutes can be useful, but neither replaces evidence about real component interactions.
<!-- bilingual-en:end -->

## 3. 沿回文程序区分“没有调用”与“共享对象”

<!-- bilingual-en:start -->
*3. Separate a missing call from shared-object mutation*
<!-- bilingual-en:end -->

[[调试]]从已观察到的偏差寻找原因。把任务固定为：判断整数列表是否回文，结果为布尔值；本例还明确要求保持输入列表不变。用 `[1, 2]` 可以观察预期 `False` 与错误 `True`，不用带着长输入猜。

<!-- bilingual-en:start -->
[[调试|Debugging]] investigates an observed discrepancy. Here the task is to return whether an integer list is palindromic; this example explicitly also requires preserving the input. `[1, 2]` exposes expected `False` versus erroneous `True` without a large distracting input.
<!-- bilingual-en:end -->

```python
def palindrome_v1(items):
    temporary = items
    temporary.reverse
    return temporary == items


def palindrome_v2(items):
    temporary = items
    temporary.reverse()
    return temporary == items


def palindrome_v3(items):
    temporary = items[:]
    temporary.reverse()
    return temporary == items
```

第一版的 `temporary.reverse` 语法合法，只取得方法，并没有调用；两边仍是同一列表，所以比较为真。先提出一个能被观察推翻的假设：“反转根本没有执行。”在语句前后观察列表，或加括号重跑，就能检验它。这是[[调试假设检验]]，不是一口气重写整个函数。

<!-- bilingual-en:start -->
In version one, `temporary.reverse` is valid attribute access, not a call. The unchanged list compares equal to itself. Test the hypothesis “reversal never executed” by observing state or adding parentheses and rerunning. This is [[调试假设检验|hypothesis-driven debugging]], not wholesale rewriting.
<!-- bilingual-en:end -->

第二版确实反转了，却仍为真，而且调用者的输入变成 `[2, 1]`。这次该问[[对象别名|两个名称是否指向同一个对象]]；不是怀疑比较符。第三版先复制外层列表，再反转副本，才给出 `False` 并保留原列表。只调整外层顺序不修改元素，[[复制层级边界|浅复制已经足够]]，不需要无条件换成深复制。

<!-- bilingual-en:start -->
Version two reverses the list yet still returns true and mutates the caller's input to `[2, 1]`. Now inspect [[对象别名|aliasing]]. Version three reverses a separate outer list, returning false while preserving the original. Since only outer order changes, [[复制层级边界|a shallow copy suffices]].
<!-- bilingual-en:end -->

每个版本都用新建的输入重跑，避免上一次测试的副作用污染下一次。检查空列表、单元素、真正回文与非回文，并保留输入不变的检查。[[最小失败复现]]要求缩小后仍出现同一类失败；并不保证能机械地找到全局最短输入。若失败偶发，先记录相关输入和环境；涉及随机调用时，按[[伪随机复现]]保存重放条件，单独记录 seed 未必足够。

<!-- bilingual-en:start -->
Use fresh inputs for each version to avoid contamination. Check empty, singleton, palindrome and non-palindrome cases, including input preservation. [[最小失败复现|Failure reduction]] must retain the same failure; it does not promise a globally smallest input. For intermittent failures, record relevant conditions; randomized runs need the replay protocol described in [[伪随机复现|pseudorandom reproducibility]], not merely a seed.
<!-- bilingual-en:end -->

## 4. 异常先改变控制流，再由接口决定是否接住

<!-- bilingual-en:start -->
*4. Exceptions transfer control; contracts determine who should handle them*
<!-- bilingual-en:end -->

[[Python异常]]不是“打印了一条错误消息”。例如 `mean([])` 执行 `raise` 后，不再执行本次调用中余下的正常语句；按[[异常传播]]寻找处理器。调用者的 `except ValueError` 能否接住它，由[[异常类型匹配]]决定。[[返回值与打印|打印一句警告不会自动返回替代结果]]，捕获后继续也不会自动修复数据。

<!-- bilingual-en:start -->
A [[Python异常|Python exception]] is not merely an error message. After `mean([])` raises, normal execution of that call stops and [[异常传播|propagation]] searches for a handler according to [[异常类型匹配|type matching]]. [[返回值与打印|Printing a warning supplies no replacement return value]], and continuing does not automatically repair data.
<!-- bilingual-en:end -->

Lecture 13 的 `pairwise_div(Lnum, Ldenom)` 规定：等长、非空的数值列表逐项相除；分母含零时抛出 `ValueError`。这不是“跳过那个元素继续算”。跳过会改变输出位置与含义，是另一个接口。下面将长度、非空和零分母都显式验证；这是比课堂 `assert` 示例更明确的运行时边界，仍假定元素为数值。

<!-- bilingual-en:start -->
Lecture 13 specifies pairwise division of equal-length, nonempty numerical lists, raising `ValueError` for zero denominators. Skipping an element changes output positions and defines a different interface. The following version explicitly validates lengths, emptiness and zero denominators; unlike the classroom assertions these checks remain active at runtime. Numerical elements are still assumed.
<!-- bilingual-en:end -->

```python
def pairwise_div(Lnum, Ldenom):
    if len(Lnum) != len(Ldenom) or not Lnum:
        raise ValueError("lists must be nonempty and equally long")
    if 0 in Ldenom:
        raise ValueError("zero denominator")
    return [num / den for num, den in zip(Lnum, Ldenom)]
```

原课堂代码的一个答案版本误写 `if 0 in L2`，读取了外部变量而非参数 `Ldenom`。原文件保留为来源，但不能把这个版本当成契约的正确实现。详细对照在课堂记录中；回归检查应当独立改变外部 `L2`，确认函数行为只取决于声明的输入。

<!-- bilingual-en:start -->
One supplied answer mistakenly checks external `L2` instead of parameter `Ldenom`. The source file remains intact, but that version is not a correct implementation of the contract. The lecture record documents it; a regression check can vary external `L2` independently of the parameters.
<!-- bilingual-en:end -->

## 5. 同一个空成绩表，可以暴露四种不同策略

<!-- bilingual-en:start -->
*5. Four strategies for the same empty grade list*
<!-- bilingual-en:end -->

课堂把求均值函数作为参数传给 `get_stats(class_list, avg_func)`，正好复用[[一等函数对象]]。外层遍历学生，内层策略决定如何对待空成绩。假设某学生成绩是 `[]`，四个版本的结果如下；完整函数与输入例子可在 [[13_Exceptions and Assertions#课堂长例：空成绩列表|课堂记录的成绩统计例子]] 连续阅读。

<!-- bilingual-en:start -->
The lecture passes an averaging function into `get_stats(class_list, avg_func)`, reusing [[一等函数对象|first-class functions]]. The outer loop processes students; the supplied policy handles empty grades. The [[13_Exceptions and Assertions#课堂长例：空成绩列表|lecture's grade-statistics example]] contains the complete functions and inputs.
<!-- bilingual-en:end -->

| 版本 | 遇到空成绩时的行为 | 必须看清的意思 |
| --- | --- | --- |
| `avg1` | `ZeroDivisionError` 向外传播 | 没有在此处处理 |
| `avg2` | 捕获后打印，隐式返回 `None` | 警告不是有效平均数 |
| `avg3` | 捕获后打印，返回 `0.0` | 把缺失成绩记零的政策，不是空集平均数 |
| `avg4` | 启用断言时产生 `AssertionError` | `-O` 去掉检查后仍会除零 |

<!-- bilingual-en:start -->
`avg1` propagates `ZeroDivisionError`; `avg2` warns but implicitly returns `None`; `avg3` assigns zero as a policy for missing grades; `avg4` raises `AssertionError` when assertions are enabled but divides by zero when that assertion is removed by `-O`.
<!-- bilingual-en:end -->

这就是[[异常处理策略]]：先决定接口允许传播、重试、跳过还是默认值，再写处理器。没有人批准把缺失当零，就不能因为“程序终于跑完了”而接受 `avg3`。同样，若输入来自用户，按[[输入解析边界]]区分文本转换失败与转换成功后不满足业务范围。

<!-- bilingual-en:start -->
[[异常处理策略|Failure policy]] comes before handlers: decide whether propagation, retry, skipping or a default is permitted. Completion alone does not authorize treating missing grades as zero. For user input, [[输入解析边界|separate parsing failures from invalid domain values]].
<!-- bilingual-en:end -->

## 6. 把正常路径、恢复路径和清理职责分开

<!-- bilingual-en:start -->
*6. Separate success, recovery and cleanup*
<!-- bilingual-en:end -->

按[[异常捕获边界]]缩小 `try` 的语句范围，并捕获自己确实知道如何处理的类型。`try` 正常走到结尾才进入[[try的else分支]]；这个 `else` 自己抛出的异常，不会倒回同一组 `except`。例如转换输入成功后再进行计算，可以避免把后续计算的编程错误误报成“用户没有输入整数”。

<!-- bilingual-en:start -->
Choose a narrow [[异常捕获边界|catch boundary]] and handle only understood failures. The [[try的else分支|else clause]] runs after normal fallthrough of the `try`; errors raised in that `else` are not caught by the same handlers. Keeping later computation outside the conversion handler avoids mislabeling programming defects as invalid user input.
<!-- bilingual-en:end -->

[[finally清理]]处理离开这段控制流时的清理，但不是自动回滚；其中新的异常或 `return` 还可能替代正在传播的结果。需要向调用者报告失败时，按[[主动抛出异常]]使用 `raise`；改变抽象层而保留原始原因时看[[异常链]]，需要调用者按领域失败分类处理时才定义[[自定义异常]]。

<!-- bilingual-en:start -->
[[finally清理|Finally]] handles cleanup, not automatic rollback; a new exception or return there can replace an in-flight outcome. Use [[主动抛出异常|raise]] to report failure, [[异常链|exception chaining]] to preserve a cause across abstraction layers, and [[自定义异常|custom exceptions]] when callers need distinct domain failure categories.
<!-- bilingual-en:end -->

最后回到[[Python断言]]。它在启用时检查本应成立的条件，失败产生可被捕获的 `AssertionError`，不是无条件终止整个程序。`-O` 可以删除整条断言，包括条件里的副作用；所以[[断言不替代输入验证|必须执行的验证不能交给 assert]]。本路径开头用显式 `raise AssertionError` 写检查，正是为了把异常类型与会被优化移除的语句区别开。

<!-- bilingual-en:start -->
A [[Python断言|Python assertion]] checks an expected invariant when enabled; failure raises catchable `AssertionError`, not unconditional process termination. `-O` can remove the entire statement, including side effects. Hence [[断言不替代输入验证|required validation cannot rely on assert]]. The opening test deliberately used explicit `raise AssertionError` to separate the exception type from the removable statement.
<!-- bilingual-en:end -->

## 7. 把修复变成下一次改动的保护

<!-- bilingual-en:start -->
*7. Preserve a fix as evidence for the next change*
<!-- bilingual-en:end -->

完成一次修复时，用同一判据确认旧实现失败、新实现通过，再运行其他相关输入与调用者测试。不要只保留新实现“演示成功”的输入。若功能正确但速度不够，转到[[性能剖析]]定位这次工作负载的资源消耗；它与复杂度证明回答不同问题，见[[计时与渐近分析]]。Missing Semester 的 [[03_Computer_Science/99_Miscellaneous/the_missing_semester#第 7 讲 调试及性能分析|第 7 讲]]复用这里的调试原子，补充工具层的观察方法。

<!-- bilingual-en:start -->
After a fix, check that the same oracle rejects the old implementation and accepts the new one, then test related inputs and callers. Retain the failure, not merely a successful demonstration. For correct but slow code, use [[性能剖析|profiling]] and distinguish it from [[计时与渐近分析|asymptotic analysis]]. [[03_Computer_Science/99_Miscellaneous/the_missing_semester#第 7 讲 调试及性能分析|Missing Semester Lecture 7]] shares these debugging atoms and adds observation tools.
<!-- bilingual-en:end -->
