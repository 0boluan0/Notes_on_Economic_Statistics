# The Missing Semester

## 课程定位

>[!note]
> 这门课真正想补的不是某个单一工具，而是程序员的工作流能力。
> 它默认你已经会写代码，但还没有系统掌握：
> - 如何高效使用 shell 和命令行环境
> - 如何真正把编辑器变成生产工具
> - 如何用 Git、调试工具、构建系统和安全工具支撑长期工作
> - 如何让自己的环境、脚本和流程可复用、可迁移、可自动化

大学里的很多课程会教你算法、体系结构、操作系统、机器学习，但不会专门训练你如何高效使用每天都要碰的工具。于是很多人虽然会写程序，却仍然停留在“复制粘贴命令”“出问题再搜”“环境一换全崩”的阶段。`The Missing Semester` 想解决的正是这个问题。

它的核心精神不是“多背命令”，而是：

- 把命令行看成可编程环境，而不是黑窗口
- 把编辑器看成语言和工作流，而不是输入框
- 把 Git 看成数据模型，而不是神秘命令集合
- 把调试、性能分析、安全和构建看成工程习惯，而不是高级附属品

## 第 1 讲 课程概览与 shell

资料：<https://missing-semester-cn.github.io/2020/course-shell/>

### 这讲解决什么问题

这一讲要你明白：为什么即使今天图形界面极强，shell 仍然是程序员最该掌握的接口之一。

GUI 适合覆盖高频、固定、被设计者预先考虑到的交互；shell 适合开放式组合、批量处理、自动化和远程工作。程序员需要的恰恰经常是后者。

### shell 是什么

shell 是一个命令解释器，也是一个编程环境。

它至少做三件事：

- 读取你输入的命令
- 解析命令、参数、重定向、管道和变量
- 找到对应程序并执行

因此 shell 不是“一个程序列表”，而是“组织程序协作的语言层”。

### 核心概念

- `command`：你要执行的程序
- `argument`：传给程序的参数
- `current working directory`：程序默认工作的目录
- `PATH`：shell 在哪些目录里搜索可执行程序
- `absolute path` vs `relative path`：绝对路径从根目录开始，相对路径相对于当前工作目录
- `.` 与 `..`：当前目录和父目录

### 最先要掌握的命令

```bash
pwd
cd /path/to/dir
cd ..
cd ~
ls
ls -l
man ls
which echo
echo $PATH
```

这些命令表面简单，但它们连着 shell 的最基本模型：你现在在哪、系统会去哪里找程序、一个程序又是如何被文档化的。

### 重定向与管道

shell 中最重要的抽象之一，是“程序读输入流、写输出流”。

- `>`：把标准输出写到文件
- `>>`：追加写入
- `<`：从文件读取作为输入
- `|`：把前一个程序的输出接到后一个程序的输入

这意味着你可以把很多小工具像积木一样串起来，而不是写一大坨程序。

>[!example] 典型工作流
>
> ```bash
> echo hello > hello.txt
> cat hello.txt
> cat < hello.txt > hello2.txt
> ls -l / | tail -n 1
> curl --head --silent google.com | grep -i content-length
> ```
>
> 这类命令真正重要的不是具体输出，而是你要形成直觉：
> 一个程序的输出通常都能成为下一个程序的输入。

### 权限与 root

`ls -l` 里最容易被忽视但非常重要的内容是权限位。

- 目录的 `x` 更多表示“可进入/可搜索”
- 文件的 `x` 表示“可执行”
- root 用户几乎不受限制，所以 `sudo` 很强也很危险

官网里专门用亮度文件的例子说明了一件很容易踩坑的事：`sudo echo 3 > brightness` 往往失败，不是因为 `echo` 没有 root 权限，而是因为重定向是 shell 先做的，写文件这一步不是由 `sudo echo` 完成的。

正确思路通常是：

```bash
echo 3 | sudo tee brightness
```

### 这讲真正要记住什么

- shell 不是老旧接口，而是可组合、可自动化的文本接口
- 你执行的不是“魔法命令”，而是“程序 + 参数 + 环境 + 输入输出流”
- 管道和重定向是 shell 最有力量的抽象
- 出现权限问题时，要分清“谁在执行程序”和“谁在做文件重定向”

- 课程不是在教新编程语言
- 课程也不是深入某个单一系统
- 课程真正关心的是“你如何和计算机高效交互”
- 后面几讲会围绕 shell、编辑器、版本控制、调试、安全等长期生产力主题展开

#### 08:00-16:00 shell 的角色、命令结构、参数和引号意识

视频随后转到 shell 最基本的交互模型。讲者让你先接受一个事实：在命令行里，你输入的每一行通常都可以拆成“程序名 + 参数 + 选项”。这和写函数调用很像，只不过函数是在终端里被 shell 解析后启动。

这一段逐步建立的知识点有：

- 什么是 shell prompt
- 什么叫命令、参数、选项
- 为什么 `man` 和 `--help` 是第一参考入口
- 参数中如果含空格或特殊字符，就必须考虑 quoting 和 escaping
- 引号规则不是语法洁癖，而是决定参数到底如何被 shell 解释

#### 16:00-24:00 当前工作目录、相对路径、绝对路径、home 目录

接下来视频进入文件系统导航。这一部分看上去基础，但讲者是在给后面的所有内容搭底座：命令之所以能省略一大堆路径，是因为每个进程都有当前工作目录。

视频里隐含的推进顺序大致是：

- `pwd` 告诉你当前坐标
- `cd` 改变坐标
- 相对路径总是相对于当前工作目录解释
- 绝对路径从根目录开始解释
- `~` 代表 home 目录
- `.` 和 `..` 是相对路径里最常见的定位符

讲者在这一段其实已经在训练一种空间感。没有这种路径直觉，后面写脚本、跑 Git、远程 SSH 都会一直迷路。

#### 24:00-32:00 常用文件操作、`PATH`、环境变量和命令发现方式

视频到中段开始把“我在哪”和“系统怎么找到我要的程序”连起来。讲者一边展示 `ls`、`mv`、`cp`、`mkdir` 这类命令，一边把注意力转向 `PATH` 和环境变量。

这一段最关键的不是命令名，而是三个判断：

- shell 到底去哪里找可执行程序
- 为什么同一个命令在不同机器上可能对应不同版本
- 为什么环境变量会影响程序行为

因此这里应该记住：

- `echo $PATH` 用来查看搜索路径
- `which` / `type` 帮你确认真正执行的是谁
- 环境变量本身也是 shell 和程序沟通的一部分

#### 32:00-40:00 标准输入输出、重定向、管道作为组合抽象

视频后半段开始进入第一讲真正最有力量的内容：程序并不是只会“在屏幕上打印”。它们会读写标准流，而 shell 可以把这些流重新接线。

讲者在这段里等于完成了两个认知升级：

- `>`、`>>`、`<` 是在改写程序与文件/终端之间的连接
- `|` 是把一个程序的输出直接接到另一个程序的输入

这也是为什么视频开始出现 `ls -l / | tail -n 1`、`curl ... | grep ...` 这类例子。讲者不是在炫命令，而是在演示 shell 的核心能力其实是“让小程序互相配合”。

#### 40:00-48:00 root、权限、`sudo` 与重定向陷阱

最后几分钟，讲者专门讲了一个命令行新手极容易踩的坑：权限问题不是单纯“在命令前加 sudo”就结束。因为 `sudo` 提升的是命令执行权限，而重定向往往在 shell 层就先发生了。

这一段最该牢牢记住的是亮度文件例子背后的逻辑：

- `sudo echo 3 > brightness` 容易失败
- 原因不是 `echo` 没有权限
- 真正打开文件写入的是当前 shell
- 所以需要 `echo 3 | sudo tee brightness`

讲者借这个例子强调了第一讲的总目标：别把命令行看成一串魔法字符串，要知道每一步到底是谁在解释、谁在执行、谁在碰文件。

### 逐条知识点展开

#### 1. 终端、shell、程序三者不是一回事

初学者很容易把“终端窗口”“shell”“命令”混成一个东西。课程其实在一开始就在帮你拆开这三层：

- 终端模拟器是那个显示黑框、接收键盘输入、输出字符的程序
- shell 是运行在终端里的命令解释器，例如 `bash`、`zsh`
- `ls`、`grep`、`python` 这些是 shell 帮你启动的外部程序

这件事重要，因为后面很多现象都要靠它解释：

- 为什么 `cd` 必须是 shell 内建，而不能只是普通外部程序
- 为什么有些行为是 shell 完成的，例如变量替换、通配展开、重定向
- 为什么程序本身并不知道你是从终端里、图形界面里还是脚本里启动它的

#### 2. shell 在做的事情是“解析并启动”

当你输入一行命令时，shell 不是原样照搬地“执行文字”，它会经历一整套解析流程：

- 按空格和引号规则切分参数
- 做变量展开、通配展开、命令替换
- 识别重定向和管道
- 判断命令是内建、函数、别名还是外部可执行文件
- 最后基于 `PATH` 找到程序并启动

所以“命令为什么会这样表现”通常要先问一句：这是 shell 的行为，还是被调用程序自己的行为？

#### 3. 路径系统是所有命令行操作的坐标系

课程第一讲虽然看起来只是在讲 `pwd`、`cd`、`ls`，但它真正要你建立的是路径直觉：

- 每个进程都有当前工作目录
- 相对路径总是相对于当前工作目录解释
- 绝对路径从文件系统根开始解释
- `.` 是当前目录，`..` 是父目录，`~` 是 home 目录

如果你没有这个坐标系，后面所有脚本、Git、SSH、Makefile 都会经常出错。命令行里大量 bug 本质上都是“我以为程序在 A 目录下运行，实际上它在 B 目录下”。

#### 4. `PATH` 决定 shell 去哪里找可执行程序

当你直接输入 `python` 或 `rg` 时，shell 并不知道这些程序在哪。它会按 `PATH` 里列出的目录顺序查找。

因此需要形成几个基本习惯：

- 用 `echo $PATH` 查看搜索路径
- 用 `which` 或 `type` 看一个命令实际指向什么
- 理解“同名命令为什么会执行错版本”，往往就是 `PATH` 顺序问题

这一点在你同时安装多个 Python、多个 `node` 或多个自定义脚本时尤其关键。

#### 5. 手册页是命令行里的第一参考源

课程没有把 `man` 当成“补充工具”，而是当成标准工作流的一部分。命令行世界的默认假设是：工具的用法应该由它自己的文档解释。

最基础的查阅方式有：

- `man ls`：看完整手册
- `tldr tar`：看常用示例
- `cmd --help`：快速看选项

真正重要的能力不是记住所有选项，而是知道：

- 我能快速查
- 我能看懂 synopsis 里参数和选项的表示方式
- 我知道哪些选项是“只看一眼就够”的，哪些需要长期内化

#### 6. 标准输入、标准输出、标准错误是命令行组合的基础协议

课程把 shell 描述为“文本接口”，而 `stdin` / `stdout` / `stderr` 就是这个接口的协议。

- `stdin`：程序读入的地方
- `stdout`：正常结果输出的地方
- `stderr`：错误信息输出的地方

很多工具之所以能随意组合，就是因为它们都遵守这套约定。程序不需要知道后面接的是屏幕、文件还是另一个程序，它只负责按规则读写流。

#### 7. 重定向是“把流接到别处”

第一讲里的 `>`, `>>`, `<` 看上去只是文件写入技巧，实际上是在改写程序和外部世界连接的方式：

- `>` 覆盖写入标准输出
- `>>` 追加写入标准输出
- `<` 让程序从文件而不是键盘读取
- `2>` 把标准错误单独导向文件
- `/dev/null` 是“丢弃输出”的黑洞

这也是为什么很多“安静执行”的命令会写成：

```bash
cmd > /dev/null 2> /dev/null
```

这里不是“神秘咒语”，而是明确地同时丢弃正常输出和错误输出。

#### 8. 管道的意义是“用小程序拼大工作流”

课程反复强调：命令行最强的地方不是单个工具多厉害，而是你可以让很多小工具通过 `|` 连起来。

`|` 的意义不是“先打印再复制”，而是：

- 前一个程序写到 `stdout`
- 后一个程序从 `stdin` 读取
- shell 把这两者连起来

一旦理解了这个抽象，很多事情就自然了：

- `journalctl | grep sshd | sort | uniq -c`
- `curl ... | jq ...`
- `find ... | xargs ...`

这也是 Missing Semester 整门课最核心的方法论之一：让每个工具只做好一件事，再用管道把它们拼起来。

>[!example] 第一讲真正想让你形成的直觉
>
> ```bash
> curl --silent https://example.com \
>   | grep -i title \
>   | head -n 5
> ```
>
> 这里真正重要的不是这三条命令本身，而是你要意识到：
> 网络响应、文本过滤、截断输出，本来是三件不同的事，但在 shell 里可以自然串成一个工作流。

#### 9. 权限问题要分清“读、写、执行”分别针对什么对象

课程虽然没有展开讲完整 UNIX 权限系统，但已经把最容易混淆的点提示出来了：

- 文件的 `r/w/x` 和目录的 `r/w/x` 含义并不相同
- 对目录来说，`x` 更像“可进入/可搜索”
- 对文件来说，`x` 才表示“可执行”
- `sudo` 提升的是命令执行权限，不会自动替你改写 shell 已经完成的重定向行为

所以 `sudo echo 3 > file` 失败，是因为：

- `echo` 确实以 root 权限运行了
- 但 `>` 是当前 shell 先处理的
- 真正尝试打开文件写入的是原 shell，而不是 `echo`

这也是为什么 `sudo tee` 是更稳的写法。

#### 10. 第一讲的真正产出是一个心理模型

如果只把第一讲记成“会几个命令”，这讲就学浅了。它的真正产出是下面这个模型：

- shell 负责解释和编排
- 程序负责读写和计算
- 文件、流、路径和权限共同构成工作环境
- 通过重定向和管道，程序被接成更大的工作流

后面脚本、Git、SSH、数据处理、调试，其实都建立在这套模型之上。

## 第 2 讲 Shell 工具和脚本

资料：<https://missing-semester-cn.github.io/2020/shell-tools/>

### 这讲解决什么问题

第一讲让你学会手动使用 shell；这一讲让你学会把 shell 变成自动化工具。

当你发现自己总是在重复执行一串命令时，就应该开始考虑脚本、函数、别名和更合适的命令行工具。

### Shell 脚本的核心地位

shell 脚本并不是“比 Python 更高级”的语言，而是“更贴近命令行工作流”的语言。

它擅长的事包括：

- 调命令
- 连管道
- 重定向
- 批量处理文件
- 在系统环境里做轻量自动化

它不适合承担大型程序的复杂数据结构、复杂错误处理和长期维护逻辑。

### 变量、引号、控制流

#### 变量赋值

```bash
foo=bar
echo "$foo"
echo '$foo'
```

关键点：

- 赋值时等号两侧不能有空格
- 双引号会展开变量
- 单引号基本保持原样

#### 条件执行

```bash
false || echo "Oops, fail"
true && echo "Things went well"
false ; echo "This will always run"
```

关键点：

- `&&`：前一个成功才继续
- `||`：前一个失败才继续
- `;`：无论如何都继续

### 特殊变量

官网特别强调 Bash 的一组特殊变量，因为它们极常用：

- `$0`：脚本名
- `$1` 到 `$9`：位置参数
- `$@`：全部参数
- `$#`：参数个数
- `$?`：前一条命令退出码
- `$$`：当前脚本进程号
- `!!`：上一条完整命令
- `$_`：上一条命令最后一个参数

### 命令替换与进程替换

#### 命令替换

```bash
files=$(ls)
now=$(date)
```

shell 会先执行命令，再把输出结果替换进去。

#### 进程替换

```bash
diff <(ls foo) <(ls bar)
```

这类写法适合“某个工具想读文件，但你手头只有命令输出”的场景。

### 函数、脚本与 shebang

函数和脚本的关键差异：

- 函数运行在当前 shell 进程里，能直接改当前环境
- 脚本通常在新的进程里执行，不能直接修改父 shell 的当前目录
- 脚本可以用任意解释器，不局限于 shell

shebang 的作用是告诉系统用什么解释器执行脚本。

```bash
#!/usr/bin/env bash
#!/usr/bin/env python3
```

`/usr/bin/env` 的价值在于可移植性，它会根据 `PATH` 去找解释器。

### 查找与搜索工具

#### `find`

适合按文件树、属性、时间、权限等复杂条件搜索。

```bash
find . -name '*.tmp' -exec rm {} \;
find . -name '*.png' -exec magick {} {}.jpg \;
```

#### `fd`

官网推荐把它看成更现代、更友好的 `find` 替代品。

- 默认更快
- 语法更简单
- 默认行为更符合直觉

#### `locate`

基于数据库索引，速度快，但结果可能不够新，也不如 `find` 灵活。

#### `grep` / `ripgrep`

- `grep`：经典文本搜索
- `rg`（ripgrep）：更快，更适合代码仓库

### 代码质量工具

shell 脚本很容易写出“能跑但很脆”的东西，所以课程推荐用 `shellcheck` 之类工具检查常见错误。

比如：

- 忘记给变量加引号
- 误用 `for file in $(ls)`
- 条件判断写法不稳

### 这讲真正要记住什么

- shell 脚本擅长“命令行自动化”，不擅长“大型通用程序”
- 变量、引号和退出码是 Bash 最常见的坑源
- 函数和脚本最大的差别在于是否运行在当前 shell 环境
- 工具选择也很重要：`fd`、`rg` 这类现代工具常常比传统工具更顺手

### 逐条知识点展开

#### 1. Bash 的强项是“编排命令”，不是“取代通用语言”

课程对 Bash 的定位非常清楚：它是一门为了命令行工作流而设计的语言。

它天然适合：

- 启动外部程序
- 传递参数
- 做重定向和管道
- 在文件和目录上批量操作
- 写短小的自动化脚本

它不适合：

- 复杂数据结构
- 稳健的大型程序
- 需要长期维护的复杂业务逻辑

因此课程其实在教一种判断力：当任务主要是在“调系统工具”时先想 shell；当任务开始涉及复杂状态和抽象时，应及时切换到 Python 等语言。

#### 2. 变量赋值、引号和空格是 Bash 的第一大坑

`foo=bar` 和 `foo = bar` 在 Bash 里不是“风格差异”，而是完全不同的语义。前者是变量赋值，后者会被解释成运行程序 `foo`，并把 `=` 和 `bar` 当作参数。

同样，引号规则直接决定脚本是否稳健：

- 单引号几乎完全保留字面值
- 双引号会展开变量，但保留整体为一个参数
- 不加引号时，空格和通配展开都可能发生

所以课程强调“给变量加引号”不是形式主义，而是防止脚本在遇到空格、特殊字符、空字符串时崩掉。

#### 3. `$?`、退出码和短路运算是 shell 的控制流核心

shell 世界里，很多判断不是靠布尔值对象，而是靠退出码：

- `0` 表示成功
- 非 `0` 表示失败或特殊状态

于是就有了三种最常见的写法：

- `cmd1 && cmd2`：前者成功才执行后者
- `cmd1 || cmd2`：前者失败才执行后者
- `cmd1 ; cmd2`：无论如何都执行后者

这不只是语法糖，而是命令行工作流最自然的“异常传播”机制。

#### 4. 特殊变量必须熟到能随手用

课程列出来的这些 Bash 特殊变量都很高频：

- `$0`：脚本名
- `$1...$9`：位置参数
- `$@`：所有参数
- `$#`：参数个数
- `$?`：上一条命令退出码
- `$$`：当前 shell 或脚本的进程号
- `!!`：上一条完整命令
- `$_`：上一条命令最后一个参数

这些变量的意义在于：它们把“脚本自身的运行上下文”暴露给你。写 shell 脚本时，参数传递、错误检查、重跑命令，几乎都离不开它们。

#### 5. `[[ ... ]]`、`test`、条件和循环是 shell 编排的基本语法

课程没有把 Bash 当通用语言细讲，但要求你掌握最实用的一层：

- `if` / `then` / `fi`
- `case`
- `for`
- `while`
- 函数

真正重要的是理解这些控制结构通常用来做什么：

- 遍历参数或文件列表
- 根据退出码决定是否继续
- 对批量文件做相同处理
- 把一串高频命令封成函数

而不是把 Bash 当成“能做一切的编程语言”。

#### 6. 命令替换和进程替换让 shell 可以把“命令结果”当数据

课程特别强调两个高级但非常实用的特性：

- `$(cmd)`：把命令输出替换成字符串
- `<(cmd)`：把命令输出伪装成一个文件名

它们分别解决两类问题：

- 你想把命令结果放进变量或参数里
- 某个工具要求输入必须是文件，但你的数据恰好来自另一个命令

`diff <(ls foo) <(ls bar)` 这类写法的价值不在于酷，而在于你开始把“程序输出”视为可继续组合的数据对象。

#### 7. 通配展开和大括号展开是批处理的常用武器

课程里提到两种常见展开：

- 通配（globbing）：如 `*.sh`, `foo?.txt`
- 大括号展开（brace expansion）：如 `convert image.{png,jpg}`

它们的作用是减少重复输入，把一组结构相似的参数交给同一个程序处理。

不过这里有一个重要边界：这些展开是 shell 先做的，不是程序做的。因此如果写法不当，展开结果可能比你预期多很多或少很多。

#### 8. `shellcheck` 的意义是“Bash 太容易写出脆脚本”

课程专门推荐 `shellcheck`，原因很现实：很多 Bash 脚本不是不会跑，而是只对“作者当时那组输入”能跑。

它常抓到的问题包括：

- 变量未加引号
- 对空值处理不稳
- `for file in $(ls)` 这种脆弱写法
- 条件判断使用不规范

所以 Missing Semester 的态度不是“Bash 很简单不用检查”，而是恰恰相反：正因为 Bash 容易写出脆代码，所以更需要工具护栏。

#### 9. 找文件、找代码、找历史命令，本质上是三类不同搜索

课程把搜索拆成三层，而很多人平时把它们混用：

- 找文件路径：`find`、`fd`、`locate`
- 找文件内容：`grep`、`rg`
- 找你自己曾经输过的命令：`history`、`Ctrl+R`、`fzf`

这三类问题应该用三类工具。

`find` 强在表达复杂筛选条件，比如：

- 按类型找
- 按时间找
- 按权限找
- 找到后 `-exec` 执行操作

`fd` 强在交互体验更好、默认行为更贴近日常使用。

`locate` 强在预建索引，查找非常快，但结果可能不是最新。

`grep` / `rg` 则是内容搜索，核心是按模式匹配文本，而不是找文件名。

#### 10. `rg` 和 `fd` 代表的是一类“现代命令行工具”的设计哲学

课程推荐 `fd`、`rg`，不是单纯偏爱新工具，而是因为这些工具在默认行为上更符合现代开发者习惯：

- 自动忽略 `.git`
- 输出更适合人眼阅读
- 性能更好
- 常见参数更少、更直觉

这对应着 Missing Semester 的一个隐含观点：提高效率不只是“苦练老工具”，也包括在同类工具里选择默认体验更好的那个。

#### 11. 历史搜索和目录跳转解决的是“记忆负担”

程序员经常重复相似命令和目录切换。如果每次都重打一遍，不仅慢，而且容易出错。

课程因此强调：

- `Ctrl+R` 反向搜索历史命令
- `history | grep ...` 程序化搜索历史
- `fzf` 做模糊查找
- `autojump` / `fasd` 按频率和最近访问历史跳目录

这类工具的价值不在“少打几个字”，而在于把长期使用的环境训练成会配合你的记忆和习惯。

>[!example] 第二讲最典型的自动化场景
>
> ```bash
> for file in "$@"; do
>   grep -q foobar "$file" || echo "# foobar" >> "$file"
> done
> ```
>
> 这段脚本体现了 shell 的几个关键点：
> 参数遍历、退出码判断、输出重定向、批量文件处理。它短，但正是 shell 最擅长的事。

#### 12. 第二讲真正建立的是“能否脚本化”的意识

看完这讲以后，最重要的变化不是“会不会写 Bash”，而是：

- 看到重复劳动会先想自动化
- 知道 shell 脚本应该写到什么程度就该停
- 遇到搜索、筛选、批量处理时会自然想到合适工具

这才是 Shell 工具和脚本这一讲最值钱的产出。

## 第 3 讲 编辑器 (Vim)

资料：<https://missing-semester-cn.github.io/2020/editors/>

### 这讲解决什么问题

这讲不是在教你一个“终端里的古老编辑器”，而是在教一种高效率的编辑思想。

程序员的大量时间并不花在连续输入文本上，而是花在：

- 阅读代码
- 跳转位置
- 选中对象
- 做小范围修改
- 在多个文件之间切换

Vim 之所以值得学，是因为它把这些高频动作设计成了一个可组合的语言。

### Vim 的哲学

#### 多模态

Vim 的一个核心假设是：阅读/导航/编辑是不同动作，不应该都用“插入字符”的同一套键盘语义。

常用模式包括：

- 正常模式
- 插入模式
- 替换模式
- 可视模式
- 命令模式

你大部分时间应该在正常模式，而不是插入模式。

#### 命令可组合

Vim 的接口像一种微型语言：

- 移动命令像“名词”
- 编辑命令像“动词”
- 次数和修饰语进一步改变它们的含义

例如：

- `dw`：删除一个词
- `d$`：删除到行尾
- `ci(`：改括号内内容
- `3w`：向前移动三个词

#### 00:00-08:00 为什么编辑器值得单独讲一整节

#### 08:00-16:00 四种主要模式、最小可用编辑流程

这一段视频把 Vim 最反直觉的部分讲清楚：同一个键在不同模式下含义不同。讲者从 normal、insert、visual、command-line 四种模式讲起，然后演示最小工作流：

- 输入文字
- `Esc` 回到普通模式
- `:w` 保存
- `:q` 退出

这一段的重点不是“现在就能很快”，而是先让你接受：Vim 的操作不是围绕鼠标和菜单，而是围绕模式切换和键盘命令。

#### 16:00-24:00 移动命令、计数、把导航做成语言

视频随后进入移动命令。讲者一步步展示 `h j k l`、`w`、`b`、`e`、`0`、`$`、`gg`、`G` 等，让你意识到 Vim 的第一生产力不是删除或插入，而是“非常快地定位到目标位置”。

这一段要抓住的推进逻辑是：

- 编辑器里最耗时间的常常是导航
- Vim 把导航压缩成短小可组合命令
- 计数前缀让“重复 n 次”变成语法一部分

一旦这个逻辑成立，后面的删除、替换、复制都会自然很多。

#### 24:00-32:00 动作命令、operator + motion、重复操作

这一段是 Vim 真正开始“像语言”的地方。讲者把 `d`、`c`、`y` 这类 operator 和前面学过的 motion 组合起来，形成 `dw`、`d$`、`c0` 这类高密度命令。

视频在这里想完成的认知升级是：

- Vim 不是一堆散装快捷键
- 它更像“动作 + 目标范围”的组合系统
- 只要学会少数原子命令，就能推导出大量操作

这也是为什么会觉得 Vim 难，但一旦过了门槛，速度和稳定性都会显著提升。

#### 32:00-40:00 visual mode、yank/paste、text objects 和缓冲区意识

中后段视频进入更高级但也更实用的部分。讲者开始讲 visual mode、复制粘贴、text objects，并把 buffer 的概念引进来。

这一段最关键的知识点包括：

- visual mode 适合显式选择范围
- `y`、`p` 配合寄存器构成复制体系
- text objects 让操作直接面向单词、引号、括号、段落等语义对象
- buffer 说明 Vim 不是只会在一个文件里来回跳

这一步意味着 Vim 不再只是“终端里能用的编辑器”，而开始成为结构化操控文本的环境。

#### 40:00-48:00 搜索替换、宏、窗口分屏、配置和学习路径

最后几分钟，讲者把 Vim 的高阶收益点集中展示了一轮：搜索替换、宏录制、窗口切分、帮助系统和 `vimtutor`。这不是为了让你一口吃完，而是给出一条长期成长路线。

收尾逻辑大致是：

- 当你已经能基本导航和编辑时，宏会让重复修改出现飞跃
- 分屏和多 buffer 会把 Vim 变成真正的工作空间
- 配置值得投入，但必须建立在理解之上
- 最务实的下一步不是抄大配置，而是做 `vimtutor`

所以第三讲视频的真正结论是：先建立最小可用流，再持续把高频动作压缩进键盘语言。

### 逐条知识点展开

#### 1. 这讲真正讨论的是“编辑思想”，不是“Vim 冷门技巧”

课程花一整讲讲 Vim，并不是因为 Vim 本身必须成为唯一编辑器，而是因为它把“高效编辑”这件事表达得最清楚。

程序员的大量时间不是在连续打字，而是在：

- 导航到目标位置
- 选中某一段文本
- 重复相似修改
- 在文件间跳转
- 在窗口间切换

Vim 恰好把这些动作设计成一门很强的“编辑语言”。

#### 2. 模式化编辑的核心是“同一个键在不同语境下含义不同”

Vim 最反直觉但也最有威力的设计是 mode：

- Normal mode：发编辑命令
- Insert mode：插入文本
- Visual mode：选择文本
- Command-line mode：执行 `:` 开头命令

初学者最大障碍通常是“为什么不能直接打字”，但课程强调：一旦把大多数时间放回 normal mode，你会发现编辑器开始像一个操作文本的工具，而不只是输入框。

#### 3. Vim 把编辑做成了“动词 + 名词/范围”的组合语言

这一点是整讲最值得内化的地方。很多命令不是死背，而是组合出来的：

- `d` 是 delete
- `c` 是 change
- `y` 是 yank
- `w` 是 word
- `)` 是句子
- `}` 是段落

于是：

- `dw`：删到下一个单词
- `ci(`：改括号里的内容
- `ya"`：复制引号中的文本
- `d$`：删到行尾

课程想让你意识到，Vim 的威力来自可组合性，而不是命令数量。

#### 4. 文本对象是 Vim 比“会快捷键”更深一层的能力

很多编辑器也支持移动和删除，但 Vim 的文本对象让操作可以直接面向语义单元：

- 单词
- 句子
- 段落
- 括号内内容
- 引号内内容
- HTML 标签包围的内容

你不是在“从第 13 个字符删到第 25 个字符”，而是在“删除这个参数列表内部内容”。

这让编辑动作变得更稳定，也更贴近程序员真实想做的修改。

#### 5. 缓冲区、窗口、标签页是三个不同层级

课程专门提醒了一点：Vim 里的 buffer、window、tab 和很多 GUI 编辑器不一样。

- buffer 是文件内容本体
- window 是 buffer 的可视视图
- tab 更像一组窗口布局

理解这个模型以后，你会更清楚：

- 为什么一个文件可以在多个窗口同时显示
- 为什么 tab 不是“文件页签”的简单等价物
- 为什么分屏、跳文件和组织工作区是三件不同的事

#### 6. 搜索、替换和宏代表了“从单点编辑到批量编辑”

课程后半段展示的不是“高级花活”，而是 Vim 真正开始替你省时间的地方：

- `:s/foo/bar/g` 做范围替换
- 正则替换配合分组引用做结构性改写
- `q{register}` 录制宏，`@{register}` 重放

宏尤其重要，因为它解决的是“重复但不完全规则”的编辑任务。很多事情不值得写脚本，但手工做 50 次又太蠢，这正是宏的用武之地。

>[!example] 为什么宏是视频里非常关键的一部分
>
> 当一批文本结构相近、但还没规整到值得上脚本时，Vim 宏可以把“人眼判断 + 机械重复”结合起来。课程用 XML 转 JSON 风格转换演示的，正是这种中间地带的任务。

#### 7. 多窗口和多文件导航是 Vim 真正走向“工作环境”的标志

如果你只会在单文件里插入删除，其实还停留在入门层。课程把 `:sp`、`:vsp`、窗口切换讲出来，是因为真实开发总是在：

- 看代码和文档对照
- 在实现和测试之间来回跳
- 左边看 log，右边改代码

因此 Vim 的价值不只是“编辑快”，还在于它把导航、对照和批量修改组合到一个环境里。

#### 8. 配置的意义是把“偶尔会”变成“默认会”

课程没有鼓励你一上来复制一大坨别人配置，而是强调两个步骤：

- 先形成稳定的最小工作流
- 再把高频动作固化进配置

典型配置包括：

- 行号、缩进、搜索高亮
- leader 键映射
- 插件管理
- 设定默认编辑器 `EDITOR=vim`

配置的真正作用不是炫，而是把常用能力从“想起来才会用”变成“默认就在手边”。

#### 9. Vim 模式并不局限于 Vim 本体

课程专门提到 shell、readline、浏览器、Jupyter 等环境的 Vim 模式，想传达的是：Vim 的很多收益来自“统一的键盘语义”。

如果你在：

- shell 命令行
- 浏览器页面跳转
- REPL
- 编辑器

都能用相似的移动和编辑手法，那么你的整个工作流会更连贯。

#### 10. 学 Vim 的正确方式不是“一天学完”，而是渐进替换日常动作

课程给出的实际策略非常务实：

- 先完成 `vimtutor`
- 先学移动、插入、删除、复制、粘贴、撤销这些硬需求
- 每次在编辑时感觉“这一定有更快的方法”就去查
- 只吸收真正高频的能力

这意味着 Vim 学习本身就是一种持续优化过程，而不是一次性背命令。

## 第 4 讲 数据整理

资料：<https://missing-semester-cn.github.io/2020/data-wrangling/>

### 这讲解决什么问题

现实里的数据往往不是“直接拿来就能分析”的，它通常是日志、CSV、命令输出、半结构化文本，需要经过一连串变换才变成有用信息。

数据整理的关键不是某一个工具，而是：

- 理解输入是什么
- 明白目标输出要长什么样
- 选择合适的小工具逐步把前者变成后者

### 核心工作流思想

课程用日志处理说明了一个非常典型的思路：

1. 先过滤噪音
2. 再提取感兴趣字段
3. 再排序、统计或聚合
4. 必要时把中间结果保存下来

这与 shell 的哲学完全一致：不要一上来就写大程序，先把小工具串起来。

### 正则表达式

正则是数据整理的基本功。至少要熟悉这些模式：

- `.`：任意单字符
- `*`：前一模式重复零次或多次
- `+`：前一模式重复一次或多次
- `[abc]`：字符集合
- `(A|B)`：或
- `^`：行首
- `$`：行尾

课程也特别提醒了正则的现实问题：

- 不同工具的正则方言有差异
- 贪婪匹配很容易匹配过头
- 正则非常强大，但并不总是最稳的解决方案

### 高频工具

#### `grep`

做过滤，找匹配行。

#### `sed`

做流式替换与简单重写，最经典语法是：

```bash
sed 's/REGEX/SUBSTITUTION/'
```

#### `awk`

按字段处理文本，适合：

- 取列
- 统计
- 条件筛选
- 简单汇总

#### `sort` / `uniq`

适合排序与去重统计。

#### `cut` / `paste`

适合按分隔符抽列、拼列。

#### `less`

适合把长输出变得可读。

### 远程数据整理

课程里一个非常好的习惯是：尽量在数据所在位置先过滤，再传输结果。

```bash
ssh myserver 'journalctl | grep sshd | grep "Disconnected from"' > ssh.log
```

这不只是“会用 ssh”，而是理解了：

- 网络也是成本
- 过滤应该尽量前置
- 管道可以跨机器工作

### 这讲真正要记住什么

- 数据整理的本质是“把输出逐步逼近目标格式”
- 管道是组织数据变换的主干
- 正则表达式很重要，但也容易误伤
- 不要默认所有问题都要上 Python；很多问题先用命令行就能解决

### 按视频时间顺序的逐段讲义

#### 00:00-08:00 什么是 data wrangling，为什么程序员离不开它

第四讲开头先解释“数据整理”这个词到底在说什么。讲者强调，现实里的数据很少直接长成你想要的样子，通常是日志、半结构化文本、命令输出或表格碎片，需要经过多轮变换。

视频开场希望你建立的思维是：

- 数据整理不是一次性神操作
- 而是一串连续的格式变换
- shell 管道特别适合承载这种逐步变形的过程

#### 08:00-16:00 从 SSH 日志开始，先删掉不需要的部分

讲者随后选了 SSH 登录日志作为主例子。这不是随便选的，因为日志天然具备“信息很多，但你真正要的只有一小部分”的特点。

这一段视频的推进是：

- 先观察原始日志长什么样
- 决定哪些字段不需要
- 用 `sed` 或类似工具把稳定重复的前缀去掉
- 把行文本逐步逼近“只剩用户名/IP/动作”的形式

讲者其实是在现场示范：数据整理的第一步通常不是统计，而是先减噪。

#### 16:00-24:00 正则表达式逐段拆解、捕获组和匹配边界

中段视频开始把正则真正展开。讲者会一边写模式，一边解释每个括号、量词、可选项到底匹配什么。这个过程很重要，因为很多人对正则只有“能抄会抄”的层面。

这段里最该抓住的是：

- 为什么需要扩展正则
- `?`、`+`、`*`、`()` 在这里各自承担什么作用
- 为什么同一模式在日志里有时会多吃或少吃
- 捕获组是怎样把“匹配”进一步变成“提取”动作的

#### 24:00-32:00 `sed` 到 `awk` 的过渡：从整行文本到按字段处理

讲者接着把问题从“字符串替换/提取”推进到“按列理解文本”，于是 `awk` 登场。视频到这里的主题其实变了：前面关注的是字符模式，这里开始关注字段和条件动作。

这一段的推进逻辑大致是：

- 先决定分隔符
- 再用 `$1`、`$2` 等字段表达你真正关心的列
- 用模式加动作组合出筛选、计数和重排

这也是为什么第四讲不只是正则课，而是真正的数据流水线课。

#### 32:00-40:00 `sort`、`uniq`、`cut`、`xargs` 等小工具如何接力

当文本已经被清洗成更整齐的结构后，视频开始进入统计和批处理阶段。讲者在这一段连续展示了多种小工具，并强调它们各有职责：

- `sort` 负责排序
- `uniq -c` 负责压缩并计数
- `cut` 负责取列
- `xargs` 负责把文本重新变成命令参数

这段最重要的不是每个选项，而是你要开始把这些工具看成流水线里的固定工位。

#### 40:00-48:00 把管道结果送进计算和可视化工具

视频到后半段开始把数据整理的终点向外扩展。讲者让管道结果继续流向 `bc`、`R`、图像工具或 plotting 工具，目的是说明 shell 文本处理并不是分析的终点，而是分析的上游。

这一段真正建立的知识点是：

- 管道前半段负责整理格式
- 后半段可以进入数学、统计或绘图阶段
- 命令行生态是互通的，不应把“文本处理”和“分析”割裂开看

#### 48:00-50:00 二进制流、远端管道和这一讲的方法论总结

视频最后几分钟展示了更有冲击力的例子，例如把音视频、压缩流或远端数据串在一条管道里。讲者借此打破“管道只能处理纯文本”的误解。

最终这一讲的视频顺序落在一个很清晰的方法论上：

- 先观察原始格式
- 再逐步删噪、提取、结构化
- 再统计、聚合、可视化
- 每接一段都检查输出

这才是 data wrangling 这一讲真正想教会你的。

### 逐条知识点展开

#### 1. 这讲的核心不是某个工具，而是“把数据变形”的流程感

课程用日志处理举例，是在告诉你现实里的数据通常不是一上来就适合分析。常见路径是：

- 先把数据取出来
- 再过滤掉大部分无关内容
- 再只保留需要的字段
- 再做去重、计数、排序、汇总
- 最后喂给统计或可视化工具

也就是说，数据整理不是一次变换，而是一条逐步逼近目标格式的流水线。

#### 2. 在远程机器上先过滤，再传回本地，是很重要的工程意识

课程用 `ssh myserver journalctl | ...` 这类例子，不只是为了展示 `ssh`。它想强调：

- 数据靠近哪里，计算就尽量靠近哪里
- 先在远端过滤，能减少网络传输
- shell 管道可以跨主机边界工作

这是一种非常实际的系统直觉。很多日志、数据库、远端命令输出问题，先问“能不能在源头先过滤”通常就会更高效。

#### 3. `grep` 负责过滤，`sed` 负责改写，`awk` 负责按字段计算

这讲最重要的不是记住哪个工具更强，而是理解它们各自最自然的角色：

- `grep`：判断一行是否匹配某模式
- `sed`：对文本做流式替换、删除、编辑
- `awk`：把文本按字段看待，并做条件 + 动作处理

它们不是绝对边界，但这个分工对初学很重要。你会更容易判断“这个问题先试哪种工具更顺手”。

#### 4. 正则表达式是文本整理的共同语言

课程在 `sed` 和 `awk` 里都用了正则，这说明正则不是某个单一命令的语法，而是很多文本工具共享的一套模式语言。

最需要理解的点包括：

- `.`、`*`、`+`、`?` 等基本量词
- `^` 和 `$` 表示行首行尾
- `(...)` 用于分组
- `\1`, `\2` 等分组引用
- 贪婪匹配为什么容易“吃太多”

这也是为什么课程建议不要把正则当咒语，要理解它到底在匹配什么。

#### 5. `sed` 最典型的角色是“把脏文本转成更规整的文本”

课程里的 `sed -E 's/.../.../'` 示例，体现了 `sed` 最常见的使用模式：

- 提取某一行里真正要的那部分
- 删掉噪音前缀后缀
- 把文本改写到下游工具更容易处理的格式

`sed` 本质上是流编辑器，所以它特别适合嵌在管道中间，不一定非要对文件原地修改。

而且课程借练习题也提醒了一个重要坑：不要轻易写 `sed ... input > input`，因为 shell 可能在 `sed` 读取之前就先把文件截断。

#### 6. `sort`、`uniq`、`cut`、`paste`、`wc` 这些“小工具”是统计前的积木

数据整理里很多“看起来高级”的结果，其实就是几个小工具叠出来的：

- `sort`：排序
- `uniq -c`：统计重复项频次
- `cut`：按列切字段
- `paste -sd+`：把多行拼成一行表达式
- `wc -l`：计数

课程有意用这些工具，是在训练你别急着上大程序。很多统计、清洗、聚合，其实文本层面就能先做一大半。

#### 7. `awk` 的真正价值是“文本也可以像表格一样处理”

`awk` 最重要的观念是字段。对于每一行：

- `$0` 是整行
- `$1`, `$2`, ... 是各字段
- 默认用空白分隔，也可以用 `-F` 改分隔符

再加上模式和动作：

- `条件 { 动作 }`
- `BEGIN { ... }`
- `END { ... }`

它立刻就从“文本工具”升级成“轻量表格处理语言”。课程用它统计用户名、计数和筛选，就是在展示这一点。

#### 8. 数据整理的终点不一定是屏幕，也可以是数学和图表

课程后半段把结果送进：

- `bc` 做数学计算
- `R` 做 summary
- `gnuplot` 画图

这个安排非常关键。它说明命令行里的文本处理不是孤立游戏，最终目标往往是：

- 统计
- 建模
- 可视化
- 自动化报告

所以你应把数据整理理解成分析工作流的上游，而不是独立技巧。

#### 9. `xargs` 负责把“文本列表”重新变回“命令参数”

在一长串管道之后，结果通常变成一行行文本。但很多时候你接下来想做的是“对这些结果再运行命令”。这就是 `xargs` 的用武之地。

课程给出的删除 toolchain 例子，本质就是：

- 前半段负责筛选出目标列表
- `xargs` 负责把列表重新喂给卸载命令

你可以把它理解成“从文本世界返回命令世界”的桥。

#### 10. 二进制数据同样可以放进管道

课程特意给了 `ffmpeg | convert | gzip | ssh ...` 这样的例子，是为了打破一个误解：管道不只适合纯文本。

只要程序愿意从标准输入读、往标准输出写：

- 图片
- 音频
- 压缩流
- 网络流

都可以串起来。这其实是 shell 设计非常强的一点。

>[!example] 这讲真正要学会的不是某条命令，而是拆解思路
>
> 如果你要从 SSH 日志里找“连接次数最多的用户名”，正确思路通常是：
> 先 `grep` 过滤出目标行，再 `sed` 提取用户名，再 `sort | uniq -c` 做计数，再 `sort -n` 排序。课程反复演示的，就是这种把任务拆成一串小变换的能力。

#### 11. 数据整理最常见的失败不是工具不会，而是中途不验证

课程示例都很短，但背后有一个隐含原则：每接一段管道，就应该先看输出是否符合预期。

否则常见错误包括：

- 正则多吃或少吃了内容
- 字段分隔理解错了
- 排序顺序不对
- 文本里还带隐藏空格、换行、大小写差异

所以数据整理的实际工作流通常是“加一段，看一眼，再继续”，而不是一口气写出十段管道再祈祷。

### 这讲解决什么问题

### 任务控制

需要掌握的不是命令本身，而是信号模型。

常见信号与操作：

- `Ctrl-C`：通常发 `SIGINT`
- `Ctrl-\`：通常发 `SIGQUIT`

tmux 解决的是“一个终端窗口不够用，而且断线后不想丢工作”的问题。

它的核心对象层次：

- session
- window
- pane

最重要的价值：

- 多任务并行
- 分屏
- 断开后重连
- 远程工作更稳定

### 别名与 dotfiles

别名适合缩短高频命令，例如：


但别名只是表层。更重要的是 dotfiles：

- `.bashrc`
- `.zshrc`
- `.vimrc`
- `.gitconfig`

课程真正鼓励的是：把自己的环境配置文本化、版本化、可迁移。

### SSH

SSH 不只是“远程登录”。

你应该把它看成：

- 远程 shell
- 文件传输能力
- 端口转发能力
- 公钥认证体系

长期习惯包括：

- 用公私钥登录，少用密码

- 理解 known_hosts 与 host key 的意义

- 命令行环境不是“黑框背景”，而是一整套工作流基础设施

### 逐条知识点展开

#### 1. 这一讲把“会敲命令”推进到“能长期在命令行里工作”

前几讲讲的是局部技能，这一讲讲的是环境级能力。你开始需要考虑：

- 一个任务怎么放后台
- 断网后任务会不会丢
- 如何维持长时间远程会话
- 如何让配置跨机器复用
- 如何用 SSH 把多台机器纳入同一套工作流

也就是说，这一讲的主题是“命令行作为工作环境”，而不是单条命令。

#### 2. 进程、信号和任务控制是终端工作的底层机制

课程先讲任务控制，是因为你在终端里迟早会碰到：

- 一个命令太慢
- 一个任务误启动了
- 一个程序卡住了
- 需要暂时挂起、切回来继续

相关核心概念包括：

- 前台进程与后台进程
- `Ctrl+C` 发 `SIGINT`
- `Ctrl+Z` 发挂起信号
- `jobs`、`bg`、`fg` 管理当前 shell 里的任务
- `kill` / `pkill` / `pgrep` 与 pid 打交道

重点不是背信号编号，而是理解终端和进程之间确实通过信号交互。

#### 3. `nohup`、`disown` 和 `tmux` 解决的是不同层次的“断开连接”

很多人以为“后台运行”就等于“我关终端也没事”，其实不是。课程想让你区分几种场景：

- `cmd &`：只是放到后台，仍附着当前 shell
- `nohup cmd &`：忽略挂断信号，终端关闭后仍可继续
- `disown`：让当前 shell 不再管理这个任务
- `tmux`：保持一个独立会话，断线后可以重新连回去

其中 `tmux` 才是长期远程工作的主力工具，因为它解决的不是“单命令不断”，而是“整个工作会话不断”。

#### 4. `tmux` 的对象模型要分清：session、window、pane

课程不是让你背快捷键，而是让你理解 tmux 的层级：

- session：一整个工作会话
- window：一个标签页式终端
- pane：一个窗口内的分屏

理解这个模型后，你才会自然形成这样的工作方式：

- 一个项目一个 session
- 一个 session 内按任务开多个 window
- 在单个 window 里用 pane 并排看服务、日志、编辑器

#### 5. alias、函数和 shell 配置是在塑造“默认行为”

课程把 alias 和 dotfiles 放在一起讲，意思很明确：效率来自你是不是把高频动作写进环境。

例如：

- 给常错拼的 `dc` 做别名
- 给常用命令加安全参数
- 给提示符加分支信息
- 把常用目录跳转、激活环境、项目初始化封成函数

alias 适合短替换，函数适合带逻辑的小工作流。两者共同作用，是让终端从“原生壳”变成“你的工作壳”。

#### 6. dotfiles 的重点不是仓库本身，而是“可迁移、可安装、可重建”

课程要求你把配置文件放进版本控制，并写安装脚本，这背后的目标是：

- 新机器不靠手工一点点点回来
- 配置变更有历史
- 故障后可恢复
- 环境能复制给别的机器或容器

这是一种工程化思维：把“我的使用习惯”从脑内经验，变成能交付的文本资产。

#### 7. SSH 是远程命令行环境的核心协议

课程对 SSH 的定位非常高，因为它几乎把前面所有 shell 技术带到了远程机器：

- `ssh user@host` 登录远端
- `ssh host command` 直接远程执行命令
- 与管道结合，把远端输出接回本地

所以 SSH 不是“远程桌面的简陋替代”，而是“远程 shell 的正式接口”。

#### 8. 基于密钥的认证要从密码学和运维两个角度理解

课程在这一讲讲密钥的实践，在安全那一讲再讲其密码学原理。这里先要掌握运维层面的要点：

- 用 `ssh-keygen -o -a 100 -t ed25519` 生成更现代的密钥
- 私钥必须好好保管，最好再加口令保护
- 公钥放进远端的 `authorized_keys`
- `ssh-agent` 用来缓存解锁后的私钥

关键理解是：私钥几乎就等于你的登录能力，因此“密钥登录更方便”并不意味着“密钥可以随便放”。

#### 9. 复制文件、端口转发、SSH 配置是 SSH 真正常用的三大扩展

课程讲 SSH 并不止于登录。

你还需要知道：

- `scp`：直接复制文件
- `rsync`：增量同步，适合目录和大文件
- `~/.ssh/config`：为主机起别名、配置用户、端口、密钥、转发
- `LocalForward` / `RemoteForward`：把本地和远端端口桥接起来

这些能力让 SSH 从“登录工具”变成“远程工作基础设施”。

#### 10. `mosh`、`sshfs`、shell framework、terminal emulator 是“舒适层”优化

课程最后讲的一些杂项其实非常实用：

- `mosh` 解决高延迟和网络切换时的 SSH 体验问题
- `sshfs` 让远端目录像本地目录一样挂载
- `zsh` / `fish` / shell framework 提升交互体验
- 终端模拟器的字体、主题、快捷键、性能会显著影响日常感受

这些不是最先学的东西，但当你已经大量在命令行里工作时，它们会逐渐成为生产力差异。

>[!example] 命令行环境这一讲最典型的长期工作流
>
> 在本地开一个 `tmux` 会话，通过 `ssh` 连到远端服务器，在一个 pane 里跑服务，在一个 pane 里看日志，在另一个 pane 里做编辑和 Git 操作。网络断开以后，稍后重新登录并 `tmux attach`，整个上下文仍在。

#### 11. 这一讲真正培养的是“别让环境只存在于当前这台机器”

如果只把第五讲记成若干命令，就会错过重点。它最重要的价值是让你开始系统地思考：

- 我的任务如何不中断
- 我的配置如何迁移
- 我的远程机器如何纳入统一工作流
- 我的终端是否已经是一个可维护环境

这也是 Missing Semester 从“工具课”上升到“工程工作流课”的关键一步。

## 第 6 讲 版本控制 (Git)

资料：<https://missing-semester-cn.github.io/2020/version-control/>

### 这讲解决什么问题

课程对 Git 的态度非常明确：不要从命令表学 Git，要从数据模型学 Git。

很多人用 Git 时像在背咒语，是因为只记命令，不理解底层对象和历史图。

### Git 的本质

Git 不是“改动列表工具”，而是“快照图管理工具”。

它把项目在某个时刻的完整状态记录成快照，并用提交图把这些快照串起来。

核心对象可以粗略理解为：

- blob：文件内容
- tree：目录结构
- commit：一次快照与元数据

提交不是“补丁”，而是“带父指针的快照节点”。

### 为什么这个模型重要

一旦你理解提交图是 DAG，很多命令就不再神秘：

- `branch`：本质是某个提交的可移动引用
- `HEAD`：当前所在位置
- `merge`：把两段历史合并
- `rebase`：在另一条基线上重放提交
- `checkout` / `switch`：移动工作位置

### 你至少要能清楚区分的东西

- 工作区
- 暂存区
- 提交历史
- 本地分支
- 远程分支

如果这几层混在一起，Git 就会永远显得诡异。

### 高频命令的正确理解

```bash
git status
git add
git commit
git log --all --graph --decorate
git diff
git checkout
git switch
git branch
git merge
git rebase
git stash
git reset
git reflog
git cherry-pick
git bisect
```

课程真正强调的不是“记住这些名字”，而是知道每个命令在操作哪一层状态。

### merge 与 rebase

- `merge`：保留分叉结构，生成合并提交
- `rebase`：改写提交基底，让历史看起来更线性

没有哪一个永远更高级。你需要理解两者在“历史表达方式”上的差异。

### reflog 的现实价值

Git 最让人安心的一点，是很多“看起来丢了”的东西其实没真丢。

`reflog` 能帮你找回：

- 被 reset 掉的提交
- 被误切换前的位置
- 一时找不到的历史状态

这也是为什么理解引用和提交对象很重要。

### 这讲真正要记住什么

- Git 的核心是快照图，不是命令表
- 分支本质上只是指针
- 很多 Git 操作都是在移动引用、更新暂存区和工作区
- 一旦理解数据模型，冲突、merge、rebase 和找回历史都会清楚很多

### 按视频时间顺序的逐段讲义

#### 00:00-08:00 为什么必须从数据模型而不是命令表学 Git

第六讲一开头就明确立场：如果你把 Git 学成 `add/commit/push` 的背诵题，一定会在稍复杂一点的历史、分支或协作问题上卡住。讲者先用版本控制的目标铺垫，再把 Git 的设计导向“历史图”这个抽象。

这一段视频的重点是：

- 版本控制不是备份工具那么简单
- Git 要支持分支、合并、协作和找回历史
- 这些能力都建立在一个很明确的数据模型之上

#### 08:00-16:00 快照、tree、commit、parent：历史为什么是一张图

讲者接着开始解释 Git 存的不是“修改步骤”，而是项目在不同时间点的快照。随后引出 tree、commit、parent 等概念，把一次提交描述成一个指向目录树和父提交的对象。

这一段最重要的推进是：

- 项目状态可以表示成目录树
- 提交对象记录某一时刻的树和它的父节点
- 因为一个提交可以有多个父节点，所以历史天然是一张图，不必强行线性

#### 16:00-24:00 refs、branch、HEAD：如何用人类可读名字指向历史

理解了对象以后，视频开始讲引用系统。讲者把 branch、tag、HEAD 这些常见名字统一放回“ref”这个概念里，解释为什么它们本质上只是对 commit 的命名方式。

这一段你应该按视频顺序把关系理清：

- branch 是可移动引用
- tag 更像固定标签
- HEAD 表示你当前所在的位置
- checkout 本质上是在改 HEAD 指向什么

这也是 Git 真正开始变得“可以推理”的时刻。

#### 24:00-32:00 Git 历史不可变、对象存储和低层 plumbing 命令

视频中段开始往底层走。讲者展示历史对象的不可变性，并用 `git cat-file` 之类的 plumbing 命令直接查看对象存储里的内容。

这段的重要性在于：

- 你第一次看到 Git 不只是工作区界面，而是真有对象数据库
- 你会明白 commit hash 为什么能稳定标识内容
- 你开始知道“Git 内部到底存了什么”

这一步对后面理解 reset、checkout、rebase 特别关键。

#### 32:00-40:00 暂存区、工作区和提交历史的三层分离

讲者随后把视角从对象库拉回日常使用，开始解释 staging area 的角色。视频里这一段最常见的问题是：为什么 Git 要有一个暂存区，为什么不直接 commit 工作区。

按讲者的推进逻辑，这一段要抓住：

- 工作区是你正在改的文件
- 暂存区是“准备纳入下一次提交”的候选集
- commit 则是正式固化下来的快照

一旦这三层分清，`add`、`commit`、`diff` 这些命令的行为都会清楚很多。

#### 40:00-48:00 checkout、detached HEAD、恢复历史状态

视频到这里开始演示切回旧提交、查看历史快照以及 detached HEAD。讲者通过实际切换，让你看到 Git 不只是记录历史，还能把工作区真的还原到过去某个状态。

这一段最该记住的是：

- checkout 老 commit 会把你放到 detached HEAD
- 这并不神秘，只是 HEAD 暂时不跟某个 branch 名字绑定
- 你仍然可以从这里继续探索或分叉出新分支

#### 48:00-56:00 restore/reset 等“危险命令”的真实本质

讲者在这一段开始拆解那些最让人怕的命令。视频的核心不是教你背语法，而是解释这些命令究竟是在改：

- 工作区
- 暂存区
- 还是引用本身

这也是为什么第六讲特别强调：很多 Git 命令看上去可怕，只是因为你没把它们映射到正确的数据层。

#### 56:00-64:00 branch 和 merge：分叉历史如何重新汇合

接下来视频进入分支和合并。讲者用最小例子演示一条主线分出两个功能分支，再 merge 回来，让你看到合并提交为什么会有两个父节点。

这一段真正要记住的是：

- branch 只是多了一个可移动引用
- merge 是创建一个新提交，把两条历史接起来
- 冲突不是神秘失败，而是 Git 无法自动决定文本该怎样合并

#### 64:00-72:00 远端仓库、bare repo、push 和 clone

视频继续推进到协作层。讲者先在本地造一个 bare repository，再用它解释远端究竟是什么。这样做的用意非常好：你会发现“远端”不是云端黑箱，只是另一个仓库而已。

这一段的视频顺序大致是：

- bare repo 为什么适合作为远端
- clone 的本质是什么
- push 如何更新远端引用
- 为什么协作的本质还是对象和引用同步

#### 72:00-80:00 fetch、pull、远端跟踪分支和历史同步

讲者接下来把“与远端交互”拆成 fetch 和 pull 两步，借此让你理解远端跟踪分支。这里最关键的是不要把 `pull` 想成某种神奇同步按钮。

按视频顺序需要抓住：

- `fetch` 先把远端对象和引用拿回来
- 远端跟踪分支只是你本地对远端状态的记忆
- `pull` 通常等于 `fetch` 再接一个 merge 或 rebase

#### 80:00-85:00 bisect、reflog、在历史里定位问题和找回状态

最后几分钟，讲者把 Git 拉回调试和恢复层面。视频重点展示 `git bisect` 这种真正体现历史图价值的工具，以及 `reflog` 这种救命索引。

第六讲的最终推进顺序因此非常完整：

- 先理解对象和引用
- 再理解三层状态
- 再理解分支、合并、远端
- 最后把 Git 用回调试、恢复和历史定位

这也解释了为什么这一讲虽然长，但每一步都必须按顺序来。

### 逐条知识点展开

#### 1. Git 之所以让人痛苦，通常不是命令难，而是对象模型没进脑子

课程对 Git 的批评非常到位：很多人是在“背命令”，不是在“理解版本控制”。于是会出现：

- 不知道 commit 到底存了什么
- 不知道 branch 和 HEAD 是什么关系
- 不知道 merge/rebase 到底改了哪里
- 一旦出冲突或误操作就慌

这一讲的任务就是把 Git 变成一个可推理的系统，而不是神秘盒子。

#### 2. Git 的底层对象是 blob、tree、commit

课程从数据模型出发讲 Git，核心对象有三类：

- blob：文件内容
- tree：目录结构，把名字映射到 blob 或子 tree
- commit：一次提交，指向一个 tree，并记录父提交、作者、信息等元数据

关键理解是：commit 不是“补丁列表”，而是“整个项目在某一时刻的快照”。这就是为什么 Git 在概念上更像一张由快照组成的有向图，而不是一串线性的差异。

#### 3. 分支只是指向某个 commit 的可移动引用

课程反复强调 branch 本质上就是 ref。这一点一旦明白，很多命令立刻变简单：

- 创建分支：新建一个指针
- 提交：让当前分支指向新 commit
- 切分支：让 `HEAD` 指到另一个分支
- 合并：创建一个同时指向两个父提交的新 commit

因此，分支并不是“复制一份项目”，而是在同一张历史图里给你一个可移动书签。

#### 4. `HEAD` 表示“你当前所在的位置”

`HEAD` 是理解 Git 当前状态的关键：

- 正常情况下它指向某个分支
- detached HEAD 状态下它直接指向某个 commit

很多“我怎么改着改着不在分支上了”的问题，都是因为 `HEAD` 现在没有挂在某个分支名上。

#### 5. 要区分提交历史、暂存区、工作区三个层次

课程虽然重点讲对象模型，但实操里必须把三层状态分清：

- 提交历史（repository）：已经正式保存的快照
- 暂存区（index / staging area）：准备纳入下一次提交的内容
- 工作区（working tree）：你磁盘上当前改出来但未必提交的文件

这样你才能真正理解：

- `git add` 是把工作区改动放进暂存区
- `git commit` 是把暂存区内容固化成新快照
- `git diff`、`git diff --staged` 比较的是不同层次之间的差异

很多“为什么我改了但 commit 里没有”“为什么 status 显示两种变化”都得靠这个模型解释。

#### 6. Git 的很多命令本质上是在移动引用或在三层状态之间复制数据

课程想让你从“操作本质”而不是“命令描述”理解 Git：

- `git add`：把工作区内容复制到暂存区
- `git commit`：从暂存区生成 commit，并移动当前分支
- `git checkout` / `git switch`：切换 `HEAD` 指向并更新工作区
- `git restore`：用历史或暂存区内容覆盖工作区
- `git reset`：重置分支、暂存区，必要时还会改工作区

当你把命令映射到“引用/暂存区/工作区”三层，就不会再觉得这些命令是在随机施法。

#### 7. merge 和 rebase 的差别不是“哪个更高级”，而是“怎么改写历史”

课程的核心是让你理解两者各自做了什么：

- `merge`：保留原有分叉历史，并产生一个新的合并提交
- `rebase`：把一串提交“搬到”另一个基底之上，改写提交历史

所以二者的差别主要是：

- 是否保留原来的分叉形态
- 是否产生新 commit id
- 协作时是否会改写别人已经基于其工作的公共历史

课程更关心你的心智模型，而不是强行给出唯一风格偏好。

#### 8. Git 的图视角非常重要

很多困惑只要把历史画出来就清楚了。因此课程很推荐经常看：

```bash
git log --all --graph --decorate --oneline
```

这条命令的价值在于它把：

- 分支指向
- 合并点
- 当前所在位置
- 提交相对关系

一次性可视化出来。Git 如果只看文件列表很抽象，但一看图就清楚很多。

#### 9. 远端不是“云端魔法”，而是另一个仓库和它的引用

课程讲远端时，背后的模型同样很简单：

- 远端也是一个 Git 仓库
- `fetch` 是把它的引用和对象拿回来
- `push` 是把你的引用更新推过去
- `pull` 往往等于 `fetch + merge/rebase`

因此 GitHub / GitLab 在概念上不是新系统，只是托管了一个远端仓库并额外提供协作界面。

#### 10. 找回历史的能力决定你是不是“真正会用 Git”

课程里很看重 `reflog`，因为它能救回大量误操作：

- reset 之后找不到原位置
- 错切分支
- 意外丢掉某次提交
- 合并/变基做坏了想退回去

`reflog` 记录的是引用移动历史，而不是项目逻辑历史，所以它常常能帮你找到“我刚刚明明还在的那个状态”。

除了 `reflog` 之外，你还应区分：

- `revert`：用新提交撤销旧提交
- `reset`：移动引用并可选覆盖暂存区/工作区
- `restore`：恢复文件内容
- `stash`：暂存一批未完成改动

#### 11. 理解 Git 的真正目标是敢于操作，而不是只敢最基础命令

课程最希望你达到的状态不是“只会 add/commit/push”，而是：

- 我能解释一次 commit 到底是什么
- 我知道 branch 和 HEAD 的关系
- 我知道为什么 merge/rebase 会这样改历史
- 我知道丢东西时先看 `reflog`

这会直接改变你对 Git 的心理感受，从“危险”变成“可推理”。

## 第 7 讲 调试及性能分析

资料：<https://missing-semester-cn.github.io/2020/debugging-profiling/>

### 这讲解决什么问题

这讲处理两个现实问题：

- 程序错了，怎么定位
- 程序慢了，怎么证明它为什么慢

很多人对这两件事的默认做法是“盲改”和“凭感觉优化”，课程要你彻底改掉这种习惯。

### 调试的层次

#### 打印与日志

打印调试依然有效，但日志更适合长期系统。

日志的价值在于：

- 可持久化
- 可分级
- 可过滤
- 很多问题发生时，日志可能已经包含线索

常见日志级别：

- DEBUG
- INFO
- WARN
- ERROR

### 调试器与系统调用追踪

有些问题不是“程序逻辑错了”，而是“程序和系统交互出了问题”。

这时就需要：

- `gdb` / `pdb` 等调试器
- `strace` / `dtruss` 看系统调用
- `lsof` 看打开文件
- `tcpdump` / `Wireshark` 看网络包
- 浏览器 DevTools 看前端和网络请求

### 静态分析

静态分析的价值在于：不运行代码，也能发现大量明显问题。

例如：

- 拼写错误
- 未定义变量
- 覆盖名字
- 风格与潜在 bug

这类工具包括语言自己的 linter、type checker、静态分析器等。

### Profiling：先测再优化

性能分析最重要的原则：

- 不要先猜
- 先测瓶颈
- 优化后再测

你通常会用到：

- wall-clock time
- CPU time
- 内存分配
- I/O 等待

典型工具包括：

- `time`
- `perf`
- 各语言 profiler
- benchmark 工具

### 微基准测试的坑

课程会提醒你：benchmark 很容易测错。

常见干扰项包括：

- 缓存预热
- 编译器优化
- 输入规模太小
- 测试环境不稳定
- 把启动成本和核心逻辑混在一起

### 这讲真正要记住什么

- 调试不是“改一行试一行”，而是系统收集证据
- 打印、日志、调试器、系统调用跟踪各自解决不同层面的问题
- 性能优化必须建立在 profiling 之上
- 没有测量就谈优化，通常是在浪费时间

### 按视频时间顺序的逐段讲义

#### 00:00-08:00 从“程序错了”到“如何系统定位错误”

第七讲开头先把调试和 profiling 并列摆出来，讲者要解决的是两个同样现实的问题：程序为什么错，程序为什么慢。视频一开始并没有急着上工具，而是先强调获取信息的重要性。

这段视频的核心推进是：

- 调试首先要能看到系统发生了什么
- 日志、traceback、系统日志都是证据来源
- 问题没有被稳定观察到之前，不要急着改代码

#### 08:00-16:00 traceback、打印调试、进入调试器看运行状态

讲者接着用具体 bug 演示调试流程。视频会先展示错误信息，再逐步进入交互式调试器，让你看到变量值、当前位置和调用顺序。

这一段最关键的顺序是：

- 先利用已有错误输出定位到大概位置
- 再通过打印或 debugger 检查真实状态
- 区分“程序崩了”和“程序没崩但结果错了”这两类问题

#### 16:00-24:00 单步执行、状态检查和“修掉一个 bug 后还有下一个 bug”

这一段的视频非常有价值，因为讲者不是修完第一个异常就结束，而是继续往下走，发现程序虽不报错但结果仍然不对。这恰好说明真实调试往往是多层的。

按视频推进，这段最该抓住的是：

- debugger 不只是找 crash 点，也能验证逻辑是否按预期推进
- 单步执行和查看变量，能帮助你找出“静悄悄的错误”
- 一个错误消失，不代表程序正确

#### 24:00-32:00 lint、静态分析、类型检查和编辑器集成

视频中段把调试往前移，讲者开始讨论为什么很多错误应该在运行前就被拦住。这里登场的是 linter、静态分析器和类型检查工具。

这一段的真正主线是：

- 不是所有 bug 都该等到运行期才发现
- 工具可以提前提示不一致、未定义、类型问题和可疑模式
- 如果这些工具能和编辑器集成，反馈会更及时

第七讲在这里开始把“调试”扩成“整套错误发现机制”。

#### 32:00-40:00 profiling：为什么慢，先区分 tracing 和 sampling

视频后半段切入性能分析。讲者先不急着跑 profiler，而是先告诉你 tracing profiler 和 sampling profiler 分别是怎样工作的，以及它们为什么会给出不同类型的答案。

这一段需要掌握的推进关系是：

- tracing 更细，但可能更重
- sampling 更轻，但看到的是概率性的热点
- profiler 的结果要结合程序结构理解，而不是机械照抄

#### 40:00-48:00 line profiler、memory profiler、benchmarking 和 `hyperfine`

随后视频把粒度继续往下压。讲者展示了行级 profiler 和内存 profiler，又顺手引入 benchmark 的基本纪律。

这一段最重要的知识点包括：

- 先粗看函数级热点，再细看行级热点
- 内存问题也需要专门工具，而不是只盯 CPU 时间
- benchmark 需要多次运行和条件控制
- `hyperfine` 之类工具的价值在于自动做统计和预热

#### 48:00-56:00 系统监控工具：CPU、I/O、磁盘、网络各看什么

最后几分钟的视频转向操作系统层面的观察工具。讲者按资源维度罗列了 `htop`、`iotop`、`ncdu`、`ss`、`lsof` 等工具，其实是在教你建立“性能问题属于哪一层”的分类意识。

第七讲按视频顺序收束到一个统一方法：

- 先收集证据
- 再确认问题类型
- 再选合适粒度的工具
- 优化和修复都必须建立在可观察事实之上

### 逐条知识点展开

#### 1. 调试的核心不是工具，而是证据链

课程对调试的基本态度非常明确：不要一边猜一边改，而要先建立问题的证据链。

一个像样的调试流程通常包括：

- 稳定复现问题
- 缩小问题出现的条件
- 确认输入、输出、中间状态
- 判断问题是在应用逻辑、运行时、系统调用还是环境层

所以调试首先是一种思维方式，然后才是工具选择。

#### 2. 最基础的调试手段仍然是打印和日志

课程没有轻视打印调试。原因很现实：打印和日志是最便宜、最普适、最容易保留上下文的证据方式。

你需要区分：

- 临时调试输出：快速验证某个猜想
- 正式日志：长期保留系统状态变化，便于事后分析

日志里最关键的不是“多打”，而是打对信息：

- 时间
- 请求或任务 id
- 关键参数
- 分支路径
- 错误上下文

#### 3. 调试器解决的是“停住程序看内部状态”

当打印已经不够时，调试器的价值就出来了。课程强调的典型能力有：

- 下断点
- 单步执行
- 查看变量
- 查看调用栈
- 条件断点

调试器不是每次都必须上，但一旦你需要回答“程序为什么在这里变成这个值”，它往往比再加十行打印更直接。

#### 4. 版本控制也是调试工具

课程把 Git 放到调试语境里，不是顺手提一句。它真正的作用包括：

- 比较问题出现前后的差异
- 用 `git bisect` 缩小引入 bug 的提交范围
- 快速切回历史版本验证猜想

这说明调试并不只发生在运行时，也发生在“代码历史”这个维度上。

#### 5. 静态分析、Lint、类型检查是在“运行前抓错”

调试并不一定要等代码跑崩。课程提到的静态工具，目标就是尽早在编译期或分析期发现问题，例如：

- 未定义变量
- 死代码
- 风格异常
- 可疑类型转换
- 常见 API 误用

因此静态分析的价值在于：减少那些根本不值得跑到运行时才发现的问题。

#### 6. 系统层调试要学会看进程到底在和谁说话

课程里把 `strace`、`ltrace` 这类工具纳入调试清单，说明一个很重要的事实：很多 bug 不是语言层逻辑错，而是程序和系统边界处出了问题。

比如：

- 文件路径不对
- 权限不足
- 网络连接失败
- 动态库加载异常
- 程序阻塞在某个系统调用

这类问题靠应用内打印往往不够，必须看程序和操作系统实际发生了什么交互。

#### 7. 性能分析之前先分清“慢在哪里”

课程不接受“感觉它慢”这种说法，而要求你先分辨：

- 是 CPU 慢
- 还是 I/O 慢
- 是网络慢
- 还是锁竞争、上下文切换、缓存失效之类问题

也就是说，性能问题首先是分类问题。只有分类清楚，后面的 profiler 和系统监控才知道往哪打。

#### 8. `time`、profiler、line profiler 解决的是不同粒度的问题

课程提到的性能工具不是替代关系，而是逐层深入：

- `time`：整体花了多久，粗粒度
- 函数级 profiler：时间花在了哪些函数
- 行级 profiler：时间花在了哪一行
- 内存 profiler：对象和代码行如何占内存

如果你上来就想用最重的工具，往往是在浪费时间。正确方式是先粗测，再逐渐细化。

#### 9. benchmark 必须考虑预热、缓存和环境噪声

课程非常强调基准测试的陷阱。哪怕是简单地比较两个命令，如果不控制条件，也很容易得出错结论。

常见误差来源包括：

- 首次运行的缓存预热成本
- 文件系统缓存
- CPU 频率波动
- 输入样本太小
- 把初始化和核心逻辑混在一起算

因此像 `hyperfine` 这种工具有价值，是因为它默认帮你处理了多次运行、预热和统计摘要。

>[!example] 这讲想培养的不是“会 profile”，而是测量习惯
>
> 如果你觉得 `find` 太慢，不要马上得出结论。先用 `hyperfine --warmup 3 'fd -e jpg' 'find . -iname \"*.jpg\"'` 去测。课程真正强调的是：在证据出来之前，不要把主观感受当结论。

#### 10. 系统监控工具让你看到整个机器在发生什么

课程后半段罗列了很多命令，但背后的逻辑其实是按资源维度分类：

- CPU / 进程：`top`、`htop`
- I/O：`iotop`
- 磁盘：`df`、`du`、`ncdu`
- 内存：`free`
- 打开文件：`lsof`
- 网络和端口：`ss`
- 网络带宽：`nethogs`、`iftop`

你不需要每天都用全套，但应该知道：当你怀疑问题在某个资源层时，有对应的系统观察窗口可以打开。

#### 11. 调试和性能分析本质上是“从现象回推原因”

整讲串起来看，其实是一条统一主线：

- 调试：从错误现象回推 bug 原因
- profiling：从慢的现象回推瓶颈原因

两者共同反对的都是“凭感觉改”。Missing Semester 在这讲里真正教的是一种工程纪律。

## 第 8 讲 元编程

资料：<https://missing-semester-cn.github.io/2020/metaprogramming/>

### 这讲解决什么问题

这里的 “元编程” 不是指语言层面的宏系统，而是指“围绕程序开发流程的编程”。

课程关注的是：

- 构建系统
- 依赖管理
- 测试
- 持续集成

它们看起来不像“写功能”，但在真实工程里经常比功能本身更决定效率。

### 构建系统

构建系统本质上是在声明三件事：

- 目标
- 依赖
- 规则

典型例子是 `make`。

它的关键价值不是“帮你执行命令”，而是：

- 知道依赖关系
- 知道哪些目标已经过期
- 只重建必要部分

这就是增量构建思想。

>[!example] 典型理解
>
> 如果 `paper.pdf` 依赖 `paper.tex` 和 `plot-data.png`，而 `plot-data.png` 又依赖脚本和数据文件，那么当你只改了 `paper.tex` 时，`make` 不应该重新生成图像。
>
> 构建系统的价值就在于“自动判断哪些步骤真的需要重跑”。

### 依赖管理

一个项目可能依赖：

- 解释器或编译器
- 系统包
- 语言生态里的库
- 外部服务和工具链

课程强调几个现实原则：

- 依赖必须有版本
- 版本升级必须理解兼容性
- 不同层级的包管理器要分清角色

### 语义化版本

课程明确提到 `semver` 的思路：

- patch：修 bug，不改 API
- minor：新增兼容功能
- major：破坏兼容

这套约定的价值，是让依赖关系能更有预测性地管理。

### 测试

测试不是“交作业前再跑一下”，而是给重构和协作提供安全边界。

你至少要理解几类测试：

- 单元测试
- 集成测试
- 回归测试
- 性能测试

好测试的目标不是追求数量，而是：

- 关键路径有保护
- 失败能快速定位
- 执行成本可接受

### 持续集成

CI 的核心不是“上云跑命令”，而是把“质量检查”从个人习惯变成系统流程。

典型 CI 会自动做：

- 安装依赖
- 构建
- 测试
- Lint
- 部署前检查

### 这讲真正要记住什么

- 工程不是只有代码，流程同样需要被设计
- 构建系统的核心是依赖图和增量重建
- 依赖管理最关键的是版本与兼容性
- 测试和 CI 的价值在于把“别出问题”变成机制，而不是靠记性

### 按视频时间顺序的逐段讲义

#### 00:00-08:00 为什么把这一讲叫做 metaprogramming

第八讲一开始就承认这个名字有点别扭。讲者真正想讲的不是语言宏，而是“围绕程序开发过程本身的自动化”。因此视频开头先把范围收紧到 build、dependency、test、CI 这些工程流程问题。

这段的核心是一个视角转变：

- 程序本身需要写代码
- 程序之外的流程也需要被设计和自动化

#### 08:00-16:00 `make`、目标、依赖和“为什么它知道该重建什么”

视频很快用 `make` 作为主例子切入构建系统。讲者先造出一个缺依赖的例子，再让 `make` 报错，从而逼着你理解构建系统不是“帮你跑一串命令”，而是在维护一个依赖图。

这一段的推进逻辑是：

- target 是你想得到的东西
- dependency 是它依赖的前提
- rule 描述如何从依赖得到目标
- 一旦依赖缺失或更新，构建系统就知道哪些步骤要重新执行

#### 16:00-24:00 版本号、兼容性、semver 和依赖约束

讲者随后把注意力从构建过程转向依赖版本。视频里这一段的核心不是某个语言生态的具体命令，而是“软件版本变化意味着什么”。

这里按视频顺序应记住：

- 版本号不只是标签，还承载兼容性承诺
- 语义版本号给了你一个粗略理解升级风险的框架
- 项目不能对依赖版本毫无约束，否则复现和协作都会出问题

#### 24:00-32:00 锁文件、依赖来源、可复现环境

中段视频进一步把问题推进到可复现性。讲者讨论为什么锁文件很重要，为什么不同来源的依赖会影响可靠性，以及版本解析一旦交给“当前最新”就容易导致环境漂移。

这一段的真正主线是：

- 依赖不只是“能装上”
- 还要确保别人、CI、未来的你也能装出相同结果
- 锁文件和更严格的依赖管理是在对抗环境漂移

#### 32:00-40:00 测试、CI、badge 和“代码一变就自动验证”

视频后半段把构建和依赖再往前推一步：如果这些流程很重要，就不该靠人手动记住。于是讲者引出 CI。

这一段最关键的推进是：

- 代码仓库可以绑定自动构建和测试
- 每次变更都能在干净环境下重跑流程
- README 上的 badge 本质上是在公开展示当前自动验证状态

这一步让“工程流程”开始真正变成系统的一部分。

#### 40:00-50:00 这一讲真正希望你带走的工程视角

视频最后并不是继续堆工具，而是把前面的 build、dependency、test、CI 收束成一个整体视角：写项目不是只写源代码，还要把源代码周围的流程都文本化、自动化、版本化。

第八讲按视频推进的最终结论因此很清晰：

- 构建规则应该显式
- 依赖版本应该受控
- 验证流程应该自动
- 项目工作流最好不依赖某个人的记忆

### 逐条知识点展开

#### 1. 这里的“元编程”指的是围绕代码工作的自动化流程

课程一开始就说明，这里不是语言宏系统意义上的 metaprogramming，而是更广义的“程序开发流程自动化”。

也就是说，这一讲的重点不是写业务逻辑，而是：

- 如何构建
- 如何管理依赖
- 如何验证
- 如何在代码变更时自动执行这些动作

这正是学生阶段经常被忽略、但进了真实项目就绕不开的部分。

#### 2. 构建系统的本质是“目标、依赖、规则”

课程用 `make` 讲得很清楚。无论具体工具叫什么，构建系统一般都需要你描述三件事：

- 目标：我要生成什么
- 依赖：生成它需要什么
- 规则：如果依赖变了，该如何生成目标

一旦写成依赖图，系统就可以自动判断：

- 哪些东西已经是最新的，不用重建
- 哪些东西因为依赖变了必须重建
- 构建顺序应该怎样安排

#### 3. `make` 的价值在于“把构建过程显式化”

课程选择 `make`，是因为它简单且广泛。通过 `Makefile`，原本散落在人脑中的流程被写成了文本：

- 第一条规则通常是默认目标
- 模式规则 `%` 可以批量描述一类生成关系
- `$@`, `$<`, `$*` 这类自动变量帮助你写通用规则

最重要的是，当你再运行一次 `make`，它不会盲目重来，而是基于时间戳和依赖关系做增量构建。

#### 4. 构建系统解决的不是“少打一条命令”，而是“流程不会失控”

如果项目稍微复杂一点，手工执行往往会出问题：

- 漏掉中间步骤
- 执行顺序错
- 重复做无意义工作
- 别人接手时不知道怎么构建

构建系统的真正收益，是把“构建过程”从经验技巧升级为可执行规范。

#### 5. 依赖管理的关键不是“怎么安装”，而是“版本如何约束”

课程在依赖管理部分没有陷入各个生态的命令细节，而是抓住几个共通概念：

- 依赖可能来自系统包管理器，也可能来自语言生态
- 每个依赖都有版本
- 版本变化可能带来兼容或不兼容的接口变化
- 项目必须明确自己接受的版本范围

这使你开始以“可复现构建”的角度看依赖，而不是“能装上就行”。

#### 6. 语义版本号是理解兼容性的常见约定

课程引入 semver，是为了给“升级到底安不安全”一个粗略但有用的判断框架：

- 主版本号：不兼容修改
- 次版本号：向后兼容的新功能
- 补丁号：向后兼容的修复

虽然现实项目不一定严格遵守，但这套约定至少让你在面对依赖升级时有一个解释兼容性的基本语法。

#### 7. 锁文件和 vendoring 解决的是“我明天还能不能复现今天的环境”

课程提到锁文件时，核心关切是可复现性：

- 锁文件把当前依赖解析结果固定下来
- 重新安装时不会因为上游新版本发布而突然变化
- 有助于团队成员、CI、生产环境保持一致

而 vendoring 则是更极端的方式，直接把依赖代码纳入项目。这样控制力更强，但同步上游更新的成本也更高。

#### 8. 测试的价值在于把“我觉得没问题”替换成“系统证明没问题”

虽然课程没有展开完整测试理论，但它明确把测试视为工程流程的一部分，而不是“写完再看看”。

你至少应形成这样的意识：

- 每次改代码都值得有一套自动检查
- 人脑记不住所有回归风险
- 测试不是替代思考，而是给思考提供护栏

这也是为什么 CI 最常见的第一件事就是跑测试。

#### 9. CI 的核心不是平台品牌，而是“代码一变，自动发生什么”

课程用 GitHub Actions、Travis CI 等举例，但重点不在选型，而在抽象：

- 仓库发生某个事件
- 平台启动干净环境
- 按你的配置执行构建、测试、lint、部署等流程
- 把结果反馈给开发者

这让“别忘了跑测试”“别忘了构建文档”这种口头提醒，变成了系统化机制。

>[!example] 元编程这一讲最关键的提升
>
> 以前你可能是“先手工跑脚本，再手工编译，再手工测试，再手工发布”。课程希望你把这些动作写进 `Makefile`、依赖清单和 CI 配置里。这样项目的工作流就不再绑定某个人的记忆。

#### 10. 这一讲真正培养的是“把流程也当成代码”

整讲串起来，Missing Semester 想让你建立一个很重要的工程观：

- 构建步骤要文本化
- 依赖关系要显式化
- 版本约束要固定化
- 测试和检查要自动化

换句话说，程序之外的流程同样值得被设计、被版本控制、被自动执行。

## 第 9 讲 安全和密码学

资料：<https://missing-semester-cn.github.io/2020/security/>

### 这讲解决什么问题

这讲不是教你设计密码算法，而是教你理解常见安全工具背后的基本模型，避免在日常开发和使用中“会用但不懂”。

### 熵

熵衡量的是不确定性，也就是猜测难度。

课程借密码强调一个现实原则：

- 安全性不是“字符看起来复杂”
- 而是“攻击者可行搜索空间到底有多大”

40 比特熵大致能抵抗很多在线暴力猜测；
面对离线暴力破解，通常需要更高熵。

### 密码散列函数

散列函数把任意输入映射到固定长度输出。

安全散列至少要求：

- 确定性
- 难以反推原文
- 难以构造碰撞

课程用 Git 里的 SHA-1 说明散列的工程用途：

- 内容寻址
- 文件完整性校验
- 承诺机制

### KDF

密钥生成函数的作用是：

- 从密码导出密钥
- 抵抗暴力枚举

关键实践包括：

- 不存明文密码
- 加盐
- 使用慢一点的 KDF

### 对称加密与非对称加密

#### 对称加密

同一把密钥负责加密和解密。

适合：

- 文件加密
- 磁盘加密
- 会话内数据加密

#### 非对称加密

公钥与私钥分工不同。

适合：

- 安全分发加密能力
- 签名与验签
- SSH / PGP / 软件签名

课程这里最重要的不是数学细节，而是使用模型：

- 加密解决保密性
- 签名解决真实性与不可抵赖

### 现实安全习惯

课程最后强调的安全建议非常务实：

- 用密码管理器
- 对每个站点使用独立强密码
- 开启 2FA
- 用全盘加密
- 理解 SSH / Git 签名等工具背后的信任模型

### 这讲真正要记住什么

- 安全首先是模型问题，不是“玄学设置”
- 熵、散列、KDF、对称/非对称加密要分清各自职责
- 不要自己发明密码算法
- 对普通开发者而言，最有价值的是采用正确工具和正确实践

### 按视频时间顺序的逐段讲义

#### 00:00-08:00 安全这一讲究竟讲什么，不讲什么

第九讲开头先界定范围：这不是完整密码学课，也不是漏洞攻防课。讲者真正想做的是，把几个最常见的安全构件讲清楚，让你能正确理解日常会碰到的工具和实践。

视频开场的重点是：

- 安全问题首先取决于威胁模型
- 很多开发者会使用安全工具，但并不理解它们在解决什么问题
- 这讲要补的正是这层基本模型

#### 08:00-16:00 熵、密码空间、hash 的基本性质

视频随后从 entropy 和 hash 切入。讲者先解释为什么密码强度不能只靠“看上去复杂”，然后把散列函数定义为“把任意长度输入映射成固定长度输出”的工具。

这一段按视频顺序主要在建立：

- 熵衡量的是搜索空间大小
- hash 不是加密
- 好的 hash 需要确定性、抗碰撞、不可逆等性质
- Git 里的内容寻址和文件校验都与 hash 紧密相关

#### 16:00-24:00 用少量可信信息验证大量不可信数据

视频接着讨论校验和与完整性验证场景。讲者会用“从不完全可信来源下载文件，但从可信来源拿到一个小摘要”来解释 hash 的实际用途。

这一段最关键的是：

- hash 让你能验证数据是否被篡改
- 可信来源不一定需要提供整份文件，只需提供可靠摘要
- 安全工具的价值经常来自这种“信任锚点很小，但能验证很大对象”的结构

#### 24:00-32:00 对称加密、API 视角和“如何正确使用而不是如何实现”

视频中段开始进入 symmetric cryptography。讲者明确说，课程不关心算法实现细节，而关心 API 和使用模型。

这里的推进逻辑是：

- 对称加密用同一把密钥加解密
- 你要理解什么时候适合用它保护文件或消息
- 你不应该自己发明模式或协议
- 重点是正确调用成熟工具

#### 32:00-40:00 KDF、passphrase、文件加密和密码管理实践

这段视频把“人类记得住的密码”和“机器需要的密钥”连接起来。讲者通过工具演示说明：口令通常不会直接拿来加密，而会先经过 KDF。

这一段最值得记的是：

- KDF 会把低速、有人类输入特征的口令变成更适合当密钥的结果
- KDF 故意做得更慢，以提高暴力破解成本
- 这和密码管理器、受口令保护的私钥、加密文件都有关

#### 40:00-48:00 非对称加密、签名和“谁能看”“谁发的”是两回事

视频后半段进入 public key cryptography。讲者会把公钥/私钥体系和对称加密做出清晰区分，并解释签名和加密虽然常一起出现，但目的完全不同。

这一段的推进顺序是：

- 公钥/私钥体系允许你公开一部分信息而不破坏安全
- 加密解决保密问题
- 签名解决身份与完整性问题
- 很多工程工具都在组合使用这两类机制

#### 48:00-56:00 证书、信任模型、Git 签名和 SSH 背后的身份问题

讲者接着把数学构件拉回现实世界：即使你有公钥体系，也还要回答“我怎么知道这真是你的公钥”。于是视频进入信任模型、证书、Git commit signing、SSH host key 等问题。

这一段的真实主线是：

- 安全不仅是算法，还包括身份绑定
- 证书体系、信任网络、TOFU 都是在解决公钥分发与信任确认
- Git 和 SSH 都把这些问题带到了开发者日常工作流里

#### 56:00-61:00 混合加密、最终实践建议和这讲的落脚点

最后几分钟的视频会收束到 hybrid encryption 和现实实践。讲者把安全课最终落点放在非常务实的建议上：密码管理器、2FA、全盘加密、不要自造密码学轮子。

第九讲按视频推进的结论因此可以压缩成一句话：先把构件职责分清，再把成熟实践落地，而不是在“会用一点命令”和“看过几个概念”之间停住。

### 逐条知识点展开

#### 1. 这一讲的目标不是让你设计密码协议，而是看懂工具背后的模型

课程一开始就明确划线：不要把这讲当作系统安全课或密码学课替代品。它真正想做的是：

- 解释几个最常见的密码学构件
- 说明这些构件如何出现在 Git、SSH、密码管理器、2FA 等实际工具里
- 帮你建立基本判断力，避免“会点命令却误用安全工具”

#### 2. 熵描述的是密码空间有多大，而不是“看起来像不像乱码”

课程用 XKCD 漫画引入熵，是为了纠正一个直觉错误：复杂字符长得花，不一定就比多个随机单词拼接更强。

熵真正衡量的是：

- 攻击者在已知生成模型的前提下，需要试多少种可能
- 单位通常是比特
- 粗略可用 `log_2(可能性总数)` 估算

这让你开始从“搜索空间”而不是“肉眼复杂度”理解密码强度。

#### 3. 威胁模型决定需要多少熵

课程特别强调 threat model，因为同样的密码，在不同攻击场景下要求不同：

- 在线攻击受限于登录速率和锁定机制
- 离线攻击受限于攻击者算力

因此 40 比特、80 比特这类数字不是脱离场景的神圣阈值，而是和攻击方式绑定的近似判断。

#### 4. 散列函数不是加密，它解决的是摘要、完整性和承诺

课程把 hash 单独拎出来，是因为很多人会把它和加密混淆。散列函数的重要性质包括：

- 确定性
- 不可逆
- 抗碰撞
- 输出长度固定

它常见的用途包括：

- Git 的内容寻址
- 下载文件校验
- 承诺机制

因此 hash 的核心角色不是“保密”，而是“为数据生成稳定指纹并抗伪造”。

#### 5. Git 为什么关心密码散列而不是普通散列

课程拿 Git 举例非常好。Git 用哈希不是为了查找表速度，而是为了内容寻址和完整性保证：

- 对象内容一变，哈希就变
- commit、tree、blob 通过哈希串起来
- 历史结构因此具备很强的完整性特征

这也帮助你把 Git 那一讲和安全这一讲真正连起来。

#### 6. KDF 的核心思想是“把人类密码变成更适合计算机使用的密钥”

课程把 KDF 单独讲出来，是为了说明密码管理和登录验证不能直接用明文密码或普通 hash 糊过去。

KDF 的作用包括：

- 从口令导出固定长度密钥
- 故意做得更慢，抬高暴力破解成本
- 与盐一起使用，避免相同密码产生相同存储结果

这也是为什么存密码时正确做法是：

- 每个用户生成随机盐
- 存 `salt` 和 `KDF(password + salt)` 的结果
- 验证时重新计算再比较

#### 7. 对称加密解决的是“共享一个密钥来保密”

课程在对称加密部分强调两个核心点：

- 加密和解密使用同一把密钥
- 安全性取决于密钥保密，而不是算法保密

它最常见的日常应用包括：

- 加密磁盘或文件
- 与 KDF 结合，用口令保护文件

像 AES 这类算法已经足够复杂和成熟，普通开发者的任务是正确使用现有方案，而不是自造算法。

#### 8. 非对称加密让“公开一把钥匙而不破坏安全”成为可能

课程把公钥/私钥体系讲成“挂锁”类比，非常有帮助。非对称体系通常支持两类操作：

- 用公钥加密、私钥解密
- 用私钥签名、公钥验证

因此它同时支撑：

- 保密通信
- 身份证明
- 软件签名

它的真正威力在于把“密钥分发问题”从共享秘密，变成共享可公开验证的信息。

#### 9. 签名和验证解决的是“这个东西真的是你发的吗”

课程用 Git commit/tag 签名、PGP、SSH 解释签名体系。这里最重要的是区分：

- 加密：防止别人看到内容
- 签名：让别人验证来源和完整性

很多工具同时涉及二者，但它们的目的并不相同。

#### 10. 公钥分发和信任模型是非对称密码真正困难的部分

课程没有停留在“有公钥就行”，而是追问：你怎么知道这个公钥真的是那个人的？

不同系统给出不同答案：

- TOFU（首次使用时信任）
- 信任网络
- 社交证明
- 线下验证
- 证书体系

这说明安全问题不只是数学，还包括现实中的身份绑定和信任建立。

#### 11. 密码管理器、2FA、全盘加密是最应该立即落地的实践

课程最后的案例部分很务实，因为对普通用户和开发者，收益最大的往往不是理解更多理论，而是立即使用正确工具：

- 密码管理器：为每个网站生成独立高熵密码
- 2FA：降低密码泄露后的风险
- 全盘加密：防止设备丢失带来的数据暴露

这些实践之所以重要，是因为它们把前面讲的熵、KDF、对称加密、身份验证，转成了真实可用的安全护栏。

>[!example] 这讲最应该贯通的一个案例
>
> SSH 密钥登录同时用到了多层概念：系统熵生成密钥、私钥用口令和 KDF 保护、公钥分发到服务器、登录时通过挑战应答和签名证明你持有私钥。也就是说，它不是单一命令，而是一整套密码学构件在工程里的落地。

#### 12. 这讲真正要建立的是“不要想当然”

整讲反复传递的态度可以概括为：

- 不要自己发明加密方案
- 不要把 hash、加密、签名混为一谈
- 不要忽视威胁模型
- 不要只会命令，不懂信任前提

这才是 Missing Semester 对安全最务实的贡献。

### 逐条知识点展开

#### 1. 大杂烩这讲的意义是“把工具地图补齐”

课程把很多零散主题放在一起，不是因为它们不重要，而是因为它们各自都很值，但不足以单独撑一门主线课。

这一讲最值得带走的不是记住所有工具名，而是知道：

- 有哪些长期高收益但常被忽略的能力
- 它们分别解决什么现实问题
- 等你遇到对应问题时，知道去哪里继续学

#### 2. 键位映射是最典型的“高频小优化”

课程把键位映射放在最前面，是因为键盘是程序员最常用的输入设备。像 Caps Lock 改成 Ctrl / Escape 这种改动之所以重要，不是因为酷，而是因为：

- 它每天会被按成百上千次
- 高频动作的位置优化收益巨大
- 一旦形成肌肉记忆，长期收益非常稳定

这也体现出整门课的一个风格：优先优化高频摩擦点。

#### 3. 守护进程和 `systemd` 让后台服务可控

课程用 daemon 和 `systemd` 说明：并不是所有程序都要由你手动启动并盯着运行。

你需要理解的核心有：

- daemon 是长期后台运行、通常不与用户直接交互的进程
- `systemd` 负责管理它们的启动、停止、重启、依赖和开机自启
- `systemctl status/start/stop/restart/enable` 是与其交互的主要入口

这对部署服务、维护开发环境、排查系统问题都非常重要。

#### 4. FUSE 的价值在于“把别处的东西伪装成本地文件系统”

课程讲 FUSE，是为了让你意识到文件系统接口本身也可以被复用和扩展。

通过 FUSE，用户态程序可以把：

- 远程目录
- 云存储
- 加密存储
- 备份归档

挂载成“像本地目录一样”的东西。`sshfs` 就是一个很典型的例子。

这让你明白：很多看似“系统级”的能力，其实也能通过接口抽象重新组合出来。

#### 5. 备份最容易犯的错误，是把“复制”或“同步”误当备份

课程在备份这一节非常务实，核心结论包括：

- 同一块磁盘上的拷贝不是备份
- RAID 不是备份
- 单纯同步到云端也不等于备份
- 备份必须考虑异地、版本、恢复能力和安全性

尤其是“同步不是备份”这一点，很多人直到误删文件才真正理解。

#### 6. API 让命令行自动化从本地扩展到互联网服务

课程讲 API 的重点不是 Web 开发，而是让你明白互联网服务也能像本地命令一样被脚本调用。

核心观念包括：

- API 通常通过结构化 URL 和参数暴露能力
- `curl` 是最基础的请求工具
- 返回常是 JSON，可用 `jq` 选取字段
- 有些 API 需要 token 或 OAuth 认证

这意味着“自动化”不只发生在你的电脑里，也可以跨服务发生。

#### 7. 命令行参数的通用模式值得长期记住

课程在这一部分整理了大量工具共有的行为习惯，这很有价值，因为它提升的是迁移能力：

- `--help` 看用法
- `--version` 查版本
- `-v` / `--verbose` 增加输出
- `--quiet` 减少输出
- `-` 代表标准输入/输出
- `--` 表示后面的内容不再按选项解析
- dry run 和 interactive 模式适合危险操作

理解这些惯例以后，你面对陌生命令行工具时会快很多。

#### 8. 窗口管理器和桌面自动化是在 GUI 世界里继续贯彻“减少鼠标”

课程前面一直在讲键盘和命令行，这里则把这个哲学延伸到图形桌面：

- 平铺窗口管理器让窗口组织更像 tmux
- Hammerspoon / AutoHotkey / Karabiner 等工具让桌面行为也可编程

这说明整门课真正推崇的不是“命令行原教旨主义”，而是“让高频工作流尽量可编排、可快捷、可自动化”。

#### 9. VPN、Markdown、Live USB、容器和虚拟机这些主题都在补“现实工作能力”

这些内容看似分散，其实都对应非常常见的现实场景：

- VPN：理解网络信任边界，而不是迷信产品宣传
- Markdown：用简单文本写结构化文档
- Live USB：安装、修复、恢复系统
- Docker / VM / Cloud / Vagrant：隔离、复现和快速获取环境

它们共同说明：程序员的工作不仅是写代码，还要能处理环境、文档、部署和恢复。

#### 10. GitHub 和交互式记事本说明“开发协作和探索式计算”也有工具层方法

课程把 GitHub 放进大杂烩，是在提醒你：

- Issues、PR、代码 review、CI badge 这些都属于现代开发工作流
- Jupyter 这类交互式笔记本适合探索、演示和计算记录，但也有版本控制和复现上的特殊问题

这部分内容没有展开成主线课，但它们都是真实项目里经常出现的工具层问题。

#### 11. 大杂烩真正教的是“长期关注边角工具”

这一讲最容易被当成“零散彩蛋”，但其实它很符合 Missing Semester 的整体精神：

- 真正的生产力常来自很多小摩擦点的持续优化
- 你不需要今天全学完，但要知道这些问题有更好的解法
- 当工作流卡住时，往往不是核心语言或框架不行，而是周边工具层欠缺

这也是为什么大杂烩虽然不成体系，却非常值得反复回看。

## 第 11 讲 提问&回答

资料：<https://missing-semester-cn.github.io/2020/qa/>

### 这讲解决什么问题

Q&A 的价值不在于提供唯一答案，而在于把很多学习和工具选择问题拉回现实上下文。

### 课程里反复出现的判断逻辑

#### 先问是否真的需要某个层级的复杂度

比如更底层的操作系统知识、复杂性能工具、特殊编辑器配置，都不是默认人人都该立刻深入的主题。课程非常强调“按问题驱动学习”。

#### 不要把工具选择绝对化

例如：

- Python vs Bash：看任务复杂度、可维护性、与系统交互程度
- `apt` vs `pip`：看系统级安装还是语言生态、看隔离需求
- Docker vs VM：看隔离粒度和目标场景
- Vim vs Emacs vs VS Code：看你是否愿意投入相应学习成本

#### 优先建立稳定工作流，而不是追逐所有新工具

这门课的整体态度一直是：

- 先把最常用的工具真正用熟
- 再按痛点扩展
- 不要陷入“收藏工具却没有工作流升级”的假进步

### 课程给出的高价值现实建议

- 软件包尽量分清系统级和语言级
- 对语言级依赖优先使用隔离环境
- 不要混用多个包管理方案造成环境污染
- 浏览器、插件、编辑器和终端的选择都应服务于你的真实工作流
- 2FA、密码管理器、全盘加密这类安全实践值得尽早变成默认配置

### 这讲真正要记住什么

- 好问题通常比“标准答案”更重要
- 工具选择没有绝对最优，只有场景匹配
- 长期高效来自稳定、可维护、可迁移的个人工作流

### 逐条知识点展开

#### 1. Q&A 这一讲在做的事，是把整门课的方法论落回现实选择

前十讲主要在讲工具和概念，Q&A 则回答很多“那我实际该怎么选”的问题。它的重要性在于：

- 打破“课程内容 = 唯一标准答案”的误解
- 把工具选择重新放回场景
- 帮你建立优先级，而不是收集更多工具名

#### 2. 课程对“先学什么”给出的优先级非常明确

在众多工具里，课程最推荐优先投资的能力是：

- 更多使用键盘，减少鼠标依赖
- 学好编辑器
- 自动化重复任务
- 掌握 Git 并融入协作平台

这说明课程的价值观非常稳定：先优化那些最频繁、最基础、复利最高的环节。

#### 3. Bash、Python、其他语言的选择标准是任务结构

课程对语言选择没有教条，而是给了判断框架：

- Bash 适合简短、一次性、围绕外部命令的脚本
- Python 适合更复杂的逻辑、错误处理和代码复用
- 其他语言则看生态、性能、部署需求

真正重要的不是“哪门语言更高级”，而是任务是否仍然属于 shell 擅长的“编排”问题。

#### 4. `source script.sh` 和 `./script.sh` 的区别体现了 shell 环境边界

这是一个典型好问题。课程借它强调：

- `./script.sh` 会启动一个新的进程运行脚本
- `source script.sh` 会在当前 shell 中执行

所以前者对当前 shell 环境变量、工作目录的修改通常不会保留下来，后者会。

这正好呼应前面关于函数、脚本和 shell 进程边界的内容。

#### 5. 包管理、文件系统布局和安装位置，需要按层次理解

Q&A 里关于 `/bin`、`/lib`、`apt`、`pip` 的讨论，本质上是在帮你建立“软件安装层级”概念：

- 有系统级包管理器
- 有语言生态包管理器
- 它们的安装位置、升级机制、隔离边界不同

因此“用 apt 还是 pip”不是简单二选一，而要看你安装的是：

- 系统工具
- 语言库
- 命令行程序
- 项目本地依赖

#### 6. Docker、虚拟机、不同操作系统的选择，都应回到需求

课程在这些问题上的态度都很一致：

- Docker vs VM：看隔离粒度、系统完整性、部署需求
- Linux 发行版怎么选：看稳定性、包管理、社区、你的使用场景
- 浏览器怎么选：看性能、扩展、隐私和你的工作流

也就是说，工具比较不是排名赛，而是需求匹配。

#### 7. 编辑器宗派之争没有意义，真正重要的是你是否把工具用深

课程对 Vim vs Emacs 这类问题的回答很成熟：没有必要把工具变成身份认同。

真正要问的是：

- 这个工具是否支持你高频工作流
- 你是否愿意投入学习成本
- 你是否真的学到了足够深的层次

这也解释了为什么 Missing Semester 一直在强调工作流而不是品牌。

#### 8. 安全问题的建议仍然回到“成熟工具 + 正确实践”

Q&A 再次强调了几项最值得尽早默认化的实践：

- 密码管理器
- 2FA
- 合理的浏览器与插件选择
- 分清哪些 token、密钥、凭证应该如何保存

这和安全那一讲形成闭环：普通开发者最应该做的，是把成熟实践落地，而不是追逐表面复杂度。

#### 9. Q&A 最终想给你的，不是一套标准配置，而是一套判断框架

这一讲把整门课压缩成一种判断方式：

- 先找高频摩擦点
- 再找是否已有成熟工具可解决
- 再看学习成本与长期收益是否匹配
- 最后把有效方案固化进自己的工作流

这套框架比任何具体工具列表都更耐用，因为工具会变，但判断方法更稳定。

## 全课主线回顾

如果把整门课压成几句话，我会这样记：

### 1. 命令行不是备用方案，而是开放式接口

GUI 负责常见路径，shell 负责组合、自动化和远程操作。

### 2. 小工具组合比大而全更强

管道、脚本、正则、文本处理工具、Git、SSH、tmux 都在体现同一个思想：把复杂任务拆成可组合组件。

### 3. 环境和流程也要工程化

dotfiles、构建系统、测试、CI、包管理、调试工具，都是让个人工作方式从“临时手工”走向“可维护系统”。

### 4. 工具能力最终要落到习惯

真正有用的不是“我知道 tmux / Vim / Git / shellcheck 的存在”，而是：

- 我会在真实工作里默认使用它们
- 我的环境是文本化、版本化的
- 我的排错与优化是基于证据的

## 最值得养成的习惯

- 遇到重复操作，先问能不能脚本化
- 遇到大量文本，先问能不能管道化
- 遇到 Git 困惑，先回到数据模型
- 遇到 bug，先收集证据再修改
- 遇到性能问题，先 profile 再优化
- 遇到环境问题，先文本化和版本化配置
- 遇到安全问题，优先采用成熟工具，不自己造轮子

## 建议实践清单

- 为自己的 shell 写一份最小可用配置文件
- 学会用 `ssh` + `tmux` 在远端机器稳定工作
- 让 `git log --graph --all --decorate` 成为默认观察历史的方式之一
- 至少完整学一遍 `vimtutor`
- 把 3 个真实的数据处理任务改写成管道
- 为一个小项目补上 `Makefile`、测试和简单 CI
- 使用密码管理器并开启关键账户的 2FA

## 最后判断

`The Missing Semester` 真正缺失的不是“某几个命令”，而是“把工具、环境和流程当成计算机教育正式内容”的视角。

如果你学完后只多记住了一些命令，这门课就学浅了。
如果你开始：

- 主动自动化重复劳动
- 把环境配置成自己的工作系统
- 用正确抽象理解 Git、Shell、Vim 和安全工具

那这门课才算真正发挥价值。
