# 数据库约束是所有写入路径共享的最终合法性边界

<!-- bilingual-en:start -->
*Database constraints are the final shared validity boundary for all write paths*
<!-- bilingual-en:end -->

> [!summary] 原子定义
> 能用 `NOT NULL`、`CHECK`、`UNIQUE`、[[主键约束|PRIMARY KEY]] 或[[外键与关系基数|FOREIGN KEY]]直接表达的数据不变量，应尽量放在数据库 schema。所有写入同一数据库的服务、脚本和并发事务最终都经过这道边界；应用验证则负责更早、更友好的提示。
>
> <!-- bilingual-en:start -->
> Data invariants expressible with `NOT NULL`, `CHECK`, `UNIQUE`, [[主键约束|PRIMARY KEY]], or [[外键与关系基数|FOREIGN KEY]] should generally live in the database schema. Every service, script, and concurrent transaction writing that database crosses the boundary; application validation provides earlier, friendlier feedback.
> <!-- bilingual-en:end -->

## 自然解释

“注册前先查邮箱是否存在”能给用户即时提示，却挡不住两个并发请求同时查到不存在。`UNIQUE(email)` 让数据库在共同写入点只接受一个；另一个收到 constraint violation，再由应用翻译成可读错误。两层不是重复浪费，而是 UX 与完整性分工。

<!-- bilingual-en:start -->
Checking whether an email exists before registration gives immediate feedback but cannot stop two concurrent requests from both observing absence. `UNIQUE(email)` lets the database accept only one at the shared write point; the application translates the other constraint violation into a readable message. The layers divide user experience from integrity rather than redundantly doing the same job.
<!-- bilingual-en:end -->

约束还让数据规则进入 schema introspection、迁移和测试。相比散落在多个服务中的 `if`，它更接近受保护数据，也更容易发现旁路写入违反规则。

<!-- bilingual-en:start -->
Constraints also make rules visible to schema inspection, migrations, and tests. Compared with `if` statements scattered across services, they live closer to the protected data and catch bypass writes more reliably.
<!-- bilingual-en:end -->

> [!warning] 边界
> 不是每个跨系统或高度动态规则都能写成普通 constraint。无法直接表达时，仍要明确事务、锁、触发器或工作流边界；“约束优先”不等于把任意业务程序塞进数据库。
>
> <!-- bilingual-en:start -->
> Not every cross-system or highly dynamic rule fits an ordinary constraint. When it does not, define transaction, locking, trigger, or workflow boundaries explicitly. Constraint-first does not mean moving arbitrary application programs into the database.
> <!-- bilingual-en:end -->

> [!question]- 回忆与应用
> 已经有 `UNIQUE` 约束后，应用层还要不要先检查？
>
> **答案：** 可以为用户体验先检查，但最终仍必须捕获 constraint violation，因为并发可能让预检查立即过时。

## 来源与核验

- PostgreSQL 18, [*Constraints*](https://www.postgresql.org/docs/current/ddl-constraints.html)：定义 `NOT NULL`、`CHECK`、`UNIQUE`、主键和外键作为 schema-enforced rules。
