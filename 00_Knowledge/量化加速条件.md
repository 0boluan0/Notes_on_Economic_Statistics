# 量化只有减少实际瓶颈且收益超过转换开销时才会加速推理

<!-- bilingual-en:start -->
*Quantization accelerates inference only when it reduces the actual bottleneck enough to outweigh conversion overhead*
<!-- bilingual-en:end -->

降低[[量化对象|某个对象的存储位宽]]能减少其有效负载，但只有当实际运行因此缩短了限制速度的工作，且节省超过新增开销时，推理才会加速。需要检查真正的读入字节、kernel 使用的算术、反量化与布局处理，以及当前 batch 和上下文下的[[推理瓶颈诊断|实际瓶颈]]。

<!-- bilingual-en:start -->
Reducing [[量化对象|an object's storage bit width]] lowers its effective payload, but inference accelerates only if the actual execution shortens speed-limiting work by more than the added overhead. Relevant checks include bytes actually read, kernel arithmetic, dequantization and layout handling, and the [[推理瓶颈诊断|actual bottleneck]] at the current batch and context.
<!-- bilingual-en:end -->

## 存储收益怎样进入计算路径

<!-- bilingual-en:start -->
*How storage savings enter the execution path*
<!-- bilingual-en:end -->

若权重读取限制了速度，W4A16 可以通过读取较少的权重字节获益，即使乘法前仍要把权重反量化为 FP16。把解包和反量化融合进矩阵 kernel，能避免先把完整反量化权重写回显存；但这些操作仍有执行成本。若实际瓶颈在别处，或目标分组没有高效实现，文件缩小并不足以保证加速。

<!-- bilingual-en:start -->
If weight reads limit speed, W4A16 can benefit from reading fewer weight bytes even when weights are dequantized to FP16 before multiplication. Fusing unpacking and dequantization into the matrix kernel avoids writing a complete dequantized weight tensor back to device memory, but those operations still cost time. A smaller file is insufficient when the bottleneck lies elsewhere or the target grouping lacks an efficient implementation.
<!-- bilingual-en:end -->

## 用一笔构造成本看收益门槛

<!-- bilingual-en:start -->
*A constructed cost calculation shows the break-even point*
<!-- bilingual-en:end -->

为了隔离条件，假设一段执行的成本可直接相加：原来权重读取花 $8$ ms，其他工作花 $2$ ms，总计 $10$ ms。再假设量化把权重读取降至 $2$ ms，新增转换成本为 $T_c$，其他部分不变，则

<!-- bilingual-en:start -->
To isolate the condition, assume execution costs add without overlap: weight reads take $8$ ms and other work $2$ ms, totaling $10$ ms. Suppose quantization reduces weight reads to $2$ ms, adds conversion cost $T_c$, and leaves other work unchanged:
<!-- bilingual-en:end -->

$$
T_{\mathrm{quant}}=2+2+T_c=4+T_c\ \mathrm{ms},
\qquad
\mathrm{speedup}=\frac{10}{4+T_c}.
$$

因此只有 $T_c<6$ ms 才加速。若 $T_c=0.5$ ms，总时间为 $4.5$ ms，约快 $2.22$ 倍；若 $T_c=7$ ms，总时间为 $11$ ms，反而变慢。这些数值是明确给定的成本假设，不是实测结果；真实 kernel 可以重叠搬运与计算，不能直接把这个相加模型套进 profiler。

<!-- bilingual-en:start -->
Acceleration requires $T_c<6$ ms. With $T_c=0.5$ ms, total time is $4.5$ ms, a speedup of about $2.22$. With $T_c=7$ ms, the total is $11$ ms and execution is slower. These are stipulated costs, not measurements. Real kernels may overlap transfers and computation, so this additive model cannot be applied uncritically to profiling results.
<!-- bilingual-en:end -->

## 怎样判断实测收益属于谁

<!-- bilingual-en:start -->
*Attributing a measured gain*
<!-- bilingual-en:end -->

比较时按[[推理性能可比性]]匹配硬件、模型设置、长度与负载，分别看 prefill 和 decode。量化让更多请求同时装入显存，可能提高最大并发下的吞吐；这不直接证明相同 batch 下单个请求的延迟降低。速度收益还要与[[量化输出误差|输出和任务质量变化]]一起验收。

<!-- bilingual-en:start -->
Use [[推理性能可比性|a matched inference comparison]] for hardware, model settings, lengths, and load, and examine prefill and decode separately. Quantization can fit more concurrent requests in memory and increase throughput at maximum batch size without proving lower single-request latency at a fixed batch. Acceptance must also include [[量化输出误差|changes in outputs and task quality]].
<!-- bilingual-en:end -->

## 来源与核验

<!-- bilingual-en:start -->
*Sources and verification*
<!-- bilingual-en:end -->

- [Lin et al. (2024), *AWQ*](https://arxiv.org/html/2306.00978v3)，§4.1–4.2：支持特定负载的权重读取瓶颈、W4A16 的混合存储/计算格式，以及融合反量化的必要实现工作和开销。成本门槛例是作者给定假设下的计算。
  <!-- bilingual-en:start -->
  Sections 4.1–4.2 analyze weight-read bottlenecks for the examined workload, mixed storage/computation formats in W4A16, and the implementation and cost of fused dequantization. The break-even example is calculated from explicitly stipulated costs.
  <!-- bilingual-en:end -->
- [Liu et al. (2024), *KIVI*](https://arxiv.org/html/2402.02750v2)，§4.2.4：其效率比较提高 batch 直到内存上限，再报告吞吐，支持区分容量带来的并发收益与固定 batch 的延迟收益。
  <!-- bilingual-en:start -->
  Section 4.2.4 increases batch size to the memory limit before reporting throughput. This supports distinguishing concurrency gains enabled by capacity from latency gains at a fixed batch.
  <!-- bilingual-en:end -->
