# 锁文件记录一次依赖解析选中的精确版本或提交
<!-- bilingual-en:start -->
*A lockfile records the exact versions or commits selected by one dependency resolution*
<!-- bilingual-en:end -->

> [!summary] 原子状态
> manifest 表达允许范围，resolver 计算一个满足整张依赖图约束的具体结果，lockfile 保存该结果的精确信息。以 Cargo 为例，`Cargo.lock` 记录包版本、来源以及 Git dependency 的具体 commit；当 manifest 与现有 lockfile 仍兼容时，后续构建复用这些选择，`cargo update` 则显式要求重新解析并改写锁文件。
> <!-- bilingual-en:start -->
> A manifest expresses admissible ranges, a resolver computes a concrete result satisfying the whole dependency graph, and a lockfile records the exact result. In Cargo, `Cargo.lock` records package versions, sources, and concrete commits for Git dependencies. Later builds reuse those choices while the manifest remains compatible with the lockfile; `cargo update` explicitly requests a new resolution and rewrites the lockfile.
> <!-- bilingual-en:end -->

把 lockfile 纳入版本控制，可以让协作者和 CI 针对同一份解析快照工作，并让依赖升级成为可审查的变更，而不是每次安装时无声漂移。
<!-- bilingual-en:start -->
Version-controlling the lockfile lets collaborators and CI work from the same resolution snapshot and makes dependency upgrades reviewable changes instead of silent drift during each installation.
<!-- bilingual-en:end -->

## 边界

lockfile 的字段、更新命令和是否随某类发布物提交都由具体生态系统与项目政策决定；不要把 Cargo 的文件格式或维护规则泛化到所有包管理器。锁定解析结果也不等于已经保存依赖源码，vendoring 是另一种做法。
<!-- bilingual-en:start -->
Lockfile fields, update commands, and commit policy for different deliverables are ecosystem- and project-specific. Cargo's file format and maintenance rules must not be generalized to every package manager. Recording a resolution is also not the same as storing dependency source code; vendoring is a separate practice.
<!-- bilingual-en:end -->

> [!question]- 自检
> 为什么在 `Cargo.toml` 不变时，审查 `Cargo.lock` 的 diff 仍有意义？
>
> **答案：** manifest 的允许范围可能没变，但 lockfile diff 会显示具体解析版本、来源或 commit 是否改变。
