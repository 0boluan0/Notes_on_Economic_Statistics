# 索引用冗余访问结构加速匹配查询并支付存储与写维护成本

<!-- bilingual-en:start -->
*An index accelerates matching queries with a redundant access structure paid for by storage and write maintenance*
<!-- bilingual-en:end -->

> [!summary] 原子定义
> index（索引）为表数据维护额外的可搜索结构，使某些 predicate、join、ordering 或 covering access 能减少甚至避免全表 heap 扫描。代价是额外磁盘与缓存占用，以及表发生相关 `INSERT`、`UPDATE`、`DELETE` 时保持索引同步的写入开销；具体成本取决于 index method、数据分布和写入形状。
>
> <!-- bilingual-en:start -->
> An index maintains an additional searchable structure over table data so selected predicates, joins, orderings, or covering accesses can reduce or avoid a full heap scan. The cost is extra disk and cache footprint plus the write overhead of keeping the index synchronized during relevant `INSERT`, `UPDATE`, and `DELETE` operations; exact costs depend on the index method, data distribution, and write shape.
> <!-- bilingual-en:end -->

## 自然解释

图书的主题索引能直接定位少数页，却要占页数，并在改版时同步更新。数据库索引相同：`WHERE user_id = ?` 若只返回极少行，B-tree 路径可能省掉大量读取；若查询要返回表中大多数行，逐个索引定位再访问 heap 反而可能比顺序扫描更贵。

<!-- bilingual-en:start -->
A book index locates a few pages quickly but consumes pages and must be updated on revision. A database index is similar: a B-tree can avoid much reading for `WHERE user_id = ?` when few rows match, while fetching most of a table through individual index entries and heap visits can cost more than a sequential scan.
<!-- bilingual-en:end -->

因此，索引不是“出现 WHERE 就加”的装饰。先确定工作负载中真正昂贵且频繁的访问形状，再选择能服务它们的最小索引集合，并衡量写放大与缓存压力。

<!-- bilingual-en:start -->
An index is not decoration to add whenever a column appears in WHERE. Identify expensive, frequent access shapes first, then choose the smallest index set that serves them and measure write amplification and cache pressure.
<!-- bilingual-en:end -->

> [!warning] 边界
> 索引通常不改变普通查询的逻辑结果，但 unique index 会实施唯一性，属于语义约束。不同 index method（B-tree、hash、GiST、GIN、BRIN）支持的操作不同，不能把 B-tree 规则套给全部索引。
>
> <!-- bilingual-en:start -->
> An ordinary index usually does not change query semantics, but a unique index enforces uniqueness and is therefore semantic. Different methods—B-tree, hash, GiST, GIN, and BRIN—support different operations; B-tree rules do not apply to every index.
> <!-- bilingual-en:end -->

> [!question]- 回忆与应用
> 为什么一个从不读取、但每秒大量更新的列上索引可能让系统整体变差？
>
> **答案：** 没有读收益，却让相关写入维护额外结构，并增加存储、I/O 与缓存压力。
