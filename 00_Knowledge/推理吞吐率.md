# 推理吞吐率是在明确观测窗口内完成的工作量除以窗口时长

<!-- bilingual-en:start -->
*Inference throughput is the amount of work completed in a specified observation window divided by its duration*
<!-- bilingual-en:end -->

**推理吞吐率**衡量系统每单位时间处理了多少工作。必须给出工作单位与观测窗口：完成请求数除以时间得到 requests/s；生成输出 token 总数除以时间得到 output tokens/s。两者都属于系统聚合指标，并不直接给出某一用户的等待时间。

<!-- bilingual-en:start -->
**Inference throughput** measures how much work a system processes per unit time. Specify both the work unit and observation window: completed requests per time gives requests/s, while generated output tokens per time gives output tokens/s. Both are system aggregates rather than direct measurements of an individual user's wait.
<!-- bilingual-en:end -->

设窗口时长为 $T>0$，按约定在窗口中计入的完成请求数为 $R$，输出 token 数为 $O$，则

<!-- bilingual-en:start -->
For window duration $T>0$, let $R$ be the completed-request count and $O$ the output-token count included under the declared convention. Then
<!-- bilingual-en:end -->

$$
\mathrm{Throughput}_{\mathrm{request}}=\frac{R}{T},
\qquad
\mathrm{Throughput}_{\mathrm{output}}=\frac{O}{T}.
$$

## 一个窗口里的请求与 token

<!-- bilingual-en:start -->
*Requests and tokens within one window*
<!-- bilingual-en:end -->

一个10秒窗口完成20个请求、共计600个输出token，则得到2 requests/s和60 output tokens/s。若这些请求各输出30个token，单请求从发送到完成用了4秒，则该请求按完整等待时间计算为7.5 output tokens/s。系统可同时服务多个请求，所以60与7.5无需相等。

<!-- bilingual-en:start -->
A 10-second window with 20 completed requests and 600 output tokens yields 2 requests/s and 60 output tokens/s. If each request returns 30 tokens in four seconds from send to completion, one request's rate over that full wait is 7.5 output tokens/s. Concurrent service means this need not equal the system's 60 output tokens/s.
<!-- bilingual-en:end -->

这项每请求的 $30/4$ 也不是 $1/\mathrm{TPOT}$：它的时间包含首输出之前的等待。[[首Token延迟]]、[[Token间隔]]和[[请求完成延迟]]分别保留交互体验的不同部分。

<!-- bilingual-en:start -->
The per-request $30/4$ rate also differs from $1/\mathrm{TPOT}$ because its duration includes the initial wait. [[首Token延迟|TTFT]], [[Token间隔|ITL]], and [[请求完成延迟|completion latency]] retain different aspects of the interaction.
<!-- bilingual-en:end -->

## 计数对象要与时间窗口匹配

<!-- bilingual-en:start -->
*Match the counted work to the observation window*
<!-- bilingual-en:end -->

在一个有限 benchmark 中可以把全部成功请求的输出数除以整次运行时间；在长期服务的滑动窗口中也可以统计该窗口实际发出的 token。若改为只挑“窗口内完成的请求”，它们部分输出可能在窗口开始前已经生成。两种选择需要分别声明，不能把分子来自一套窗口、分母来自另一套窗口。

<!-- bilingual-en:start -->
A finite benchmark can divide outputs from all successful requests by total run duration; a live-service window can instead count tokens actually emitted during that interval. Selecting only requests completed within a window can include outputs generated before the window began. State the convention and use a matching numerator and denominator.
<!-- bilingual-en:end -->

输入加输出 tokens/s 与仅输出 tokens/s 也应分开命名。跨模型时，[[Token口径|tokenizer与预处理]]决定每个 token 代表什么；仅凭更高 tokens/s 不能判断相同文本工作是否更快完成，也不能判断响应延迟或质量是否满足要求。公平比较见[[推理性能可比性]]；只统计满足服务条件的产出时，使用明确口径的[[达标吞吐量]]。

<!-- bilingual-en:start -->
Input-plus-output tokens/s must also be named separately from output-only tokens/s. Across models, [[Token口径|tokenization and preprocessing]] determine the counting unit. Higher tokens/s alone cannot establish faster completion of the same text workload or acceptable latency and quality. Use [[推理性能可比性|matched performance evaluation]] for comparisons, and an explicitly defined [[达标吞吐量|goodput]] when counting only work meeting service conditions.
<!-- bilingual-en:end -->
