# 推理瓶颈诊断先定位受损阶段，再用对应资源证据检验优化假设
<!-- bilingual-en:start -->
*Inference bottleneck diagnosis locates the affected stage and tests optimization hypotheses with matching resource evidence*
<!-- bilingual-en:end -->

诊断推理性能时，先把“慢”定位到实际时间线，再检查该阶段的计算、搬运、容量或等待证据。模型名字、参数量和 GPU 利用率只是线索；同样的首 token 变慢，可能来自排队，也可能来自提示处理，所需优化并不相同。

<!-- bilingual-en:start -->
Locate slowness on the request timeline before inspecting compute, traffic, capacity, or waiting in that stage. Model names, parameter counts, and GPU utilization are clues rather than diagnoses. Queueing and prompt processing can both worsen first-token latency but call for different changes.
<!-- bilingual-en:end -->

先按 [[推理性能可比性]] 固定对比条件，再把一次观测分成三层：客户端看到的 [[首Token延迟|首 token]] 与 [[Token间隔|流式间隔]]，服务端排队/调度/执行区间，以及 [[性能剖析|算子与资源占用]]。跨进程或跨机器时间戳要先解决时钟与事件对应，不能将不同时钟的原值直接相减。

<!-- bilingual-en:start -->
Start with [[推理性能可比性|matched conditions]], then relate client-visible first-token and streaming times to server queueing/scheduling/execution and [[性能剖析|operator/resource profiles]]. Establish clock and event correspondence before subtracting timestamps across processes or machines.
<!-- bilingual-en:end -->

| 现象 | 先检查什么 | 由证据决定的后续动作 |
|---|---|---|
| TTFT 升高 | 等待开始执行的时间，实际 [[预填充]] 时长，前缀命中与输入长度 | 若主要是队列，先查负载与准入；若主要是计算，查矩阵形状、内核和提示处理 |
| 生成中出现长停顿 | 时间线是否遇到长 prefill、抢占、同步或传输缓冲 | 若确有 prefill 干扰，检验 [[分块预填充]]；若为网络缓冲，GPU 内核改动未必有效 |
| 长历史或并发导致 OOM | 逐阶段峰值、有效 KV 与物理池、workspace/图执行占用 | 按 [[推理显存预算]] 核算，再决定缓存、并发、长度或表示的调整 |
| 运算量降低但延迟不降 | 算子实际流量、利用率、通信与转换成本 | 用 [[Roofline模型]] 建立资源假设，再以 profile 验证；量化具体看 [[量化加速条件]] |

<!-- bilingual-en:start -->
Check execution waits versus prefill for TTFT; scheduling and transport events for stalls; simultaneous allocations for OOM; and actual traffic, utilization, communication, or conversion cost when fewer operations fail to reduce latency. Each branch leads to a testable hypothesis, not an automatic setting change.
<!-- bilingual-en:end -->

例如一组构造记录中，修改前客户端 TTFT 为 300 ms，其中执行前等待 200 ms；修改后 TTFT 为 160 ms，而 prefill 两次均约 60 ms。这支持“总体等待缩短”，不支持“prefill 内核快了近两倍”。要进一步归因到调度改动，还需同负载对照，并排除网络、缓存命中等同时变化。

<!-- bilingual-en:start -->
Suppose constructed traces show TTFT falling from 300 to 160 ms, with 200 ms of pre-execution waiting originally and prefill remaining about 60 ms in both runs. This supports less overall waiting, not a nearly twofold kernel improvement. Attributing the gain to scheduling still requires matched load and checking other changes such as transport or cache hits.
<!-- bilingual-en:end -->

一次只检验有证据支持的具体假设，记录修改前后的质量、延迟分布、吞吐与峰值内存；剖析本身有开销，最终性能应独立重测。新瓶颈出现并不奇怪：减少权重搬运后，KV 读取或其他算子可能成为主要成本。诊断的终点是目标任务满足约束，不是把某个利用率数字推到最大。

<!-- bilingual-en:start -->
Test evidence-backed hypotheses and record quality, latency distributions, throughput, and peak memory. Profiling adds overhead, so measure final performance independently. Removing weight-traffic cost can expose KV reads or other operators as the next limit. Success means meeting the task's constraints, not maximizing a utilization number.
<!-- bilingual-en:end -->

## 来源与核验

- [NVIDIA, *GPU Performance Background*](https://docs.nvidia.com/deeplearning/performance/dl-performance-gpu-background/index.html)，§4：支持计算、带宽与延迟限制的区分。
- [Agrawal et al. (2024), *Sarathi-Serve*](https://arxiv.org/html/2403.02310v1)，§3.1、§4.1–4.3：支持长 prefill 对 decode 的调度干扰及分块处理的具体作用条件。
- [Kwon et al. (2023), *PagedAttention*](https://arxiv.org/html/2309.06180v1)，§3–4：支持有效 KV 与实际分配的区别。诊断表和构造时间例是将这些机制与 [[性能剖析]] 方法结合的应用推理，不是某次本机诊断记录。

<!-- bilingual-en:start -->
NVIDIA establishes resource limits; Sarathi explains scheduling interference; PagedAttention explains allocation effects. The diagnostic branches and timing example apply these mechanisms with the shared profiling method and do not report a local benchmark.
<!-- bilingual-en:end -->
