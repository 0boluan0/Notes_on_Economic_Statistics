# 行级锁把冲突写入串行到事务结束但不能替代完整不变量设计

<!-- bilingual-en:start -->
*PostgreSQL row locks normally serialize conflicting writes until transaction end but do not replace invariant design*
<!-- bilingual-en:end -->

> [!summary] 原子定义
> `SELECT ... FOR UPDATE` 或写入操作可以取得 row-level lock，使其他对同一行的冲突锁等待到当前事务结束。锁把明确资源上的竞争排队，却只保护实际返回并锁住的行；普通 row lock 不能直接锁住“目前不存在的行”或任意谓词范围，相关业务不变量仍可能被并发破坏。
>
> <!-- bilingual-en:start -->
> `SELECT ... FOR UPDATE` or a write can acquire a row-level lock, making conflicting lock requests on the same row wait until the current transaction ends. A lock queues competition over an identified resource but protects only rows actually returned and locked. An ordinary row lock cannot directly lock a currently absent row or an arbitrary predicate range, so the related invariant can remain vulnerable.
> <!-- bilingual-en:end -->

## 自然解释

预订座位时，先 `SELECT ... FOR UPDATE` 锁住该座位行，再检查状态和更新，能让同一座位的其他写者等待。但若规则是“一个用户在所有场次最多一张票”，只锁目标座位不能保护跨多行的用户约束；更直接的唯一约束往往更可靠。

<!-- bilingual-en:start -->
For seat booking, locking the seat row with `SELECT ... FOR UPDATE` before checking and updating makes other writers for that seat wait. But if the rule is “one ticket per user across all sessions,” locking only the target seat does not protect the cross-row user invariant; a direct unique constraint is often more reliable.
<!-- bilingual-en:end -->

锁通常持有到事务结束，所以事务越长，等待与死锁机会越大。先获取锁再调用慢外部 API，会把网络延迟带进数据库临界区；应先缩短事务并固定资源访问顺序。

<!-- bilingual-en:start -->
Locks are generally held until transaction end, so longer transactions increase waiting and deadlock opportunities. Acquiring a lock before a slow external API call drags network latency into the database critical section. Keep transactions short and acquire resources in a consistent order.
<!-- bilingual-en:end -->

> [!warning] 边界
> MVCC 下普通读取通常不会被行写锁阻塞；具体 lock mode 的冲突矩阵不同。不能把“锁行”笼统理解为所有人都无法读取该行。行锁通常在事务结束释放，但在 savepoint 之后取得的锁会随 `ROLLBACK TO SAVEPOINT` 释放。
>
> <!-- bilingual-en:start -->
> Under MVCC, an ordinary read is usually not blocked by a row write lock, and lock modes have different conflict matrices. “The row is locked” does not mean nobody can read it. Row locks normally last to transaction end, but a lock acquired after a savepoint is released by `ROLLBACK TO SAVEPOINT`.
> <!-- bilingual-en:end -->

> [!question]- 回忆与应用
> 规则涉及两行 A、B，但事务只锁 A 后读 B。为什么仍可能出错？
>
> **答案：** 另一事务仍可并发改变 B；锁的保护集合没有覆盖决定不变量的全部资源。

## 来源与核验
