# 有符号整数溢出是未定义行为而无符号算术按模数回绕
<!-- bilingual-en:start -->
*Signed integer overflow is undefined behaviour, while unsigned arithmetic wraps modulo its range*
<!-- bilingual-en:end -->

> [!summary] 原子区别
> 若一个有符号整数运算的数学结果无法由结果类型表示，C 不规定程序接下来会怎样；不能把它当成自动绕回。无符号整数则使用模 $2^N$ 的算术，其中 $N$ 是该类型值表示所用的位数，因此回绕是语义的一部分。
> <!-- bilingual-en:start -->
>
> &nbsp;
> If the mathematical result of a signed integer operation cannot be represented in the result type, C does not define what follows; automatic wraparound must not be assumed. Unsigned integer arithmetic is defined modulo $2^N$, where $N$ is the number of value bits, so wraparound is part of its semantics.
> <!-- bilingual-en:end -->

```c
int a = INT_MAX;
int b = a + 1;          // 未定义行为

unsigned u = UINT_MAX;
unsigned v = u + 1;    // 定义良好，结果为 0
```

未定义行为的重要后果不只是“结果不可预测”。编译器可以依据“有定义的程序不会发生 signed overflow”来变换代码，所以一次测试中观察到的补码回绕不能成为推理依据。
<!-- bilingual-en:start -->
The consequence of undefined behaviour is not merely an unpredictable numeric result. A compiler may transform code under the assumption that a defined program does not overflow a signed integer, so two's-complement wraparound observed in one test is not a valid semantic basis.
<!-- bilingual-en:end -->

## 怎样在运算前守住边界

对正数加法 `a + b`，应在执行加法前验证 `a <= INT_MAX - b`；若输入规模本来就可能超过范围，改用更宽且经证明足够的类型，或使用明确报告失败的 checked arithmetic。把结果赋给更宽类型为时已晚：若两个操作数仍是 `int`，溢出已经在 `int` 运算中发生。

无符号回绕虽然定义良好，也不必然符合业务语义。余额、长度和权限计数通常仍应在边界处拒绝回绕；只有哈希、位运算或环形序号等确实需要模算术的场景，回绕才是设计的一部分。
<!-- bilingual-en:start -->
For positive addition `a + b`, verify `a <= INT_MAX - b` before performing the addition. If the input range genuinely exceeds the type, choose a wider type proven sufficient or use checked arithmetic that reports failure. Assigning the result to a wider variable is too late when both operands were still evaluated as `int`.

Defined unsigned wraparound is not automatically correct business behaviour. Balances, lengths, and permission counts usually need explicit rejection at their limits. Wraparound belongs in the design only where modular arithmetic is intended, such as some hashes, bit operations, or circular sequence numbers.
<!-- bilingual-en:end -->

“无符号会回绕”还要求该运算**实际在无符号结果类型中执行**。`unsigned char`、`unsigned short` 等较小类型可能先整数提升为 `int`；若提升后的有符号运算溢出，之后再存回无符号对象并不能把它改写成一次定义良好的无符号回绕。先按[[通常算术转换|整数提升与通常算术转换]]确定运算类型，再判断溢出语义。
<!-- bilingual-en:start -->
“Unsigned wraps” also requires the operation to be **performed in an unsigned result type**. Small types such as `unsigned char` and `unsigned short` may first be promoted to `int`; if that promoted signed operation overflows, storing the result back into an unsigned object later does not retroactively make it a defined unsigned wrap. Determine the operation type through [[通常算术转换|integer promotions and the usual arithmetic conversions]] before applying overflow rules.
<!-- bilingual-en:end -->

> [!question]- 自检
> `long total = x * y;` 中 `x` 和 `y` 都是 `int`。为什么 `long` 不一定能防住乘法溢出？
>
> **答案：** 乘法先按操作数转换后的类型求值；若它仍是 `int`，可能在赋给 `long` 之前已经发生未定义的 signed overflow。应在运算前转换并验证范围。
