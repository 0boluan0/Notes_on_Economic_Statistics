# 持久性承诺从数据库确认提交后才开始且受故障模型与配置限定

<!-- bilingual-en:start -->
*Durability depends on the commit acknowledgement boundary, failure model, and configuration*
<!-- bilingual-en:end -->

> [!summary] 原子定义
> durability（持久性）指数据库已经确认成功提交的事务，在系统承诺覆盖的故障后仍可恢复。它不是“执行过 SQL 就永不丢”，也不是无限故障保证；确认时点、WAL 刷盘、同步复制和存储可靠性共同决定承诺边界。
>
> <!-- bilingual-en:start -->
> Durability means that a transaction acknowledged as committed remains recoverable after failures covered by the system's guarantee. It does not mean that any executed SQL can never be lost, nor is it an unlimited failure guarantee. Acknowledgement timing, WAL flush, synchronous replication, and storage reliability define the boundary.
> <!-- bilingual-en:end -->

## 自然解释

事务已经在内存中计算完成，却还没得到 `COMMIT` 成功响应时，客户端不能确认结果是否已持久：提交可能没有发生，也可能已经发生但响应丢失。在 PostgreSQL 默认的同步提交与可靠存储配置下，服务器先把提交所需的 WAL 刷到持久介质，再返回成功；崩溃后可据此重做尚未写入数据页的已提交更新。

<!-- bilingual-en:start -->
If a transaction has finished its in-memory work but the client has not received a successful `COMMIT` response, the outcome is unknown: commit may not have happened, or it may have happened and the response was lost. With PostgreSQL's default synchronous-commit behavior and reliable storage, the server flushes the required WAL before returning success and can later redo committed changes not yet written to data pages.
<!-- bilingual-en:end -->

PostgreSQL 的 `synchronous_commit`、`fsync`、表的 logged/unlogged 属性与复制配置都会改变保证。比如 `synchronous_commit=off` 可在本地 WAL 刷盘前返回成功；服务器崩溃可能丢失最近已确认的事务，但数据库仍保持一致，效果等同这些事务被干净中止。设计时必须写清要抵御的是进程崩溃、主机断电、存储损坏还是整站故障。

<!-- bilingual-en:start -->
PostgreSQL settings such as `synchronous_commit` and `fsync`, whether a table is logged or unlogged, and replication configuration all change the guarantee. For example, `synchronous_commit=off` may report success before local WAL is flushed; a server crash can lose recent acknowledged transactions while preserving database consistency, as if those transactions had aborted cleanly. A design must state whether it covers process crash, host power loss, storage loss, or site failure.
<!-- bilingual-en:end -->

> [!warning] 边界
> 原子性与持久性不同：一次事务可以在崩溃前从未被部分提交，却仍因没有达到所配置的持久化点而整体丢失。备份也不同于 WAL 持久性；它保护的是更广的误删、损坏和历史恢复场景。
>
> <!-- bilingual-en:start -->
> Atomicity and durability differ. A transaction may never become partially visible yet still be lost as a whole if it had not reached the configured durability point. Backups are also distinct from WAL durability; they cover broader deletion, corruption, and historical recovery scenarios.
> <!-- bilingual-en:end -->

> [!question]- 回忆与应用
> 服务端说“语句执行完了”，但客户端没有收到 commit 成功。能否把订单标成已持久保存？
>
> **答案：** 不能仅凭语句执行完判断。此时结果未知，不能假定“已提交”或“未提交”；要用幂等键或状态查询解析结果，再决定是否安全重试。

## 来源与核验

- PostgreSQL 18, [*Write-Ahead Logging*](https://www.postgresql.org/docs/current/wal-intro.html)：说明 WAL 先于数据页落盘及崩溃后的 REDO 边界。
- PostgreSQL 18, [*Write Ahead Log / synchronous_commit*](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT)：说明成功响应、本地 WAL flush 与同步副本等待之间的配置边界。
- PostgreSQL 18, [*Non-Durable Settings*](https://www.postgresql.org/docs/current/non-durability.html)：列出 `fsync`、unlogged table 等会缩小或取消持久性保证的设置。
