# 测试、调试、异常与断言
<!-- bilingual-en:start -->
*Testing, Debugging, Exceptions, and Assertions*
<!-- bilingual-en:end -->

> [!summary] 快速恢复
> **它解决什么：** 用可重复证据发现程序不符合规格的位置，并让预期失败以明确方式传播。
> **具体锚点：** 函数正常输入通过不代表正确；空列表、边界值、重复值和错误类型往往暴露隐含假设。
> **核心难点：** 测试证明发现过的反例，不证明没有 bug；异常用于运行时失败，断言用于程序内部本应成立的不变量。
> **为什么重要：** 没有规格和最小失败案例，调试会退化成随机改代码。
> **继续：** 先写 expected/actual，再二分定位最小失败；修根因后留下能复现的测试。
> <!-- bilingual-en:start -->
> **Problem addressed:** Use repeatable evidence to locate where software violates its specification, and propagate expected failures explicitly.
> **Concrete anchor:** Passing ordinary inputs does not establish correctness; an empty list, a boundary value, a duplicate, or a wrong type often exposes a hidden assumption.
> **Central difficulty:** Tests demonstrate discovered counterexamples rather than proving the absence of bugs; exceptions represent runtime failures, while assertions express internal invariants that should hold.
> **Why it matters:** Without a specification and a minimal failing case, debugging degenerates into random edits.
> **Continue with:** Write expected and actual behavior, minimize the failure, locate it by controlled experiments, and retain a regression test after fixing the root cause.
> <!-- bilingual-en:end -->

## 测试从规格开始
<!-- bilingual-en:start -->
*Testing Starts from a Specification*
<!-- bilingual-en:end -->

列等价类、边界、错误输入和不变量。black-box 从接口规格选例，glass-box 覆盖分支/路径。覆盖率提示没走过的代码，不衡量断言质量。
<!-- bilingual-en:start -->
List equivalence classes, boundaries, invalid inputs, and invariants. Black-box tests derive cases from the interface contract, while glass-box tests exercise branches and paths. Coverage reveals code that was not executed; it does not measure the quality of assertions.
<!-- bilingual-en:end -->

## 单元、集成与系统层级
<!-- bilingual-en:start -->
*Unit, Integration, and System Levels*
<!-- bilingual-en:end -->

单元测试隔离小组件，集成测试检查组件契约，端到端检查用户流程。失败应尽量在最小层级复现；全部依赖 mock 会错过真实集成问题。
<!-- bilingual-en:start -->
A unit test isolates a small component, an integration test checks component contracts, and an end-to-end test checks a user workflow. Reproduce a failure at the smallest useful level; mocking every dependency can hide real integration faults.
<!-- bilingual-en:end -->

## 调试循环
<!-- bilingual-en:start -->
*The Debugging Loop*
<!-- bilingual-en:end -->

稳定复现，读完整 traceback，缩小输入/路径，提出可证伪假设，用打印、debugger 或断点观察状态，只改一个原因并重跑。修复共享函数前搜索所有调用者，避免只补一个症状。
<!-- bilingual-en:start -->
Reproduce the failure reliably, read the complete traceback, minimize the input and path, form a falsifiable hypothesis, inspect state with logging or a debugger, change one cause, and rerun. Before changing a shared function, inspect all callers so that the fix addresses the root rather than one symptom.
<!-- bilingual-en:end -->

先复现和定位，再 profile；直觉猜热点常错。CPU、内存、I/O 和延迟需不同工具。优化前记录基线，修复后保留回归检查。
<!-- bilingual-en:start -->
Reproduce and locate the problem before profiling; intuition often guesses the wrong hotspot. CPU, memory, I/O, and latency require different measurements. Record a baseline before optimization and retain a regression check afterward.
<!-- bilingual-en:end -->

## Worked example：从失败到回归测试
<!-- bilingual-en:start -->
*Worked Example: From Failure to Regression Test*
<!-- bilingual-en:end -->

若 `mean([])` 触发除零，先把空列表缩成最小失败输入，再由接口选择“拒绝空输入”这一明确行为。测试固定预期异常，修复只发生在共享函数入口。
<!-- bilingual-en:start -->
If `mean([])` divides by zero, minimize the failure to the empty list and let the interface choose an explicit behavior: reject empty input. A regression test fixes the expected exception, and the implementation changes once at the shared function boundary.
<!-- bilingual-en:end -->

```python
def mean(values):
    if not values:
        raise ValueError("mean requires at least one value")
    return sum(values) / len(values)


def test_empty_mean():
    try:
        mean([])
    except ValueError as exc:
        assert "at least one" in str(exc)
    else:
        raise AssertionError("ValueError was not raised")
```

## 异常
<!-- bilingual-en:start -->
*Exceptions*
<!-- bilingual-en:end -->

`try` 包围可能失败的最小语句，捕获具体异常；`else` 放无异常路径，`finally` 清理资源。不要吞掉异常或用裸 `except` 隐藏编程错误。自定义异常表达领域失败。
<!-- bilingual-en:start -->
Place the smallest potentially failing statement inside `try` and catch a specific exception. Put the success path in `else` and resource cleanup in `finally`. Do not swallow failures or use a bare `except` that hides programming errors. A custom exception can represent a domain-specific failure.
<!-- bilingual-en:end -->

## assertions
<!-- bilingual-en:start -->
*Assertions*
<!-- bilingual-en:end -->

`assert` 检查内部不变量和开发期假设，不用于验证不可信用户输入或必须执行的安全检查，因为可被优化禁用。消息应说明期待条件。
<!-- bilingual-en:start -->
`assert` checks internal invariants and development-time assumptions. It must not validate untrusted user input or enforce a security check that must always run, because optimized execution can disable assertions. Its message should state the expected condition.
<!-- bilingual-en:end -->

## 防御与 fail fast
<!-- bilingual-en:start -->
*Defensive Checks and Fail Fast*
<!-- bilingual-en:end -->

接口处验证类型、范围和资源状态，错误信息包含上下文但不泄露秘密。越早发现无效状态，越易定位。
<!-- bilingual-en:start -->
Validate type, range, and resource state at an interface. An error message should include useful context without leaking secrets. The earlier an invalid state is detected, the easier it is to locate.
<!-- bilingual-en:end -->

## 回归测试
<!-- bilingual-en:start -->
*Regression Tests*
<!-- bilingual-en:end -->

每个修复保留最小能在旧代码失败、新代码通过的检查。测试应确定、快速，并隔离时间、随机和外部服务。
<!-- bilingual-en:start -->
Every fix should retain the smallest check that failed on the old code and passes on the new code. Tests should be deterministic and fast, with time, randomness, and external services isolated.
<!-- bilingual-en:end -->

## 失败诊断
<!-- bilingual-en:start -->
*Failure Diagnosis*
<!-- bilingual-en:end -->

- 测试偶发失败：先记录随机 seed、时间、并发顺序和外部响应，区分不确定输入与共享状态泄漏。
  <!-- bilingual-en:start -->
  A test fails intermittently: record the random seed, time, concurrency order, and external responses, then distinguish nondeterministic input from leaked shared state.
  <!-- bilingual-en:end -->
- 修复一个入口后别处仍坏：搜索所有调用者和所有写入路径，找到共同不变量应由哪一层维护。
  <!-- bilingual-en:start -->
  One entry point is fixed but siblings still fail: inspect all callers and write paths to locate the layer that should enforce the shared invariant.
  <!-- bilingual-en:end -->
- 捕获异常后程序静默错误：检查是否捕获过宽、未重新抛出，或把编程错误当作业务失败处理。
  <!-- bilingual-en:start -->
  The program silently continues after an exception: check for an overly broad handler, a missing re-raise, or a programming error misclassified as a domain failure.
  <!-- bilingual-en:end -->

## 最小自检
<!-- bilingual-en:start -->
*Minimum Self-Check*
<!-- bilingual-en:end -->

### 为什么高覆盖率不等于测试充分？
<!-- bilingual-en:start -->
*Why does high coverage not imply adequate testing?*
<!-- bilingual-en:end -->

> [!answer]- 答案
> 代码可被执行却没有正确断言，边界和规格也可能未覆盖。
<!-- bilingual-en:start -->
> [!answer]- Answer
> Code can execute without a meaningful assertion, while important boundaries and parts of the specification may remain untested.
<!-- bilingual-en:end -->

### 何时用异常、何时用 assert？
<!-- bilingual-en:start -->
*When should an exception be used, and when should `assert` be used?*
<!-- bilingual-en:end -->

> [!answer]- 答案
> 可预期运行时/输入失败用异常；程序内部逻辑上必须成立的不变量用 assert。
<!-- bilingual-en:start -->
> [!answer]- Answer
> Use an exception for an expected runtime or input failure, and an assertion for an internal invariant that must logically hold if the program is correct.
<!-- bilingual-en:end -->

### 调试时为什么先做最小复现？
<!-- bilingual-en:start -->
*Why should debugging begin with a minimal reproduction?*
<!-- bilingual-en:end -->

> [!answer]- 答案
> 减少同时变化因素，让因果假设可检验，并形成稳定回归测试。
<!-- bilingual-en:start -->
> [!answer]- Answer
> It reduces simultaneous variables, makes causal hypotheses testable, and provides the basis for a stable regression test.
<!-- bilingual-en:end -->

### 一个测试只断言“没有抛异常”，它漏掉了什么？
<!-- bilingual-en:start -->
*What does a test miss if it only asserts that no exception was raised?*
<!-- bilingual-en:end -->

> [!answer]- 答案
> 它没有验证返回值、状态变化、副作用或不变量，错误结果也可能安静通过。
<!-- bilingual-en:start -->
> [!answer]- Answer
> It does not verify the return value, state transition, side effects, or invariants, so an incorrect result may pass silently.
<!-- bilingual-en:end -->
