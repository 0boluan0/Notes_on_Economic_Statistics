# 显式栈把待处理调用状态变成普通数据并避免依赖解释器递归深度

<!-- bilingual-en:start -->
*An explicit stack turns pending call state into ordinary data and avoids dependence on the interpreter's recursion depth*
<!-- bilingual-en:end -->

> [!summary] 原子改写
> 递归调用栈保存“接下来处理哪个子问题、返回后从哪里继续、已有的局部结果”。把这些信息显式写成栈元素，就能用循环执行同一后进先出过程。这样不再消耗 Python 的解释器递归深度，但仍要为尚未处理的状态使用内存。

只要求前序访问时，栈元素可以只是待访问节点：

```python
def preorder(root):
    if root is None:
        return []
    out, stack = [], [root]
    while stack:
        node = stack.pop()
        out.append(node.value)
        stack.extend(reversed(node.children))
    return out
```

这里假定 `node.children` 是可反向遍历的有限有序序列。反向压入 children 是为了让原本最左的子节点最先弹出，从而保持递归版本的访问顺序；若 children 本身无序，就没有同一个“从左到右”顺序可保持。若算法要在所有子节点完成后再组合结果，仅保存节点就不够；栈项还需记录阶段，例如 `(node, expanded)`，这正是在手工编码原栈帧的“返回位置”。

显式栈不是无条件更好：

- 它绕开的是解释器的递归深度限制，不会消除算法本身的待办状态，也不会防止总体内存耗尽。固定最大分支数的深度优先树遍历常只需 $O(h)$ 个栈项；但上例会一次压入某节点的全部 children，若节点度数没有上界，星形树即使高度为 1 也可能暂存 $\Theta(n)$ 个节点。
- 树形浅、递归结构清楚时，递归版本可能更易验证；输入深度来自外部且没有可信上界时，显式栈通常更稳健。
- 直接提高 `sys.setrecursionlimit()` 不是通用修复；Python 文档明确提醒过高上限可能让底层 C 栈溢出并崩溃。

> [!question]- 自检
> 把后序树遍历改成循环时，只往栈中放节点，不记录“子节点是否已经处理”。为什么容易出错？
>
> **答案：** 后序遍历需要在返回阶段才处理父节点；原递归 frame 隐含保存了这个继续位置。显式版本必须另存阶段或采用等价的双栈/反转方法。
