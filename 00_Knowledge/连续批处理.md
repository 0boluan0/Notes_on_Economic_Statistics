# 连续批处理在生成迭代之间移除已完成请求并接纳可执行的新请求

<!-- bilingual-en:start -->
*Continuous batching removes completed requests and admits runnable new requests between generation iterations*
<!-- bilingual-en:end -->

**连续批处理**（continuous batching）把成员选择放在生成迭代的边界：调度器选择本轮请求，执行一轮，更新各请求状态，再为下一轮移除完成者、接纳符合资源与调度条件的新请求。它允许当前批随迭代变化，而无需等待原来整组请求全部生成完。

<!-- bilingual-en:start -->
**Continuous batching** selects membership at generation-iteration boundaries. The scheduler chooses requests, executes an iteration, updates their state, then removes completed requests and admits eligible new requests for the next iteration. Membership can change without waiting for the original group to finish generating.
<!-- bilingual-en:end -->

## 从空出的槽位到下一轮机会

<!-- bilingual-en:start -->
*A freed slot creates an opportunity in the next iteration*
<!-- bilingual-en:end -->

沿用[[静态批处理]]的A/B/C例子：A与B运行一轮后A完成，B还需继续，C在等待。下一轮可以选择B与C；C不必等待B生成结束。但C如果是新提示，首先需要[[预填充]]，并不是加入批次就已经变成decode请求。

<!-- bilingual-en:start -->
Using the A/B/C example from [[静态批处理|static batching]], A finishes after one shared iteration while B continues and C waits. The next iteration may select B and C, without waiting for B to finish. If C is a new prompt, it still needs [[预填充|prefill]]; admission does not make its prefill disappear.
<!-- bilingual-en:end -->

这种方式要求执行器能处理不同进度与长度的请求，调度器还要检查token预算、[[KV缓存容量|KV状态需求]]及实际可分配内存。它提供“下一轮可以考虑C”的机会，不承诺所有新请求都在一轮以内启动。

<!-- bilingual-en:start -->
The engine must support requests at different lengths and progress, while the scheduler checks token budgets, [[KV缓存容量|KV-state requirements]], and allocatable memory. The mechanism allows C to be considered in the next iteration; it does not promise admission within one iteration for every arrival.
<!-- bilingual-en:end -->

## 更细调度仍需处理长 prefill 干扰

<!-- bilingual-en:start -->
*Finer scheduling still needs to manage long-prefill interference*
<!-- bilingual-en:end -->

连续批处理可以消除“等待当前整批完成”这一额外等待来源；排队并不是它固有增加的代价。实际负载超过容量时仍会排队。若新请求带来很长的prefill，无论单独插入还是与decode混合执行，都可能拉长已有请求下一token的等待，表现为[[Token间隔]]变大。

<!-- bilingual-en:start -->
Continuous batching can remove the extra wait for an entire batch to finish; adding queueing is not inherent to the mechanism. Overload still creates queues. A long new prefill, whether inserted separately or combined with decode, can increase the wait for an existing request's next token and thus its [[Token间隔|inter-token latency]].
<!-- bilingual-en:end -->

[[分块预填充]]提供限制每次prefill工作量的办法；选择多大批次、给谁优先级则是调度策略。连续批处理的定义本身不保证吞吐和每条请求延迟同时改善。

<!-- bilingual-en:start -->
[[分块预填充|Chunked prefill]] provides a way to bound prefill work per iteration. Batch size and request priority remain scheduling-policy decisions. Continuous batching alone does not guarantee simultaneous improvement in throughput and every request's latency.
<!-- bilingual-en:end -->
