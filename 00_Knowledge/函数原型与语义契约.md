# 函数原型让编译器按参数与返回类型检查调用但不表达全部语义契约
<!-- bilingual-en:start -->
*A function prototype enables type-based call checking but does not express the whole semantic contract*
<!-- bilingual-en:end -->

> [!summary] 原子边界
> 函数原型声明函数的返回类型以及参数个数和类型，使编译器能在调用点执行规定的转换并诊断类型不兼容。普通指针形参不能表达数组真实长度、指针非空、数值范围、所有权或“调用后谁释放”等完整语义前置条件；数组形参的 `static N` 可以表达有限的最小可访问元素契约，但仍不携带实际长度，也不提供自动运行时检查。
> <!-- bilingual-en:start -->
>
> &nbsp;
> A function prototype declares the return type and the number and types of parameters, allowing the compiler to apply required conversions and diagnose incompatible calls. An ordinary pointer parameter cannot express an array's actual length, pointer non-nullness, numeric ranges, ownership, or who releases a resource after the call. An array parameter written with `static N` can state a limited minimum-access contract, but it still carries no actual length and adds no automatic run-time check.
> <!-- bilingual-en:end -->

```c
double mean(const int values[], size_t n);
```

这个原型能让实现诊断把结构体直接当成第一个参数的类型不兼容，却不能证明 `values` 至少包含 `n` 个可读元素，也不能决定 `n == 0` 应返回什么。后两项必须由接口文档、调用方验证和函数实现共同守住；诊断要求也不等于实现必须停止生成输出。
<!-- bilingual-en:start -->
This prototype lets the implementation diagnose the incompatible type produced by passing a structure as the first argument, but it cannot prove that `values` names at least `n` readable elements or decide what `n == 0` should mean. Those conditions must be maintained by interface documentation, caller validation, and the implementation together; a required diagnostic also does not mean that the implementation must stop producing output.
<!-- bilingual-en:end -->

## 把同一声明交给调用方和实现方

共享函数的原型通常放在头文件中；实现源文件也包含同一头文件。这样，调用方按同一接口检查，编译器也能比较函数定义与既有声明。复制粘贴两份独立声明会留下悄悄漂移的机会。

在 C17 及更早规则下，声明 `int next();` 的空列表不提供参数个数或类型信息；`int next(void);` 才是“不接收参数”的原型。旧式定义 `int next() { ... }` 的确声明该定义没有形参，但它仍不会让函数类型带上原型；后续错误实参可能逃过调用点约束，并在实际调用时产生未定义行为。C23 则规定每个函数声明符都提供原型，空参数列表按 `void` 列表处理，并移除了旧式标识符列表定义。`void` 写法仍能让跨标准意图一眼可见，读旧代码时必须先确认采用的语言版本。
<!-- bilingual-en:start -->
A shared function prototype normally lives in a header, and the implementation source includes that same header. Callers are checked against one interface, while the compiler can also compare the function definition with the prior declaration. Copying independent declarations leaves room for silent drift.

Under C17 and earlier rules, the empty list in the declaration `int next();` supplies no information about parameter count or types; `int next(void);` is the no-parameter prototype. An old-style definition `int next() { ... }` does declare a definition with no parameters, but its function type still lacks a prototype; a later bad argument list can escape call-site constraints and cause undefined behaviour if the call executes. C23 instead makes every function declarator provide a prototype, treats an empty parameter list as a `void` list, and removes old-style identifier-list definitions. The `void` spelling remains immediately clear across versions, so establish the selected C version when reading older code.
<!-- bilingual-en:end -->

> [!question]- 自检
> `double mean(const int *, size_t);` 已通过编译，为什么调用 `mean(NULL, 10)` 仍可能出错？
>
> **答案：** 这个普通指针原型只检查类型；`NULL` 可转换为所需指针类型，但“非空且至少有 10 个元素”没有由该形参声明表达。若改用数组形参 `static 10`，可以表达最低可访问元素数，仍不会自动执行边界检查。

## 来源与核验

- [ISO C11 committee draft N1570, 6.5.2.2, 6.7.6.3 and 6.9.1](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)：核对有原型调用、函数声明符与定义的一致性。
- [WG14 N3096, C23 draft, 6.7.6.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n3096.pdf)：核对 C23 对空参数列表的版本变化。
- [WG14 Defect Report 317](https://www.open-std.org/jtc1/sc22/wg14/www/docs/dr_317.htm)：核对 C17 及更早版本中空列表函数定义不产生原型的边界。
<!-- bilingual-en:start -->
- [ISO C11 committee draft N1570, 6.5.2.2, 6.7.6.3, and 6.9.1](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf) was checked for prototyped calls, function declarators, and consistency with definitions.
- [WG14 N3096, C23 draft, 6.7.6.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n3096.pdf) was checked for the C23 version change to empty parameter lists.
- [WG14 Defect Report 317](https://www.open-std.org/jtc1/sc22/wg14/www/docs/dr_317.htm) was checked for the C17-and-earlier boundary that an empty-list function definition does not provide a prototype.
