# 分块预填充把一个提示分成依次处理的片段并让后片段读取前片段的 KV 状态

<!-- bilingual-en:start -->
*Chunked prefill processes a prompt in successive chunks whose later chunks read earlier chunks' KV state*
<!-- bilingual-en:end -->

**分块预填充**（chunked prefill）将一条提示的[[预填充]]拆成多个先后执行的片段。前片段计算出的 [[KV cache]] 留给后片段读取，后片段内部继续遵守因果可见性。因此它拆的是执行工作量，没有把一条提示变成彼此独立的短文档。

<!-- bilingual-en:start -->
**Chunked prefill** divides one prompt's [[预填充|prefill]] across successive execution chunks. Earlier chunks leave a [[KV cache|KV cache]] for later chunks to read, while visibility within later chunks remains causal. It partitions execution work without turning the prompt into independent short documents.
<!-- bilingual-en:end -->

## 八个输入分两段仍是一条上下文

<!-- bilingual-en:start -->
*Two chunks of eight inputs still form one context*
<!-- bilingual-en:end -->

假设提示有8个token，先处理位置1–4并保存KV，再处理5–8。第二段位置5可以读取位置1–5；位置8可以读取1–8。[[因果注意力掩码]]仍按完整逻辑位置生效。普通next-token生成须处理到提示最后位置8，才得到整个提示之后的首输出分布；第一片段末尾的分布预测的是位置5，不应误当作完整提示的回答。

<!-- bilingual-en:start -->
For an eight-token prompt, process positions 1–4 and save their KV, then process positions 5–8. Position 5 can read 1–5, and position 8 can read 1–8. The [[因果注意力掩码|causal mask]] follows full logical positions. Ordinary generation needs the final prompt position, 8, before predicting the first output after the complete prompt. The first chunk's final distribution predicts position 5 rather than the answer to the full prompt.
<!-- bilingual-en:end -->

## 切块让已有 decode 获得穿插机会

<!-- bilingual-en:start -->
*Chunking creates opportunities to interleave ongoing decodes*
<!-- bilingual-en:end -->

再加入两个正在decode的请求A、B，设每轮最多处理6个新输入token。在满足实际内存与调度条件时，可以把“4个prefill token + A的1个decode token + B的1个decode token”排为一轮；下一轮再处理余下4个prefill token并继续A/B。

<!-- bilingual-en:start -->
Now add ongoing decode requests A and B, with a budget of six new input tokens per iteration. When memory and scheduling conditions permit, one iteration can contain four prefill tokens plus one decode input from each of A and B. The next iteration handles the remaining four prefill tokens while advancing A and B again.
<!-- bilingual-en:end -->

这样可以限制单轮长prefill对已有请求[[Token间隔]]的影响。Sarathi-Serve的具体策略是先放ongoing decode，再放已有未完成prefill，最后在剩余token预算中接纳新请求。仅把prefill切块，并不自动保证每一轮都让decode运行；还需要相应的[[连续批处理|迭代调度]]规则。

<!-- bilingual-en:start -->
This limits the impact of one long prefill iteration on existing requests' [[Token间隔|inter-token latency]]. Sarathi-Serve first packs ongoing decodes, then unfinished prefills, and finally new requests within the remaining budget. Chunking alone does not guarantee that decodes run each iteration; the [[连续批处理|iteration-level scheduling]] policy must provide that behavior.
<!-- bilingual-en:end -->

## 较小片段也会付出额外成本

<!-- bilingual-en:start -->
*Smaller chunks also incur costs*
<!-- bilingual-en:end -->

片段越小，每轮prefill工作量越容易控制，但可能降低矩阵运算效率，并增加kernel启动、通信与重复读取历史KV的开销。例如3个连续片段中，第1段KV在处理第2与第3段时都要再次可用，第2段KV也要供第3段读取；切块不消除这些跨片段依赖。

<!-- bilingual-en:start -->
Smaller chunks make per-iteration prefill work easier to bound but may reduce matrix-operation efficiency and increase kernel launches, communication, and repeated historical-KV reads. With three successive chunks, chunk 1's KV is needed again for chunks 2 and 3, and chunk 2's KV is needed for chunk 3. Chunking does not remove those dependencies.
<!-- bilingual-en:end -->

因此应同时观察已有请求ITL与新请求[[首Token延迟]]。Sarathi所称stall-free侧重避免跳过已有decode来执行长prefill，不表示加入prefill后每轮完全没有额外耗时；最合适的片段大小取决于模型、设备、负载与延迟目标。

<!-- bilingual-en:start -->
Measure existing requests' ITL alongside new requests' [[首Token延迟|TTFT]]. Sarathi's stall-free scheduling avoids skipping ongoing decodes to run long prefills; it does not mean that adding prefill incurs no extra iteration time. Chunk size depends on the model, hardware, workload, and latency target.
<!-- bilingual-en:end -->
