# 请求构建目标时系统会先递归满足其传递依赖
<!-- bilingual-en:start -->
*When a build target is requested, the system recursively satisfies its transitive dependencies first*
<!-- bilingual-en:end -->

> [!summary] 原子机制
> 构建系统从请求的目标出发，沿先决条件边递归展开：先使叶端输入和中间目标可用，再执行依赖它们的配方，直到得到最终目标。未被该目标传递依赖到的规则通常不需要执行。
> <!-- bilingual-en:start -->
> A build system starts from the requested target and recursively follows prerequisite edges. It makes leaf inputs and intermediate targets available before running recipes that depend on them, continuing until the final target is produced. Rules outside that target's transitive dependency closure normally need not run.
> <!-- bilingual-en:end -->

例如 `paper.pdf` 依赖 `plot-data.png`，而后者又依赖 `data.dat` 与 `plot.py`。请求 `paper.pdf` 时，系统先检查或生成图片，再生成 PDF；若只请求另一个互不相关的目标，这条链不会因为写在同一份 Makefile 里就自动执行。
<!-- bilingual-en:start -->
For example, `paper.pdf` depends on `plot-data.png`, which in turn depends on `data.dat` and `plot.py`. Requesting `paper.pdf` makes the system check or generate the plot before the PDF. An unrelated target is not run merely because its rule appears in the same Makefile.
<!-- bilingual-en:end -->

## 边界

递归解析不等于“系统能猜到所有输入”。叶端文件若既不存在又没有生成规则，GNU Make 会报无法生成目标；真实输入若根本没有出现在图中，则不会被递归发现。
<!-- bilingual-en:start -->
Recursive resolution does not mean the system can infer every input. If a leaf file neither exists nor has a rule that can make it, GNU Make reports that it cannot make the target. A real input omitted from the graph will not be discovered by recursion.
<!-- bilingual-en:end -->

> [!question]- 自检
> 为什么修改 `data.dat` 可能重建图片和 PDF，却不应执行一条与论文无关的 `deploy` 规则？
>
> **答案：** 前两者位于 `paper.pdf` 的传递依赖闭包内；不相关的 `deploy` 不在这条可达路径上。
