# 密封构建隔离宿主机隐式输入但不等同于已经验证可复现
<!-- bilingual-en:start -->
*A hermetic build isolates implicit host inputs but is not the same as a verified reproducible build*
<!-- bilingual-en:end -->

> [!summary] 原子区别
> hermetic build（密封构建）把工具与依赖也当作受控输入，并隔离宿主机已安装的语言、库和系统程序，使结果不随本机偶然状态变化。reproducible build（可复现构建）则是对指定输出的判据：重建后必须逐字节相同。
> <!-- bilingual-en:start -->
> A hermetic build treats tools and dependencies as controlled inputs and isolates the build from languages, libraries, and system programs accidentally installed on the host. A reproducible build is instead an output criterion: specified artifacts must be identical byte for byte when rebuilt.
> <!-- bilingual-en:end -->

密封性通过减少未声明输入来促进缓存、并行执行和可复现性，但“设计上更密封”仍不代替独立重建与产物比较。若规则读取时钟、随机数、网络服务或宿主挂载，即使命令在 container 中运行，也仍可能不密封。
<!-- bilingual-en:start -->
Hermeticity promotes caching, parallel execution, and reproducibility by reducing undeclared inputs, but a more hermetic design does not replace independent rebuilding and artifact comparison. A command running in a container can remain non-hermetic if it reads clocks, randomness, network services, or host mounts.
<!-- bilingual-en:end -->

## 反例

固定 container image 却在构建时下载 URL 的“latest”内容：宿主工具较少泄漏进来，但外部服务仍是浮动输入，不能仅凭“用了 Docker”断言密封或可复现。
<!-- bilingual-en:start -->
A fixed container image that downloads “latest” content during the build leaks less host tooling, yet the external service remains a floating input. “It uses Docker” alone proves neither hermeticity nor reproducibility.
<!-- bilingual-en:end -->

> [!question]- 自检
> 为什么在干净 container 中成功两次，仍不足以证明可复现？
>
> **答案：** 还需明确指定产物并比较其字节；container 内也可能存在时钟、随机数或网络等未控制输入。
