# 泄漏、越界、释放后使用与重复释放是不同的内存契约破坏
<!-- bilingual-en:start -->
*Leaks, out-of-bounds access, use-after-free, and double-free violate different memory contracts*
<!-- bilingual-en:end -->

> [!summary] 先判哪条不变量坏了
> **泄漏（leak）**是仍存活的分配失去可履行释放责任的所有者；**越界（out of bounds）**是在对象仍可能存活时越过其可访问范围；**释放后使用（use-after-free）**是在对象寿命结束后继续使用旧指针；**重复释放（double-free）**是对同一分配再次释放。它们可能同时出现，却不是同一个“内存报错”。
> <!-- bilingual-en:start -->
> A leak leaves a live allocation without an owner able to release it. Out-of-bounds access crosses an object's extent even if the object is still alive. Use-after-free uses an old pointer after lifetime ends. Double-free attempts to release the same allocation again. They may coexist but violate different invariants.
> <!-- bilingual-en:end -->

```c
#include <stdlib.h>

int memory_contract_example(void) {
    int *p = malloc(3 * sizeof *p);
    if (p == NULL) return 1;

    // p[3] = 7;       // 若取消注释：越界，合法元素只有 0、1、2
    free(p);
    // (void) p[0];    // 若取消注释：释放后使用
    // free(p);        // 若取消注释：重复释放
    return 0;
}
```

三行坏操作都特意保持为注释，彼此是独立的反例；这段可执行代码本身只分配并正常释放，不会为了演示错误而真正触发未定义行为。
<!-- bilingual-en:start -->
The three bad operations remain comments and are independent counterexamples. The executable portion only allocates and releases normally, rather than invoking undefined behaviour merely to illustrate it.
<!-- bilingual-en:end -->

若在 `free` 前直接让唯一所有者 `p` 指向别处，原分配仍活着却不可达，形成泄漏。把栈地址、字符串字面量或 `p + 1` 交给 `free` 则是 **invalid free（无效释放）**：参数从一开始就不匹配分配函数返回值。读取尚未初始化的分配内容又是未确定值问题。准确分类决定应修边界、初始化、生命周期还是所有权路径。
<!-- bilingual-en:start -->
Overwriting the sole owner before `free` leaks a still-live allocation. Passing a stack address, literal address, or `p + 1` to `free` is an invalid free because the argument never matched an allocation result. Reading uninitialised allocated storage is another distinct failure. Classification determines whether to repair bounds, initialisation, lifetime, or ownership.
<!-- bilingual-en:end -->

“出现 segmentation fault（段错误）”只是某次运行的症状，不是 C 对未定义行为的保证；同一错误也可能暂时“看起来能跑”、静默破坏数据或在别处崩溃。诊断时为每个指针写四件事更可靠：来源是什么、当前可访问范围多大、谁拥有对象、哪个事件使它失效。
<!-- bilingual-en:start -->
A segmentation fault is one possible run-time symptom, not a guarantee of undefined behaviour. The same bug may appear to work, silently corrupt data, or fail elsewhere. For each pointer, record its origin, accessible extent, owner, and invalidating event.
<!-- bilingual-en:end -->

AddressSanitizer 常能定位越界、释放后使用和某些无效释放；LeakSanitizer 或 Valgrind 能帮助发现泄漏。工具没有报告不能证明程序满足全部契约，报告位置也未必就是根因：例如一次越界写可能到很久以后才表现为释放失败。工具证据最终仍要映射回上述四个问题。
<!-- bilingual-en:start -->
AddressSanitizer can often locate out-of-bounds access, use-after-free, and some invalid frees; LeakSanitizer or Valgrind can expose leaks. A clean run is not proof of every contract, and a report site need not be the root cause. Map tool evidence back to origin, extent, owner, and invalidation.
<!-- bilingual-en:end -->

> [!question]- 最小自检
> 一个动态数组仍可访问且最终会释放，但代码写了 `a[length]`，这首先属于哪类错误？
>
> **答案：** 若 `length` 等于元素个数，它首先是越界；对象是否泄漏或已释放是另外两条独立判断。
