# Python 的封装约定只能标示访问边界而对象不变量必须由每个状态入口维护
<!-- bilingual-en:start -->
*Python encapsulation conventions only mark access boundaries, while every state-changing entry point must preserve object invariants*
<!-- bilingual-en:end -->

> [!summary] 原子不变量边界
> 单下划线把属性标为非公开实现细节，双下划线名称改写主要避免子类命名冲突，`property` 可以集中读写逻辑；它们都不是不可绕过的安全边界。对象正确性来自更强的条件：构造器、方法、setter 以及任何暴露出去的可变成员都必须共同保持同一不变量。
> <!-- bilingual-en:start -->
> A leading underscore marks an attribute as a non-public implementation detail, double-underscore name mangling mainly prevents accidental clashes in subclasses, and a `property` can centralize access logic. None is an unbreakable security boundary. Object correctness comes from a stronger condition: constructors, methods, setters, and any exposed mutable members must all preserve the same invariant.
> <!-- bilingual-en:end -->

```python
class Account:
    def __init__(self, opening_balance=0):
        if opening_balance < 0:
            raise ValueError("negative opening balance")
        self._balance = opening_balance

    @property
    def balance(self):
        return self._balance

    def withdraw(self, amount):
        if amount <= 0 or amount > self._balance:
            raise ValueError("invalid withdrawal")
        self._balance -= amount
```

这里的不变量是 `_balance >= 0`。它直接复用[[不变量原理]]：构造阶段负责初始化成立，每一种允许的状态转移负责保持。只在 `__init__` 检查还不够；只读 `balance` property 也只控制一个入口，不能阻止类内部另一个错误方法写入负数。若把内部可变列表原样返回给调用者，调用者还可能绕过方法修改状态。

缩小公开的状态变更接口可以减少需要审查的不变量保持义务，但不能替代这些义务；任何仍然存在的 setter、方法或可变别名都必须逐项检查。

> [!question]- 回忆与应用
> 为什么把 `_balance` 改成只读 property 后，仍不能据此证明账户永远正确？
>
> **答案：** property 只控制一个访问路径；所有内部 mutator 和暴露的可变别名仍必须保持同一不变量。
