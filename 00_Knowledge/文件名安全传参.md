# 传递任意文件名应保持参数边界或使用NUL分隔而非按空白拆分

Unix 文件名可以包含空格、制表符、换行、引号和通配字符，不能包含 NUL 或作为路径分隔符的 `/`。因此处理任意文件名时，应直接保持“一个名字一个参数”，或用双方都理解的 NUL 分隔协议在字节流与参数之间转换；按空白或换行拆分 `ls` 输出不具备这个保证。
<!-- bilingual-en:start -->
Unix filenames can contain spaces, tabs, newlines, quotes, and wildcard characters, but not NUL or the pathname separator `/`. For arbitrary filenames, preserve one name per argument directly, or use a NUL-delimited protocol understood by both producer and consumer. Splitting `ls` output at whitespace or newlines does not provide that guarantee.
<!-- bilingual-en:end -->

已在 Bash 实参中的名字，用 `"$@"` 转发；单个名字用 `"$path"`。递归查找时，`find … -exec utility … {} +` 直接把查到的路径作为实参交付，不必先序列化成文本。下例只显示练习目录中的文件路径，不修改文件：
<!-- bilingual-en:start -->
Forward existing Bash arguments with `"$@"`, and quote an individual pathname as `"$path"`. For recursive discovery, `find … -exec utility … {} +` passes paths directly as arguments without first serializing them as text. This example only displays file paths from a practice directory:
<!-- bilingual-en:end -->

```bash
find ./samples -type f -exec printf '<%s>\n' {} +
```

需要通过管道交付时，可在支持这些选项的 `find` 与 `xargs` 上配对使用 `-print0` 和 `-0`。默认 `xargs` 会解释空白、引号或反斜杠，不能拿来读取任意原始文件名。空输入是否仍启动一次工具取决于实现与选项，也要核对；直接 `find -exec … {} +` 不会因零个匹配而构造一个空文件名。
<!-- bilingual-en:start -->
For pipeline transfer, pair `find -print0` with `xargs -0` on implementations supporting them. Default `xargs` interprets whitespace, quotes, or backslashes and is unsuitable for arbitrary raw filenames. Whether empty input still invokes a utility depends on implementation and options. Direct `find -exec … {} +` does not invent an empty filename when there are no matches.
<!-- bilingual-en:end -->

保持边界仍不等于所有输入都安全：工具可能把 `-name` 当选项，或把 `x=y` 当特殊操作数。按工具文档使用 `--`，或在合适场景提供 `./name`、绝对路径、输入重定向。NUL 分隔也不能消除查找与后续访问之间的文件变动风险；不要把“正确传参”当作任意破坏性批处理的授权。
<!-- bilingual-en:start -->
Preserved boundaries are not complete input safety: a utility may treat `-name` as an option or `x=y` as a special operand. Use documented `--` handling, or appropriate `./name`/absolute paths or input redirection. NUL separation also does not remove changes between discovery and later access. Correct argument passing does not authorize arbitrary destructive batch actions.
<!-- bilingual-en:end -->

## 来源与核验

- 本机 `find(1)`，`-exec … {} +` 与 `-print0`；`xargs(1)`，`DESCRIPTION`、`-0` 与 `-r`：支持直接参数交付、NUL 协议、默认再解析和空输入的实现差异。
- [POSIX.1-2024 §3.146 Filename](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap03.html#tag_03_146)：支持文件名中的 NUL 与斜杠限制；[Missing Semester Shell Tools 练习 4](https://missing.csail.mit.edu/2020/shell-tools/) 支持 stdin 转参数和 macOS `-print0`/`-0` 的课程需求。
- GNU Bash 3.2 本机 `bash(1)`，`Special Parameters` 与 `QUOTING`：支持 `"$@"` 和单参数引用；工具的选项及特殊操作数仍须按各自接口解释。
- [GNU Findutils §11.3 Security Considerations for xargs](https://www.gnu.org/software/findutils/manual/html_node/find_html/Security-Considerations-for-xargs.html)：支持默认 xargs 对空白和引号的重新解释，以及 NUL 协议不能排除文件系统竞争的边界。
<!-- bilingual-en:start -->
The local `find` and `xargs` manuals support direct argument delivery, NUL transfer, default reparsing, and empty-input differences. POSIX defines filename byte restrictions; the course exercise motivates stdin-to-argument conversion and the macOS options. The local Bash manual supports quoted forwarding, while utility-specific interpretation remains a separate contract. GNU Findutils §11.3 supports both the default parsing risk and the remaining filesystem-race boundary with NUL transfer.
<!-- bilingual-en:end -->
