# 语义化版本把公开 API 的兼容性承诺编码进主次补丁号
<!-- bilingual-en:start -->
*Semantic Versioning encodes public-API compatibility promises in major, minor, and patch numbers*
<!-- bilingual-en:end -->

> [!summary] 原子模型
> 在 Semantic Versioning 2.0.0 中，版本写成 `MAJOR.MINOR.PATCH`：公开 API 出现不兼容变更时增加 major；增加向后兼容的公开功能时增加 minor；只做向后兼容的 bug fix 时增加 patch。
> <!-- bilingual-en:start -->
> Under Semantic Versioning 2.0.0, a version is `MAJOR.MINOR.PATCH`: incompatible public-API changes increment major, backward-compatible public functionality increments minor, and backward-compatible bug fixes increment patch.
> <!-- bilingual-en:end -->

这套语义成立的前提是项目声明了清楚的公开 API，并按规范发布不可变版本。版本号传递的是维护者对兼容性的承诺，依赖方仍应通过测试验证升级后的真实行为。
<!-- bilingual-en:start -->
The scheme presupposes a clearly declared public API and immutable released versions. A version number communicates the maintainer's compatibility promise; dependants should still test the actual behaviour after an upgrade.
<!-- bilingual-en:end -->

## 边界

`0.y.z` 表示初始开发，规范明确允许任何内容随时变化，因此不能套用“同一 major 就稳定兼容”的普通直觉。预发布版本也可能不满足其对应正式版本的兼容性要求。SemVer 定义版本含义，却不定义每个包管理器的版本范围语法。
<!-- bilingual-en:start -->
`0.y.z` denotes initial development, where the specification allows anything to change at any time, so the ordinary intuition that one major version is stable does not apply. Pre-release versions may also fail the compatibility requirements of the associated normal version. SemVer defines version meaning, not each package manager's range syntax.
<!-- bilingual-en:end -->

> [!question]- 自检
> 某库把公开函数改名且不保留兼容入口，在已经发布 1.4.2 后按 SemVer 应改哪一段？
>
> **答案：** 这是公开 API 的不兼容变更，应增加 major，成为 2.0.0 系列。
