# 数据库事务、约束与索引
<!-- bilingual-en:start -->
*Database Transactions, Constraints, and Indexes*
<!-- bilingual-en:end -->

> [!summary] 快速恢复
> **它解决什么：** 在并发写入和系统失败下维护数据规则，并让真实查询以可接受成本执行。
> **具体锚点：** 两个请求都先读到库存 1，再各自扣减，若没有事务隔离或原子更新就可能卖出 2 件。
> **核心难点：** 应用层检查与数据库约束面对的并发边界不同；索引改善特定读取，却会增加写入和存储成本。
> **为什么重要：** 单次查询正确不等于系统状态始终正确，单次快速也不等于整体工作负载最优。
> **继续：** 先把不变量写成约束和事务边界，再用真实 query plan 决定索引。
> <!-- bilingual-en:start -->
> **Problem addressed:** Preserve data rules under concurrent writes and failures, while executing real queries at acceptable cost.
> **Concrete anchor:** Two requests can both read inventory as one and each decrement it, selling two units unless isolation or an atomic update protects the invariant.
> **Central difficulty:** An application check and a database constraint operate at different concurrency boundaries; an index accelerates particular reads while increasing storage and write cost.
> **Why it matters:** A correct individual query does not ensure that system state remains valid, and one fast lookup does not imply an optimal workload.
> **Continue with:** Express invariants as constraints and transaction boundaries, then choose indexes from measured query plans.
> <!-- bilingual-en:end -->

## 事务与并发
<!-- bilingual-en:start -->
*Transactions and Concurrency*
<!-- bilingual-en:end -->

事务把更新作为原子单元，ACID 涵盖原子、一致、隔离、持久。隔离级别权衡并发与脏读/不可重复读/幻读；约束放数据库可防所有写入路径破坏规则。
<!-- bilingual-en:start -->
A transaction treats updates as an atomic unit. ACID covers atomicity, consistency, isolation, and durability. Isolation levels trade concurrency against dirty reads, nonrepeatable reads, and phantoms; a database constraint protects the rule across every write path.
<!-- bilingual-en:end -->

“一致性”不是数据库自动理解所有业务，而是事务从一个满足已声明规则的状态转到另一个满足规则的状态。未写成约束或事务逻辑的业务条件不会凭空得到保护。
<!-- bilingual-en:start -->
“Consistency” does not mean that a database automatically understands every business rule. It means that a transaction moves between states satisfying the declared rules. A condition absent from constraints or transaction logic receives no automatic protection.
<!-- bilingual-en:end -->

## 约束是共同写入边界
<!-- bilingual-en:start -->
*Constraints as the Shared Write Boundary*
<!-- bilingual-en:end -->

`NOT NULL`、`CHECK`、`UNIQUE`、主键和外键分别表达缺失、域、唯一与参照规则。应用仍应给用户友好验证，但数据库约束负责抵御并发和旁路写入。
<!-- bilingual-en:start -->
`NOT NULL`, `CHECK`, `UNIQUE`, primary keys, and foreign keys express missing-value, domain, uniqueness, and referential rules. The application should still provide friendly validation, while database constraints defend against concurrent and bypass writes.
<!-- bilingual-en:end -->

## 索引与计划
<!-- bilingual-en:start -->
*Indexes and Query Plans*
<!-- bilingual-en:end -->

索引加速特定查找/排序但增加存储和写成本。使用 query plan 检查扫描、连接顺序和估计；先建正确查询，再针对真实瓶颈加最小索引。
<!-- bilingual-en:start -->
An index accelerates particular lookups or orderings but adds storage and write cost. Use the query plan to inspect scans, join order, and estimates; make the query correct first, then add the smallest index that addresses a measured bottleneck.
<!-- bilingual-en:end -->

复合索引是否有用取决于列顺序、过滤条件、排序和选择性。只看到“WHERE 中出现该列”就加索引，可能生成从未使用的结构并拖慢所有写入。
<!-- bilingual-en:start -->
The usefulness of a composite index depends on column order, predicates, ordering, and selectivity. Adding an index merely because a column appears in WHERE can create an unused structure that slows every write.
<!-- bilingual-en:end -->

## Worked example：原子扣减库存
<!-- bilingual-en:start -->
*Worked Example: Decrement Inventory Atomically*
<!-- bilingual-en:end -->

把“库存必须为正”和扣减写进一条语句，让数据库只在条件仍成立时更新；检查受影响行数判断成功。这样避免“先 SELECT、后 UPDATE”之间的竞态窗口。
<!-- bilingual-en:start -->
Put the positive-inventory condition and decrement in one statement so that the database updates only while the condition remains true; inspect the affected-row count to determine success. This removes the race window between a separate SELECT and UPDATE.
<!-- bilingual-en:end -->

```sql
UPDATE products
SET stock = stock - 1
WHERE product_id = 42
  AND stock > 0;
```

## 失败诊断
<!-- bilingual-en:start -->
*Failure Diagnosis*
<!-- bilingual-en:end -->

- 本地测试不重复、生产出现重复：检查唯一性是否只在应用中查询后判断，而未建立数据库 `UNIQUE` 约束。
  <!-- bilingual-en:start -->
  Duplicates appear only in production: check whether uniqueness is enforced by an application check without a database `UNIQUE` constraint.
  <!-- bilingual-en:end -->
- 加索引后仍慢：查看实际计划、返回行数与估计偏差，确认谓词、类型转换和列顺序是否允许使用索引。
  <!-- bilingual-en:start -->
  A query remains slow after indexing: inspect the actual plan, row counts, and estimation error, then check whether predicates, type conversions, and column order permit index use.
  <!-- bilingual-en:end -->
- 事务偶发死锁：确保资源访问顺序一致，缩短事务，并实现能识别死锁的有限重试。
  <!-- bilingual-en:start -->
  Transactions occasionally deadlock: acquire resources in a consistent order, shorten transactions, and implement bounded retries that recognize deadlock errors.
  <!-- bilingual-en:end -->

## 最小自检
<!-- bilingual-en:start -->
*Minimum Self-Check*
<!-- bilingual-en:end -->

### 为什么业务唯一性应有数据库约束？
<!-- bilingual-en:start -->
*Why should business uniqueness have a database constraint?*
<!-- bilingual-en:end -->

> [!answer]- 答案
> 应用可能有多个写入路径或并发，数据库约束在共同边界阻止所有路径产生重复/非法状态。
<!-- bilingual-en:start -->
> [!answer]- Answer
> An application can have multiple or concurrent write paths; a database constraint blocks duplicate or invalid states at their common boundary.
<!-- bilingual-en:end -->

### 为什么“先查库存，再扣库存”仍会超卖？
<!-- bilingual-en:start -->
*Why can “check stock, then decrement stock” still oversell?*
<!-- bilingual-en:end -->

> [!answer]- 答案
> 两个事务可在任一扣减前都读到相同旧值；需要原子条件更新、锁或合适隔离来串行化冲突。
<!-- bilingual-en:start -->
> [!answer]- Answer
> Two transactions can both read the same old value before either decrements it; an atomic conditional update, lock, or suitable isolation is needed to serialize the conflict.
<!-- bilingual-en:end -->

### 为什么不应给每个 WHERE 列都建索引？
<!-- bilingual-en:start -->
*Why should every column appearing in WHERE not automatically receive an index?*
<!-- bilingual-en:end -->

> [!answer]- 答案
> 索引有写入与存储成本，低选择性或不匹配查询形状时也可能不用；应从实际工作负载和计划验证。
<!-- bilingual-en:start -->
> [!answer]- Answer
> An index has write and storage costs and may be ignored when selectivity is low or its shape does not match the query; validate it against the actual workload and plan.
<!-- bilingual-en:end -->
