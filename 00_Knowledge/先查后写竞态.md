# 先检查再写入会在两条语句之间留下并发竞态窗口

<!-- bilingual-en:start -->
*Check-then-write leaves a concurrency race between statements*
<!-- bilingual-en:end -->

> [!summary] 原子定义
> 当程序先 `SELECT` 判断条件，再用另一条语句写入时，条件在两条语句之间可能已被并发事务改变。两个请求都基于同一个旧状态通过检查，不代表两次写入合在一起仍满足不变量；这就是 check-then-act race。
>
> <!-- bilingual-en:start -->
> When a program first checks a condition with `SELECT` and writes in a later statement, a concurrent transaction can change that condition between the two. Two requests can both pass based on the same old state even though their combined writes violate the invariant. This is a check-then-act race.
> <!-- bilingual-en:end -->

## 自然解释

库存为 1 时，请求 A、B 都先读到 1。A 扣减为 0；B 若随后无条件用自己读到的旧值扣减，就可能覆盖、超卖或写成负数，具体形态取决于更新表达式和隔离级别。问题不在 `SELECT` 算错，而在“检查仍成立”没有与写入处于同一并发判定点。

<!-- bilingual-en:start -->
With stock 1, requests A and B both read 1. A decrements to 0; if B later writes unconditionally from its stale observation, it can overwrite, oversell, or produce a negative value depending on the update expression and isolation level. The `SELECT` was not numerically wrong; the check was not tied to the write at one concurrency decision point.
<!-- bilingual-en:end -->

常见修法有三类：让数据库 constraint 拒绝坏状态；把局部条件与写入合成[[条件更新|一条原子 conditional update]]；或显式锁住能代表该业务资源的既有行，并在锁内重查。普通 row lock 锁不到“目前不存在的行”或任意谓词范围；这类不存在性规则通常要用 unique/partial unique index、在确有必要时锁表，或用 Serializable 加完整事务重试。

<!-- bilingual-en:start -->
Three common remedies are: encode a database constraint that rejects the bad state; combine a local condition and write into [[条件更新|one atomic conditional update]]; or lock an existing row that represents the business resource and recheck while holding it. An ordinary row lock cannot lock a currently absent row or an arbitrary predicate range; absence rules usually need a unique or partial unique index, a table lock when justified, or Serializable isolation with whole-transaction retries.
<!-- bilingual-en:end -->

> [!warning] 边界
> 把两条语句简单包进默认隔离事务，不一定消除竞态。事务给出原子提交边界，但并不自动让先前读取在写入时仍为真。
>
> <!-- bilingual-en:start -->
> Merely wrapping the two statements in a default-isolation transaction does not necessarily remove the race. A transaction provides an atomic commit boundary, but it does not make an earlier observation remain true at write time.
> <!-- bilingual-en:end -->

> [!question]- 回忆与应用
> 两个并发请求都先确认用户名不存在，再分别插入。为什么应用层检查不足？
>
> **答案：** 两次检查都可在任一插入前完成；最终唯一性应由数据库 `UNIQUE` 约束共同裁决，应用检查只负责更早、更友好的反馈。

## 来源与核验

- PostgreSQL 18, [*Read Committed Isolation Level*](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)：说明逐语句 snapshot 与并发写入行为，构成 separated check/write 的竞态基础。
- PostgreSQL 18, [*Constraints*](https://www.postgresql.org/docs/current/ddl-constraints.html)：说明数据库约束作为最终合法性判定。
- PostgreSQL 18, [*Data Consistency Checks at the Application Level*](https://www.postgresql.org/docs/current/applevel-consistency.html)：区分 Serializable、显式行锁与需要表锁才能覆盖的谓词范围。
