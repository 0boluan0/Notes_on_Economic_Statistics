# Parallel pseudorandom streams
<!-- bilingual-en:end -->

*并行伪随机子流*

<!-- bilingual-en:start -->
Parallel simulation divides work among workers, such as processes or machines. Each worker needs random inputs, but giving every worker the same starting state can make them repeat the same work. **Parallel random streams** are a deliberate allocation of generator states or indexed outputs to tasks, so the intended separate simulations use separately constructed inputs and can still be replayed.
<!-- bilingual-en:end -->

并行模拟把工作分给多个 worker，例如进程或机器。每个 worker 都需要随机输入，但给它们相同起始状态，可能让它们重复相同工作。**并行随机流**是把生成器状态或带索引的输出有计划地分配给任务，使本应分开的模拟使用分别构造的输入，并且仍能重放。

<!-- bilingual-en:start -->
A [[伪随机数生成器|PRNG]] advances deterministically from its state. A stream is its ordered output; a **substream** is a designated part or derived stream assigned to one purpose. Different numerical outputs are not a definition of [[随机变量独立|independence]], and two valid streams can occasionally output the same number. What matters is the construction and the joint behaviour required by the simulation.
<!-- bilingual-en:end -->

[[伪随机数生成器]]从状态确定性地向前推进。一条流是有序输出；**子流**是为某个用途划定的一段或派生出来的流。数值不同不是[[随机变量独立|独立性]]的定义，合适的两条流偶尔也可能输出同一个数字。关键是构造方式，以及模拟所需要的联合行为。

> [!example] Twenty copies are still one batch · 复制二十次仍是一批
> <!-- bilingual-en:start -->
> Suppose 20 workers all start `random.Random(42)` and execute the same calls for 5,000 paths. They produce 100,000 stored paths but only repeat the original 5,000-path batch. Their grand average is exactly the original batch average.
>
> In the ideal model where the original 5,000 scalar outputs are iid with finite variance $\sigma^2$, that average has variance $\sigma^2/5000$. Treating all copies as iid would instead use $\sigma^2/100000$, a factor of $20$ too small, and a standard error smaller by $\sqrt{20}$. The [[Monte Carlo均值标准误|iid mean standard-error formula]] counts independent information, not duplicated rows. These formulas describe the ideal sampling model; repeating deterministic files creates no new random experiment.
> <!-- bilingual-en:end -->
>
> 设20个 worker 都执行 `random.Random(42)`，再按完全相同的调用生成5,000条路径。虽然存下100,000条路径，其实只是把原来的5,000条复制20次；总平均值恰等于原批次平均值。
>
> 若把原来的5,000个标量输出建模为 iid，单次方差为有限的 $\sigma^2$，平均值方差为 $\sigma^2/5000$。误把全部副本当 iid，就会使用 $\sigma^2/100000$，把方差缩小20倍、标准误缩小 $\sqrt{20}$ 倍。[[Monte Carlo均值标准误|iid 均值标准误公式]]计算的是独立信息，不是重复行数。这些公式描述理想抽样模型；重复确定文件不会新增随机实验。

## Derive streams with an explicit construction
<!-- bilingual-en:end -->

*通过明确构造派生随机流*

<!-- bilingual-en:start -->
One supported NumPy route is a `SeedSequence` tree. The root holds recorded initialisation information; `spawn` combines it with each child’s position in the tree. Each child then initialises its own bit generator. The following example names `PCG64` explicitly, rather than leaving the algorithm to a changing default:
<!-- bilingual-en:end -->

NumPy 支持的一条路径是 `SeedSequence` 树：根保存有记录的初始化信息，`spawn` 把它与每个子节点在树中的位置混合，再用各子节点初始化独立保存状态的底层生成器。下面明确写出 `PCG64`，没有把算法留给可能改变的默认值：

```python
from numpy.random import Generator, PCG64, SeedSequence

root = SeedSequence(20261029)
children = root.spawn(3)
streams = [Generator(PCG64(child)) for child in children]

# Assign streams[0], streams[1], streams[2] to stable task IDs.
```

<!-- bilingual-en:start -->
Here the three child paths are `(0,)`, `(1,)` and `(2,)`. Creating a fresh root with the same input and repeating the same spawn protocol reproduces them. Calling `spawn(3)` again on the existing root instead allocates the next children; resetting the root in each worker would recreate child `(0,)` unless allocation is coordinated. Record the root information, child path, generator and task identity, following [[伪随机复现|the replay protocol]].
<!-- bilingual-en:end -->

这里三个子节点路径分别为 `(0,)`、`(1,)`、`(2,)`。重新创建相同根并重做相同派生协议，可以重放；在现有根上再调用 `spawn(3)`，则分配后续子节点。若每个 worker 都重置根、只取第一个子节点，就会重复 `(0,)`，所以必须明确分配。应按[[伪随机复现|重放协议]]记录根信息、子路径、生成算法和任务身份。

<!-- bilingual-en:start -->
NumPy describes spawning as giving independent, very probably non-overlapping streams through its mixing and collision analysis. This is a documented generator construction, not a proof that all finite-state outputs are ideal iid continuous draws. There is no universal guarantee obtained merely by seeing different seeds, and no equality test on a short output sample can certify independence.
<!-- bilingual-en:end -->

NumPy 用混合机制和碰撞分析支持派生流的独立性及极高概率下不重叠的性质。这是有文档的生成器构造，不是证明有限状态输出就是理想的 iid 连续随机数。单看种子不同没有普适保证，比较一小段输出是否相等也不能认证独立性。

## Other constructions have their own bookkeeping
<!-- bilingual-en:end -->

*其他构造有各自的记录要求*

<!-- bilingual-en:start -->
Another supported NumPy scheme combines a unique stable nonnegative task ID and the root seed as separate integers, such as `SeedSequence([task_id, root_seed])`. Keeping them separate avoids the collisions created by adding them. For example, root `100` with worker IDs `0,1,2` gives seeds `100,101,102`; root `101` on a repeat run gives `101,102,103`. Two worker streams are now reused across runs even though seeds within each run differ. This overlap invalidates treating those repetitions as new independent information; it need not change the marginal mean of each output.
<!-- bilingual-en:end -->

NumPy 还支持把唯一、稳定、非负的任务 ID 与根种子作为分开的整数输入，例如 `SeedSequence([task_id, root_seed])`。分开记录可避免直接相加造成的碰撞。例如根为 `100`、worker ID 为 `0,1,2`，相加得到 `100,101,102`；下一次把根改为 `101`，得到 `101,102,103`。每次内部种子虽不同，跨运行却重复了两条流。这样的重复不能算新增独立信息，但不一定改变每个输出的边际均值。

<!-- bilingual-en:start -->
A **jump-ahead** method moves a supported bit generator by a specified number of state steps. Allocate distinct blocks and keep consumption within the documented block separation, without reusing a block or wrapping into one already assigned. Count the engine’s steps, not merely the number of high-level distribution calls, which may consume a variable amount of state. For a counter-based generator such as Philox, unique supported keys and counters identify the outputs; keys or task IDs must not be reused accidentally. These are alternatives with specific guarantees, not a universal ranking of methods.
<!-- bilingual-en:end -->

**跳跃推进**（jump-ahead）按指定状态步数推进支持它的底层生成器。应分配不同区段、让消耗量保持在文档规定的区段间隔内，避免重复分配或绕回已用区段。这里计算的是引擎状态步数，不只是高层分布调用次数，因为后者可能消耗不定量的底层状态。Philox 等基于计数器的生成器则由受支持的唯一 key 与计数器定位输出，也必须避免意外复用 key 或任务 ID。这些是具有各自保证的备选构造，不是一份普适的优劣排名。

## Attach randomness to tasks, then verify the mapping
<!-- bilingual-en:end -->

*把随机性绑定任务，再核对映射*

<!-- bilingual-en:start -->
A worker ID can be stable in a fixed execution plan, but it is often a poor identity when the number of workers or scheduling changes. Assign streams to persistent simulation tasks or replication IDs, then let workers execute those tasks. The same task can then receive the same stream when moved to a different worker. Keep result ordering explicit if exact numerical replay matters.
<!-- bilingual-en:end -->

在固定执行方案中，worker ID 可以稳定；但当 worker 数量或调度改变时，它往往不适合作为持久身份。可把流绑定到稳定的模拟任务或重复试验 ID，再让 worker 执行任务。这样，同一个任务换了执行者，仍能获得同一条流；若要求精确数值复现，还须明确结果汇总顺序。

<!-- bilingual-en:start -->
Use small checks to detect accidental root resets, duplicated child paths or reused blocks, and trace which input belongs to which task. Such checks catch implementation mistakes; passing them does not prove every cross-stream dependence property or validate the model. Deliberate within-pair sharing for [[共同随机数|common random numbers]] is different from accidental copying: the intended dependence and the unit counted as an independent replication must be explicit.
<!-- bilingual-en:end -->

可以用小规模检查发现根被意外重置、子路径重复或区段复用，并追踪每个输入属于哪个任务。这能发现实现错误，但检查通过不证明全部跨流依赖性质，也不验证模型。[[共同随机数]]中有意的配对共享，与意外复制不同：要明确预期的依赖关系，以及哪一整个单位才算一次独立重复。

## 来源与核验

<!-- bilingual-en:start -->
- [NumPy, Parallel random number generation](https://numpy.org/doc/stable/reference/random/parallel.html): spawning, separate integer task IDs, Philox keys, jump-ahead blocks and collision/reuse limits. The two-root seed collision and copied-batch variance are directly checked here.
- [NumPy, `SeedSequence`](https://numpy.org/doc/stable/reference/random/bit_generators/generated/numpy.random.SeedSequence.html): entropy, child paths and the stateful child counter used in the reproducible example.
- [NumPy, compatibility policy](https://numpy.org/doc/stable/reference/random/compatibility.html): generator, call protocol and environment needed for exact stream replay.
- [Owen, Chapter 3, §3.2, PDF pp.6–7](https://artowen.su.domains/mc/Ch-unifrng.pdf#page=6): distinct streams by purpose and one substream per replication, including deliberate within-pair restart for common inputs.
<!-- bilingual-en:end -->

- NumPy 并行文档核对派生树、分开的整数任务 ID、Philox key、跳跃区段及碰撞/复用限制；两次运行的种子重叠及复制批次方差在本卡直接核算。
- `SeedSequence` 文档核对初始信息、子路径及已有子节点计数；兼容政策说明精确重放所需的算法、调用协议与环境条件。
- Owen 第3.2节核对按用途分流、按重复试验分配子流，以及为共同输入有意在配对内部重启。
