# 捕获异常应同时收窄可能失败的代码范围与可处理的类型范围

<!-- bilingual-en:start -->
*Exception handling should narrow both the protected code and the types it can meaningfully handle*
<!-- bilingual-en:end -->

设计处理器时先问两件事：哪一步可能产生预期失败，以及本层能对哪类失败作出正确响应。只把那一步放进 `try`，捕获有明确处理办法的具体类型；把成功后的计算放到外面或[[try的else分支|else 分支]]。否则后续代码的同类异常也可能被误认成入口失败。

<!-- bilingual-en:start -->
Ask which operation can produce the expected failure and which failures this layer can handle correctly. Protect that operation, catch the specific types with defined responses, and place subsequent successful computation outside the `try` or in its [[try的else分支|else clause]]. Otherwise, a similar exception from later code can be mistaken for an input failure.
<!-- bilingual-en:end -->

```python
def parse_then_process(text, process):
    try:
        number = int(text)
    except ValueError:
        return "invalid integer"
    else:
        return process(number)
```

若 `process` 自己抛出 `ValueError`，这里会向外传播，而非伪装成整数解析失败。`except Exception` 仍很宽，会覆盖许多编程错误；裸 `except` 更宽，还捕获 `KeyboardInterrupt`、`SystemExit` 等退出信号。顶层记录错误或清理后重抛可以有意采用宽捕获，关键是明确责任与后续动作，而不是“一律禁止”或“一律吞掉”。

<!-- bilingual-en:start -->
A `ValueError` raised by `process` propagates outward instead of masquerading as an integer-parsing failure. `except Exception` remains broad and includes many programming errors; a bare `except` also catches signals such as `KeyboardInterrupt` and `SystemExit`. Broad handling can be deliberate at a logging boundary or before re-raising after cleanup. The issue is explicit responsibility and follow-up action, not an unconditional ban or blanket suppression.
<!-- bilingual-en:end -->
