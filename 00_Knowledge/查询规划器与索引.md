# 查询规划器按估算成本选择扫描路径而不会因索引存在就必用

<!-- bilingual-en:start -->
*The query planner chooses scan paths by estimated cost rather than index existence*
<!-- bilingual-en:end -->

> [!summary] 原子定义
> PostgreSQL planner 构造并比较候选 plan，用统计量估算行数、I/O 与 CPU cost 后选择较低成本路径；复杂多表连接还可能用启发式搜索而非穷举。索引存在只增加一个候选；若预计返回很多行、随机 heap 访问昂贵、谓词不匹配或估算认为 sequential scan 更便宜，planner 可以不用索引。
>
> <!-- bilingual-en:start -->
> The PostgreSQL planner constructs and compares candidate plans, choosing a lower-cost path from estimated row counts, I/O, and CPU costs; complex joins may use heuristic rather than exhaustive search. An index merely adds a candidate. If many rows are expected, random heap access is expensive, predicates do not match, or estimates favour a sequential scan, the planner may ignore the index.
> <!-- bilingual-en:end -->

## 自然解释

一个布尔列 95% 都是 `true`，为它建普通索引后查 `WHERE active=true` 往往仍顺序扫描：沿索引找到几乎全表，再随机访问 heap，并不划算。相反，查稀有的 `false` 可能适合索引，甚至适合 partial index。真正决定是数据分布与查询形状，不是 SQL 中有没有等号。

<!-- bilingual-en:start -->
If 95% of a Boolean column is `true`, a query for `WHERE active=true` may still use a sequential scan after an ordinary index is added. Finding nearly every row through the index and then visiting the heap is not attractive. The rare `false` value may suit an index or partial index. Data distribution and query shape, not the presence of `=`, drive the decision.
<!-- bilingual-en:end -->

估算依赖 `ANALYZE` 收集的统计信息。估计行数严重偏离实际时，join order、join algorithm 和 scan choice 都可能连锁错误；先修统计或表达式可估算性，再盲目添加更多索引，通常更接近根因。

<!-- bilingual-en:start -->
Estimates depend on statistics collected by `ANALYZE`. A large gap between estimated and actual rows can distort join order, join algorithm, and scan choice. Fixing statistics or predicate estimability is often closer to the root cause than blindly adding more indexes.
<!-- bilingual-en:end -->

> [!warning] 边界
> planner cost 是相对估算单位，默认以 sequential page fetch 为基准，不是毫秒预测。调整 cost parameter 可以影响选择，但应先有硬件与计划证据；`enable_seqscan=off` 也只能劝退而不能彻底禁止顺序扫描，适合临时诊断，不是通常的生产修复。
>
> <!-- bilingual-en:start -->
> Planner costs use relative units, conventionally based on a sequential page fetch, rather than predicting milliseconds. Cost parameters can influence choices, but require hardware and plan evidence. `enable_seqscan=off` only discourages sequential scans and cannot suppress them entirely; it is a temporary diagnostic aid, not normally a production fix.
> <!-- bilingual-en:end -->

> [!question]- 回忆与应用
> 新索引建好后查询仍用 Seq Scan，能否直接断言索引失效？
>
> **答案：** 不能。先比较返回比例、谓词与索引形状、统计估算和实际 I/O；顺序扫描可能正是较便宜的正确选择。

## 来源与核验

- PostgreSQL 18, [*Using EXPLAIN*](https://www.postgresql.org/docs/current/using-explain.html)：展示 planner 的 cost、row estimate 及 index/bitmap/sequential scan 选择。
- PostgreSQL 18, [*Planner Statistics*](https://www.postgresql.org/docs/current/planner-stats.html)：说明统计量如何支持选择性与行数估计。
- PostgreSQL 18, [*Query Planning*](https://www.postgresql.org/docs/current/runtime-config-query.html)：说明相对 cost 单位、GEQO 启发式搜索与 `enable_seqscan` 的劝退性质。
