# 锁文件只固定依赖解析结果而不能单独保证构建可复现
<!-- bilingual-en:start -->
*A lockfile fixes dependency resolution but cannot by itself guarantee a reproducible build*
<!-- bilingual-en:end -->

> [!summary] 原子边界
> lockfile 只覆盖包管理器记录的那部分输入。编译器与链接器版本、系统库、目标平台、构建 flags、locale 等环境变量、生成脚本读取的时钟或网络内容，都可能在 lockfile 不变时改变产物。
> <!-- bilingual-en:start -->
> A lockfile covers only the inputs recorded by the package manager. Compiler and linker versions, system libraries, target platform, build flags, environment variables such as locale, and clocks or network content read by generation scripts can all change an artifact while the lockfile remains unchanged.
> <!-- bilingual-en:end -->

所以“有 lockfile”只能支持“依赖解析选择更稳定”这一较窄结论。要讨论整次构建，必须继续识别并控制工具链、配置和其他相关环境属性。
<!-- bilingual-en:start -->
Therefore, “a lockfile exists” supports only the narrower conclusion that dependency selections are more stable. Reasoning about the whole build also requires identifying and controlling toolchains, configuration, and other relevant environmental attributes.
<!-- bilingual-en:end -->

## 反例

两台机器使用同一 `Cargo.lock`，一台调用不同版本的 native C compiler，或 build script 把当前时间写入 binary；二者依赖解析相同，输出仍可不同。
<!-- bilingual-en:start -->
Two machines can use the same `Cargo.lock` while invoking different native C compilers, or while a build script embeds the current time in a binary. Dependency resolution is identical, yet the outputs can differ.
<!-- bilingual-en:end -->

> [!question]- 自检
> lockfile 完全一致但产物 hash 不同，第一步能否直接断言 lockfile 失效？
>
> **答案：** 不能。先比较 lockfile 之外的工具链、平台、flags、环境变量和生成步骤输入。
