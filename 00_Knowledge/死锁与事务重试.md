# 死锁是循环等待而数据库中止一个事务后应用应从头有限重试

<!-- bilingual-en:start -->
*A deadlock is cyclic waiting and the application should retry the aborted transaction from the start*
<!-- bilingual-en:end -->

> [!summary] 原子定义
> deadlock（死锁）发生在事务形成循环等待：A 持有资源 1 等资源 2，B 持有资源 2 等资源 1，双方都无法自行前进。PostgreSQL 检测到循环后会中止其中一个事务解除死锁；应用要丢弃该事务的全部中间结果，并从头做有限、带退避的重试。
>
> <!-- bilingual-en:start -->
> A deadlock occurs when transactions form a wait cycle: A holds resource 1 and waits for 2, while B holds 2 and waits for 1. Neither can progress. PostgreSQL detects the cycle and aborts one transaction to break it. The application must discard that transaction's intermediate results and retry it from the beginning with bounded backoff.
> <!-- bilingual-en:end -->

## 自然解释

最有效的预防是让所有事务按一致顺序访问资源，例如总按较小账户 ID 再较大 ID 加锁。事务短小也减少环形成的时间窗口。但即使设计良好，第三方代码、不同 query plan 或并发维护也可能产生死锁，所以生产路径仍要正确处理 deadlock error。

<!-- bilingual-en:start -->
The strongest preventive rule is a consistent resource order, such as always locking the smaller account ID before the larger one. Short transactions also reduce the window for cycles. Even with good design, third-party code, different plans, or concurrent maintenance can still deadlock, so production code must handle the error correctly.
<!-- bilingual-en:end -->

重试不是无限快速循环。它应限制次数、加入 jittered backoff、记录冲突上下文，并保证事务外副作用不会重复。持续高频死锁说明锁顺序或事务范围需要重构，不能靠重试掩盖。

<!-- bilingual-en:start -->
Retry does not mean an unbounded tight loop. Limit attempts, add jittered backoff, record conflict context, and ensure external effects are not duplicated. Persistent deadlocks indicate that lock order or transaction scope needs redesign; retries should not conceal them.
<!-- bilingual-en:end -->

> [!warning] 边界
> 普通 lock wait 不是 deadlock：若等待图没有环，持锁事务结束后仍能继续。不要用极短 lock timeout 把正常排队误诊为死锁。
>
> <!-- bilingual-en:start -->
> An ordinary lock wait is not a deadlock. Without a cycle, progress resumes when the lock holder ends. An extremely short lock timeout can misclassify normal queuing as deadlock.
> <!-- bilingual-en:end -->

> [!question]- 回忆与应用
> PostgreSQL 因 deadlock 中止事务后，为什么不能从失败语句继续？
>
> **答案：** 整个事务已进入 aborted state，先前读取和写入属于被撤销的并发历史；必须从事务边界重新执行。

## 来源与核验

- PostgreSQL 18, [*Deadlocks*](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-DEADLOCKS)：说明循环等待、自动检测与中止，以及一致锁顺序的预防原则。
- PostgreSQL 18, [*Serialization Failure Handling*](https://www.postgresql.org/docs/current/mvcc-serialization-failure-handling.html)：给出 deadlock 的 SQLSTATE `40P01`，并要求重试完整事务。
