# 哈希表用哈希函数把大键空间压缩到有限槽位

<!-- bilingual-en:start -->
*A hash table uses a hash function to compress a large key universe into finitely many slots*
<!-- bilingual-en:end -->

> [!summary] 原子模型
> 哈希表不为每个可能的键预留一个位置。它先用哈希函数 $h(k)$ 把键 $k$ 映射到较小的槽位集合，再用碰撞处理规则在该位置附近保存或寻找完整条目。
>
> <!-- bilingual-en:start -->
> A hash table does not reserve a position for every possible key. It first maps a key $k$ into a much smaller set of slots using a hash function $h(k)$, then uses a collision-resolution rule to store or find the complete entry at or near that location.
> <!-- bilingual-en:end -->

若键只可能是 $0$ 到 $u-1$ 的整数，直接寻址表可以开出 $u$ 个槽，并把键 $k$ 直接放在槽 $k$。它的定位很快，但当 $u$ 远大于实际条目数 $n$ 时，大部分空间都会空着。哈希表把槽位数缩到与实际规模同阶的 $m$，用

$$
h:U\rightarrow\{0,1,\ldots,m-1\}
$$

完成第一次定位。因此，哈希表节省空间的代价正是：不同键可能落到同一槽，数据结构必须继续处理碰撞。
<!-- bilingual-en:start -->
If keys are integers from $0$ to $u-1$, a direct-access table can allocate $u$ slots and put key $k$ directly in slot $k$. Location is immediate, but most space is wasted when $u$ is much larger than the number of stored entries $n$. A hash table reduces the array to $m$ slots on the scale of the stored data and uses the mapping above for an initial location. The price of that compression is collision handling.
<!-- bilingual-en:end -->

## 哈希函数不是整张哈希表

哈希函数只回答“先看哪个槽”。一张可用的哈希表还需要保存完整键和值、处理碰撞、决定扩容时机，并保证插入、查找和删除遵循同一套规则。只写出 $h(k)$，还没有得到完整的数据结构。
<!-- bilingual-en:start -->
A hash function answers only “which slot should be checked first?” A usable table must also store complete keys and values, resolve collisions, decide when to resize, and make insertion, lookup, and deletion follow compatible rules. Writing down $h(k)$ alone does not define the whole data structure.
<!-- bilingual-en:end -->

> [!question]- 回忆与辨别
> 哈希表为什么不直接为每个可能的键开一个槽？
>
> **答案：** 可能的键空间往往远大于实际条目数。哈希把大键空间压缩到较小数组，以允许碰撞为代价换取空间效率。
