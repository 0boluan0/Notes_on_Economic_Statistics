# Timing and asymptotic analysis
<!-- bilingual-en:end -->

*计时与渐近分析*

<!-- bilingual-en:start -->
**Timing** asks how long a particular run took. **Asymptotic analysis** asks how a specified cost grows as the input becomes large. A stopwatch provides evidence about the run that occurred; an analysis explains a family of inputs under a model. Both are useful when choosing an implementation.
<!-- bilingual-en:end -->

**实测计时**问某次运行用了多久；**渐近分析**问某种规定的成本在输入变大时如何增长。计时器提供已经发生的那次运行的证据，分析则在模型下解释一整类输入。选择实现时，两者都有用。

<!-- bilingual-en:start -->
Timing observes elapsed time for a particular implementation, machine, environment and input. Asymptotic analysis proves growth bounds under a stated [[算法成本模型|cost model]] and input case. They answer different questions and can complement each other; one timing is not a general complexity proof.
<!-- bilingual-en:end -->

实测计时观察某个实现、机器、运行环境和输入上的实际耗时；渐近分析在声明的[[算法成本模型]]与输入情形下证明成本随规模增长的界。二者回答不同问题，可以相互检验与补充，但不能把一次计时当成普遍复杂度证明。

> [!example] A crossover in model costs · 模型成本的交叉点
> <!-- bilingual-en:start -->
> Let the two hypothetical costs be $A(n)=1000n$ and $B(n)=n^2$, measured in the same abstract work units. At $n=100$, their costs are 100000 and 10000; at $n=1000$, both are 1000000; at $n=10000$, they are 10000000 and 100000000. Thus the lower-order function eventually wins, while the higher-order one is smaller below the crossover. These are calculated model counts, not measured seconds.
> <!-- bilingual-en:end -->
>
> 设两个假想成本为 $A(n)=1000n$、$B(n)=n^2$，都用同一种抽象工作单位计量。$n=100$ 时分别为 100000 和 10000；$n=1000$ 时同为 1000000；$n=10000$ 时分别为 10000000 和 100000000。因此低阶函数最终较小，但在交叉点之前，高阶函数反而较小。这些是算出的模型成本，不是实测秒数。

<!-- bilingual-en:start -->
A lower asymptotic order need not be faster at every size. The model costs $1000n$ and $n^2$ illustrate this: the first is larger for $0<n<1000$ but eventually grows more slowly. Actual timings also depend on constants, caching, the interpreter, system load and selected inputs. “Eventually better” does not remove the need to consider practical sizes.
<!-- bilingual-en:end -->

渐近阶较低不保证所有规模上都更快。例如两个模型成本分别为 $1000n$ 和 $n^2$，前者在 $0<n<1000$ 时更大，却最终增长更慢。真实计时还受常数、缓存、解释器、系统负载及所选输入影响；“最终更好”不能省掉实际使用规模。

<!-- bilingual-en:start -->
For example, a search benchmark changes its question if one implementation is timed after input construction while the other includes construction or sorting. Decide the task and timing boundary first, then use comparable input families and repeated runs. If measurements disagree with a model, inspect the implementation, operation costs and finite-size effects. A few data points fitting a curve cannot establish its behaviour for every sufficiently large input.
<!-- bilingual-en:end -->

例如比较搜索速度时，若一个实现从输入准备好之后才计时，另一个却把构造输入或排序也算进去，就已经换了问题。先固定任务与计时边界，再使用可比的输入系列并重复运行。测量若与模型不同，应检查实现、操作成本和有限规模效应。几个点拟合出一条曲线，不能证明它对所有充分大的输入都成立。

<!-- bilingual-en:start -->
Compare implementations using the same task and timing scope, repeated measurements at meaningful sizes and inputs, and a reported environment; then use operation counts to explain trends. Finite measurements can reveal a mismatch between implementation and model, but cannot alone prove a bound for all sufficiently large inputs. A sample mean of repeated timings is not automatically [[平均情况复杂度|average-case complexity]], which requires an input distribution.
<!-- bilingual-en:end -->

比较实现时，应固定要比较的任务与计时范围，在多个有意义的规模和输入上重复测量并报告环境；再用操作计数解释趋势。有限测量可以发现实现或模型不吻合，却不能单独证明所有足够大输入上的界。重复计时的样本均值也不自动等于[[平均情况复杂度]]：后者需要指定输入分布。
