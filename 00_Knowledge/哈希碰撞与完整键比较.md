# 不同键可以有相同哈希值所以查找仍需比较完整键

<!-- bilingual-en:start -->
*Different keys may have the same hash, so lookup must still compare complete keys*
<!-- bilingual-en:end -->

> [!summary] 原子区别
> 哈希值是定位线索，不是键的身份证。两个键落到同一哈希值叫作碰撞；查找抵达相应槽或探测位置后，仍须用键相等比较确认找到的是目标键。
>
> <!-- bilingual-en:start -->
> A hash value is a location hint, not a key's identity. When two keys share a hash value they collide; after reaching the relevant bucket or probe position, lookup must still test key equality.
> <!-- bilingual-en:end -->

当可能的键多于槽位时，鸽巢原理保证至少有两个键被映射到同一槽。因此，“设计一个永不碰撞的普通哈希函数”通常不是合理目标。正确目标是让碰撞可处理，并使实际数据上的碰撞分布足够温和。
<!-- bilingual-en:start -->
When the key universe is larger than the slot set, the pigeonhole principle guarantees that at least two keys map to the same slot. An ordinary hash table therefore should not aim for an impossible universal absence of collisions. It should handle collisions correctly and keep their distribution manageable for the keys it actually receives.
<!-- bilingual-en:end -->

## 一个最小例子

设表有 8 个槽，$h(k)=k\bmod 8$。键 5 与 13 都得到哈希值 5。查找 13 时，算法先去槽 5，再逐项比较完整键；若只比较哈希值，它会把键 5 误认成键 13。
<!-- bilingual-en:start -->
Suppose a table has eight slots and $h(k)=k\bmod 8$. Keys 5 and 13 both hash to slot 5. A lookup for 13 first reaches that slot and then compares complete keys. Comparing only the hash would mistake key 5 for key 13.
<!-- bilingual-en:end -->

这个区别也解释了为什么缓存一个对象的哈希值可以加快初筛，却不能普遍取代对象的相等比较：哈希不同通常足以排除相等，哈希相同却仍然不能下结论。
<!-- bilingual-en:start -->
This also explains why a cached hash can speed up rejection without generally replacing equality. Different hashes can rule equality out, but equal hashes do not establish it.
<!-- bilingual-en:end -->

> [!question]- 回忆与辨别
> 已知 `hash(a) == hash(b)`，能否推出 `a == b`？
>
> **答案：** 不能。它们可能只是发生了碰撞；必须继续比较完整键。
