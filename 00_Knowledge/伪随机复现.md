# Pseudorandom reproducibility
<!-- bilingual-en:end -->

*伪随机复现*

<!-- bilingual-en:start -->
**Pseudorandom reproducibility** means being able to replay the same random input sequence under a specified computational protocol. It is useful when a surprising simulation result needs debugging, or when a code change should be compared on the same scenarios. A seed identifies a starting point for a [[伪随机数生成器|PRNG]]; it does not describe everything the program does after starting.
<!-- bilingual-en:end -->

**伪随机复现**是在明确的计算协议下，重放同一段随机输入序列。模拟结果异常、需要调试，或希望让代码改动面对相同情景时，这很有用。种子为[[伪随机数生成器]]指定起点，却没有说明程序启动后怎样使用它。

<!-- bilingual-en:start -->
A **random stream** is the ordered output of one generator. Replaying a stream and reproducing a final answer are related but different goals. The latter additionally depends on the input data, model, numerical operations and assignment of draws to tasks. Neither goal, by itself, proves the answer is correct; that belongs to [[Monte Carlo实现验证|implementation verification]].
<!-- bilingual-en:end -->

**随机流**是一个生成器按顺序发出的输出。重放随机流与重现最终答案有关，却不是同一目标；后者还依赖输入数据、模型、数值运算和随机数到任务的分配。两项目标本身都不证明答案正确，这属于[[Monte Carlo实现验证]]。

<!-- bilingual-en:start -->
## The same starting point, the same calls
<!-- bilingual-en:end -->

*相同起点，也要有相同调用*

<!-- bilingual-en:start -->
Python’s `random.Random` creates a generator object with its own state. Within the documented compatible seeding and `random()` protocol, two objects given seed `7` and the same calls reproduce the same two outputs:
<!-- bilingual-en:end -->

Python 的 `random.Random` 创建拥有独立保存状态的生成器对象。在文档规定的兼容初始化和 `random()` 调用协议下，两个对象以种子 `7` 开始，再执行相同调用，就会重现两个输出：

```python
import random

a = random.Random(7)
b = random.Random(7)

assert [a.random(), a.random()] == [b.random(), b.random()]
```

<!-- bilingual-en:start -->
The first values in this example are approximately `0.3238327648` and `0.1508491739`. If a diagnostic consumes one extra value from `b`, its next output is now the second value while `a` still returns the first:
<!-- bilingual-en:end -->

此例前两个值约为 `0.3238327648` 和 `0.1508491739`。若一个诊断步骤从 `b` 额外取走一个值，下一次 `b` 已经来到第二个值，而 `a` 仍返回第一个：

```python
a = random.Random(7)
b = random.Random(7)
_ = b.random()
assert a.random() != b.random()
```

<!-- bilingual-en:start -->
That inequality is a check of this specific example, not a theorem that different stream positions must have different numerical values. The general point is that their positions no longer align. A high-level draw, such as a normal sample, may consume a different number of internal values from another method. Changing a branch, call order or array size can therefore alter all later assignments.
<!-- bilingual-en:end -->

这里的不等式检查的是这个具体例子，不是说随机流的不同位置一定数值不同。普遍问题在于位置已经错开。正态抽样等高层调用所消耗的底层值数量，可能与另一种方法不同；改变分支、调用顺序或数组大小，都可能改变后面每个值的用途。

> [!tip] Resume from a saved state · 从已保存状态继续
> <!-- bilingual-en:start -->
> A seed reinitialises; a saved state records a later position. Python’s `getstate()` captures the current generator state and `setstate()` restores it. For example, save immediately before a diagnostic, run it, then restore before the original simulation continues. This replays that generator only: other generators, changed input data or external program state must be handled separately.
> <!-- bilingual-en:end -->
>
> 种子用于重新初始化；保存完整状态则记录运行到后面的某个位置。Python 的 `getstate()` 捕获当前生成器状态，`setstate()` 恢复它。例如在诊断前保存、诊断后恢复，再让原模拟继续。它只重放这个生成器；其他生成器、改变的数据或程序外部状态仍须分别处理。

## Record a replay protocol, not just a number
<!-- bilingual-en:end -->

*记录重放协议，而不只一个数字*

<!-- bilingual-en:start -->
A useful record identifies the generator algorithm and initialisation; the seed or saved state; relevant software versions and build; the methods, arguments and call order; and the mapping from tasks to [[并行伪随机子流|parallel streams]]. Include the input data/order and numerical environment when they can affect computation. These items explain how a saved number becomes the same sequence of model inputs.
<!-- bilingual-en:end -->

有用的记录应包含生成算法与初始化方式、种子或已保存状态、相关软件版本和构建、方法及其参数与调用顺序，以及任务到[[并行伪随机子流|并行随机流]]的映射。若数据及其顺序、数值环境会影响计算，也应一并记录。这些信息解释了怎样让一个保存的数字重新产生同一串模型输入。

<!-- bilingual-en:start -->
The compatibility promise is library-specific. Python documents stability for `random()` with a compatible seeder, while many other methods may change across versions. NumPy’s `Generator` stream-compatibility conditions include the same `BitGenerator`, seed, call sequence and arguments, build, environment and machine. Requested array size is an argument: a batch of five draws is not promised to match five scalar calls across all supported implementations. Pinning only the seed is therefore weaker than the documented replay contract.
<!-- bilingual-en:end -->

兼容承诺取决于具体库。Python 对兼容初始化下的 `random()` 序列作出稳定承诺，许多其他方法仍可能跨版本改变。NumPy 的 `Generator` 流兼容条件包括相同 `BitGenerator`、种子、调用序列及参数、构建、环境与机器。请求数组的大小也是参数：并非所有实现都承诺一次取五个值与逐次取五个标量完全相同。因此只固定种子，比文档规定的重放条件弱。

## Random-input replay and final-result replay
<!-- bilingual-en:end -->

*随机输入重放与最终结果重放*

<!-- bilingual-en:start -->
Even identical draws can produce different final bits when floating-point sums are grouped differently. In ordinary binary64 arithmetic, `(1e16 + -1e16) + 1.0` gives `1.0`, whereas `1e16 + (-1e16 + 1.0)` gives `0.0`: the inner small addition loses the unit through rounding. A parallel reduction can change such grouping. This is a numerical-order issue, separate from random-stream identity.
<!-- bilingual-en:end -->

即使随机数完全相同，浮点求和分组不同，也可能改变最终比特。在通常的 binary64 算术中，`(1e16 + -1e16) + 1.0` 得到 `1.0`，而 `1e16 + (-1e16 + 1.0)` 得到 `0.0`：后式内部的小量相加因舍入而丢掉了那个单位。并行汇总可能改变这种分组。这是数值顺序问题，与随机流是否相同分开。

<!-- bilingual-en:start -->
Sharing one stateful generator across threads can make the assignment of draws depend on scheduling, even when access is thread-safe. Give stable tasks recorded streams, and control output ordering if exact replay matters. Comparing two policies also requires each shared draw to represent the same shock; matching seeds alone does not establish [[共同随机数输入同步|semantic input synchronisation]].
<!-- bilingual-en:end -->

多个线程共享一个有状态生成器时，即使访问是线程安全的，哪个任务得到哪个值仍可能由调度决定。若要求精确重放，应为稳定任务分配有记录的随机流，并控制输出顺序。比较两个方案时，共享的数还须代表同一个冲击；种子相同本身不证明[[共同随机数输入同步|输入语义同步]]。

> [!question]- A diagnostic changes the path · 诊断改变了路径
> <!-- bilingual-en:start -->
> Two runs use the same seed, but one adds a random diagnostic halfway through. Should all later simulated paths agree? Not generally: the original stream has advanced. Use a separately assigned diagnostic stream or deliberately restore the saved state when that is the intended protocol. Then verify the input trace, not just the final rounded answer.
> <!-- bilingual-en:end -->
>
> 两次运行种子相同，但其中一次中途新增随机诊断，后续路径应该逐条相同吗？通常不能这样期待，因为原随机流已被推进。可按预定协议给诊断分配单独的流，或明确恢复之前保存的状态；然后核对输入轨迹，而不只比较最终四舍五入的结果。
